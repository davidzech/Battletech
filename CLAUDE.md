# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A repo of custom tabletop BattleTech campaigns, one per folder under `campaigns/`, mostly Markdown. A Go web server turns the campaigns into a website; there is no lint or test tooling. The only campaign so far is `RefusalWar/` ("Refusal War", inspired by the MechWarrior 2 video game, a conflict between Clan Wolf and Clan Jade Falcon); expect more, so keep campaign-specific rules inside the campaign's folder and put only genuinely shared things (like `data/units.json`) at the top level.

## Structure

Every campaign folder (shown for `campaigns/RefusalWar/`) has the same shape:

- `campaigns/RefusalWar/Intro.md` - campaign introduction (currently just front matter). Its YAML front matter holds campaign-level fields: `min_players` and `max_players` (how many players the campaign supports; Refusal War is 1 to 2), shown under the campaign's name on the home page's campaign list. Leave `max_players` out to show nothing. It also holds the campaign's starting instructions: `starting_named_pilots` (how many named pilots must be named before scenarios deploy; Refusal War is 2; see Named pilots under Playthrough identity), `starting_pilot_sp` (the SP each of them allocates; 150) `starting_bv` (the most BV the starting hangar may total; Refusal War is 10000) and `starting_min_mechs` (the fewest mechs it may hold; Refusal War is 5). `starting_warchest` (the SP a started campaign's warchest begins with; Refusal War is 5000; stored per run in `campaign_runs.warchest`, set by `StartRunWithPilots`, listed in the start rules and shown as the Funds box in the Manage page's Warchest section; a run started before the column existed reads 0). `mission_term` (what the campaign calls a scenario, e.g. `Sortie` in Refusal War; `Scenario` by default; `Campaign.MissionNumber`/`MissionName` give "Sortie 001" and "Sortie 001: Pyre Light" for the scenario page's kicker, the Manage page's back link, the Next missions links, checkpoint labels and the MekBay operation's name) and `mvp_sp` (the extra SP a mission's MVP earns; Refusal War 20; 0 means no MVP, and an MVP is then refused; a scenario's Outcome.md `mvp_sp` overrides it). These are listed as bullets on an unstarted campaign's page (the site doesn't model Scale, it just says 10,000 BV). **The starting hangar is checked** by `checkStartingHangar` (`startcheck.go`): units are looked up in the catalog, BV is each unit's *base* BV (what a standard 4/5 pilot gives it; pilot skill never matters), only catalog type `Mek` counts as a mech (a tank adds BV but isn't a mech), and a unit missing from the catalog is a problem since its BV is unknown. The wizard asks for the check as soon as a pasted link has a valid shape (`GET /api/campaign/hangar-check?campaign=&hangar=`, which reads the force from MekBay, never writes, and needs a seed with a named account): it waits 350 ms after typing, shows a spinner and "Reading your hangar..." meanwhile, ignores a reply for a link that has since changed, then shows a summary (mechs, BV of the limit), the units counted and every problem, and keeps Start campaign disabled until the hangar passes. Because the player fixes the hangar in MekBay without changing the link, a refresh icon embedded on the right of the link box re-reads it at once (disabled until the link has a valid shape, and spinning while it reads), and returning to the tab while the hangar is failing re-checks it automatically; each read carries a sequence number so an older reply can never overwrite a newer one, **a refresh of an unchanged link keeps the finished result on screen** (a small "Updating" note with a spinner appears beside the summary, the new data replaces it only when it arrives, identical data repaints nothing at all, and a failed refresh keeps the old data with a "Couldn't refresh" note, so Start follows the committed data and the server re-checks on submit) while a *changed* link clears it, since the old result would describe a different hangar, and the reason a hangar fails is shown once (in the status area, and as the disabled button's tooltip) rather than repeated in the hint line. `POST /api/campaign/start` runs the same check on the server before creating anything (400 with the problems, 502 if MekBay can't be read); a started campaign can't be started again (409), so its hangar is never replaced from there.
- `campaigns/RefusalWar/Names.md` - the campaign's own example names, shown as the placeholders of the force and pilot name boxes (start wizard, Recruit dialog) so they fit its faction and era: front matter `force_names`, `male_pilot_names`, `female_pilot_names`, `neutral_pilot_names` (names for any portrait, mixed into both). Each list given replaces the baseline list of the same kind in `static/pilotnames.js`; one left out keeps it; the file is optional (`names.go`, `Campaign.Names`, sent as `data-names` on the `pilotnames.js` script tag; every name must pass `parseForceName`/`parsePilotName` or it is a campaign problem; `TestCampaignNames`). Refusal War's are Clan Wolf units (canon and invented) and trueborn given names.
- `campaigns/RefusalWar/Keywords.md` - registry of every keyword scenarios can grant or require, one bullet per keyword ID.
- `campaigns/RefusalWar/Scenario_NNN/` - one folder per scenario, zero-padded and numbered sequentially, containing `Setup.md` (fluff, map, forces, special rules) and `Outcome.md` (victory conditions and rewards). `Scenario_000` is the "Trial of Position", a one-off graduation mission whose kill count determines each pilot's starting SP. Later sorties are referred to as "Sortie 001", etc.

## Website

Go is the base for the website, chosen so it can grow into keyword/branch state tracking rather than staying a static site. Run it from the repo root with `go run .` (flags: `-addr :8080`, which defaults to `localhost:8080` under `go run` (detected by the `go-build` temp path of the binary) so Windows Firewall doesn't prompt for every rebuilt binary; `-content campaigns`, `-db playthroughs.db`, `-postgres <url>`). It reads the campaign folders on every request (edit a Markdown file and refresh), renders Markdown with `goldmark` and front matter with `yaml.v3`, and embeds its templates and CSS from `internal/site/` (`templates/*.html`, `static/style.css`). Dark mode only, with an industrial-yellow BattleTech look (no theme toggle). The site's emblem (a round mech skull on a transparent background) is `static/emblem.png` (512x512, shown at 2rem as the header's brand mark), with `static/favicon.png` (192) and `static/apple-touch-icon.png` (180) cut from the same image; `GET /favicon.ico` serves the PNG favicon. Every page's big title (`h1.bt-title`) use the BattleTech old-style font `internal/site/static/bt_oldstyle.ttf`, loaded with `@font-face` in `style.css`. The scenario fluff (the leading blockquote in `Setup.md`) is pulled out of the body and shown as an "incoming transmission" briefing block; a paragraph that opens with a quotation mark becomes a styled pull quote, and a paragraph right after it that opens with an em dash (`— Name, Title`) becomes its attribution line. The scenario's Waypoints section (see the scenario conventions) and Outcome section are collapsed `<details class="fold">` blocks, Waypoints above Outcome, (a collapsed Force files block with the `.mul` downloads used to sit between them; it is commented out of `scenario.html` for now with a Go template comment, and the `/<campaign>/<scenario>/forces/<file>` route still works, so restoring it is just removing the comment); their open/close animation is a small Web Animations script in `layout.html` (the CSS-only `::details-content` approach doesn't work in Firefox, so don't switch back to it); without the script it still toggles. Routes: `/` (campaigns), `/<campaign>/` (intro and scenarios), `/<campaign>/<scenario>/` (Setup then Outcome, plus download buttons for the `.mul` files listed in the `forces` front matter, served from `/<campaign>/<scenario>/forces/<file>`; only listed files are served), `/<campaign>/keywords/`. Campaigns are any folder under `campaigns/` containing `Scenario_NNN/` folders, so a new campaign or scenario that follows the conventions below needs no code changes. `go vet ./...` and `go test ./...` are the checks.

## Checks, CI and Docker

The checks are `gofmt -l .` (must print nothing), `go build ./...`, `go vet ./...`, `staticcheck ./...` (config in `staticcheck.conf`, which turns off ST1005 because a few error strings are visitor-facing sentences; run it with `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...`) and `go test ./...`. `.github/workflows/ci.yml` runs all of them, plus a `docker build`, on pushes to `main` and on pull requests. The `Dockerfile` is a multi-stage build (pure-Go, `CGO_ENABLED=0`) into a distroless nonroot image that bundles `campaigns/` and keeps the SQLite database in the `/data` volume (`-db /data/playthroughs.db`) unless `DATABASE_URL` is set; it listens on 8080. `data/units.json` is not in the image (see `.dockerignore`). Hosting note: DigitalOcean App Platform's disk is ephemeral and would lose a SQLite file on every deploy, so there it must run against Postgres via `DATABASE_URL`. The footer shows the build's short commit hash: the revision `go build` stamps when `.git` is present, else the `COMMIT_HASH` environment variable (on App Platform set it to `${_self.COMMIT_HASH}`, since neither the Go buildpack nor the Dockerfile build sees `.git`), else `dev` (as under `go run`); see `internal/site/commit.go`.

## Playthrough identity (seeds)

Visitors track their own campaign without logging in, using a **seed**: 8 to 32 lowercase letters and digits that the visitor chooses or generates (the Random button makes two English words plus three digits, e.g. `ironfalcon417`). The seed is the only credential, so anyone who knows it can read and change that playthrough; it is stored in an HttpOnly `seed` cookie (one year) and shown back to the visitor in a popup. The server hashes it (`playthroughID` in `seed.go`) into the opaque key used in the database (`internal/site/store.go`); the seed itself is never stored in the database. The store speaks SQLite (pure-Go `modernc.org/sqlite`, file set by `-db`, git-ignored; the default for local runs) or PostgreSQL (pure-Go `pgx`): the `-postgres` flag defaults to `$DATABASE_URL`, and when that is non-empty it is used instead of `-db`. Queries are written once with `?` placeholders and rebound for Postgres by `Store.q`; keep SQL to what both accept. Postgres is for hosts without a persistent disk (DigitalOcean App Platform with its dev database). `TestStorePostgres` runs only when `TEST_DATABASE_URL` is set (CI sets it with a Postgres service container); locally, e.g. `docker run -d -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=bt -p 55432:5432 postgres:17-alpine` then `TEST_DATABASE_URL=postgres://postgres:pw@localhost:55432/bt?sslmode=disable go test ./...`. In code and the database a tracked run is a "playthrough", to avoid clashing with the `campaigns/` content folders.

A seed is an **account**: a new seed continues to a second popup step asking for the **account name** (`Playthrough.AccountName`, whatever the player likes to call it; the column is still `playthroughs.company_name` from when it was a company; the name shown in the header chip), and each campaign's force has its own **force name** (see below), because campaigns can be thematically different forces, not necessarily a "company". The account name is validated by `parseCompanyName` in `setup.go`; a seed counts as set up once it has one). An account then runs **campaigns**, each with its own state: a campaign is *started* from its own page (the Start button on `/<campaign>/` opens a **wizard**, see Named pilots below), whose last step makes **that campaign's hangar**, by default by **picking its mechs on the site** (see Building the starting force below), or from **a MekBay hangar link** as a shortcut for a force already built there (any MekBay link will do: `parseHangar` in `setup.go`, mirrored by `canonicalHangar` in `campaign.js`, keeps only the force's instance ID and reduces it to `https://mekbay.com/?instance=<uuid>`, so `&sel=` (the selected unit, which we have no use for, even a garbled one), `&operation=`, tracking parameters and fragments are dropped, and a list of forces `<mine>,enemy:<theirs>` gives the first friendly one; only https on mekbay.com/www.mekbay.com is accepted, and an operation link gets a message saying to paste the hangar link instead; the wizard rewrites the link box to the plain link as soon as a pasted link is recognised; `campaign_runs` no longer has a `hangar_sel` column in its `CREATE`, existing databases keep the unused column, which defaults to empty so inserts without it work) and records a `CampaignRun` (table `campaign_runs`, one row per seed and campaign slug; the row existing means started). Starting a started campaign again is refused (409). While a campaign's pages are open the header shows a "Your hangar" link to that campaign's hangar. Endpoints (same-origin only): `POST /api/seed`, `POST /api/account` (just the account name) and `POST /api/campaign/start`; the popup logic is `internal/site/static/seed.js` and the campaign page's is `campaign.js`. There is deliberately no human player count (it used to be asked for but nothing used it). **MekBay accounts: all synthesized, nobody enters an ID** (`accounts.go`). MekBay identifiers are implicit (any UUID a client presents is an account that owns what it saves, and only the owner may change a force). The site never asks a player for a MekBay user ID (it used to: a Player 1 to 4 field in the Account details dialog, the table `player_accounts` and checks that counted the IDs saved before a campaign could start or deploy with N players; all of that is gone, and an old database loses the table). Every account the site needs is **derived from the seed**: `MekBayUID(seed, slot)` is a salted SHA-256 of the seed laid out as a v4 UUID, a stable 1:1 projection of seed to site-managed ID, recomputed from the seed whenever needed, never stored in the clear and never logged; a seed has exactly **one** such account (`SlotHangar`, a historical name: its derivation salt `p1` is kept so hangars already copied stay owned by it). It owns everything the site keeps in MekBay for the seed: the campaign's hangar copy, the OpFor, each player's force in a battle and the battle's operation, so everyone at the table can edit all of it. A browser acts as it through a **MekBay link** (see The MekBay proxy), so a player opens MekBay from a link and never sees an ID. **Starting a campaign asks how many players** when the campaign allows a range: the start wizard's step after the force name, the same [1][2][3][4] picker as the Deploy wizard up to the campaign's maximum, every count in the range offered (`parseStartingPlayers`; `POST /api/campaign/start` needs `players` when the range is more than one count, 400 otherwise). The count is saved on the run (`campaign_runs.players`, `CampaignRun.Players`) and is only the Deploy wizard's **default** (`data-default-players`; a deploy can still override it). The Manage page's **Overview** section (it was Warchest) shows the Funds box and a **Default players** picker (`static/overview.js`, `POST /api/campaign/players`, `Store.SetRunPlayers`, the same range rule). `TestMekBayUID`, `TestOneAccountPerSeed`, `TestOldPlayerIDsAreForgotten`, `TestAccountSettingsAskForNoMekBayIDs`, `TestStartNeedsAPlayerCount`, `TestOverviewDefaultPlayers`. **The hangar is cloned**: `campaign_runs.hangar_url`/`hangar_instance` are then the site's copy and the new `source_url` column is the player's link (`CampaignRun.Owned()` is true when it is set); the copy is hidden from normal play (no 'Your hangar' header link), but the Manage page shows nothing of it (no instance ID, account or link: there is no Re-import hangar or open-it-editable any more); `SourceURL` is kept as a record of where the copy came from; a started campaign's hangar is never replaced from the start endpoint, which answers 409). Repairs, rearms, purchases and (later) deploys all act on the site's copy with the derived account; a run from before this change has no `source_url`, so those endpoints answer 409 and the buttons are disabled until the hangar is imported again. The old `owner_uid` column is unused. `TestMekBayUID`, `TestCloneForceIsPristine`, `TestStartClonesTheHangar`. Keyword and scenario-progress tracking build on this but are not implemented yet.

**Force names.** Each campaign run has its own **force name** (`campaign_runs.force_name`, `CampaignRun.ForceName`; `ForceLabel()` falls back to "Your force" for a run from before forces were named), chosen in the start wizard's first step (a random BattleTech-sounding placeholder from `static/pilotnames.js` `PilotNames.randomForce`; `POST /api/campaign/start` needs `force_name`, validated by `parseForceName`, 1 to 40 characters in the same style as an account name: `parseName`) and renamed later in place on the Manage page: the force name is the **Overview section's heading**, with a pencil that turns it into a text box (`static/overview.js`: Enter or Save keeps it, Escape or Cancel doesn't; `POST /api/campaign/force-name`, `Store.SetForceName`). The campaign page's started heading, the Manage page's hangar and delete texts use it; the header chip shows the account name. `TestForceNames`, `TestStartNeedsAForceNameAndItCanBeRenamed`.

**Named pilots** follow BattleTech: Hot Spots - Draconis Reach, "Named Pilots" (pp. 34-35; the book is at `C:\Users\david\iCloudDrive\Documents\Battletech\Books\`, too big for the Read tool, so extract pages with `pdftotext -f 34 -l 37` and note the PDF's physical page is 2 higher than the printed number). Only named pilots improve Gunnery/Piloting, use Edge and earn Edge abilities; which abilities a pilot has chosen is tracked (see Edge abilities below). A pilot tracks one number, **total SP earned** (`named_pilots.sp_total`), and the SP allocated so far in four columns (Gunnery, Piloting, Edge tokens, Edge abilities); **unallocated SP is the total minus the columns' sum** (`NamedPilot.Unallocated`), never stored separately. A new pilot's starting SP is all allocated; later SP is earned into the total (`Store.EarnSP`; on the site, the `earned` field of `POST /api/pilots/allocate`) and spent with `Store.AllocateSP` (`POST /api/pilots/allocate`, which adds to the columns and refuses more than is unallocated, checked in the same SQL statement). `Store.AwardSP` raises total and columns together; only tests use it (the `POST /api/pilots/sp` endpoint that exposed it is gone). A database from before the total existed gets `sp_total` backfilled to the columns' sum (`Store.init`, `TestMigrateSPTotal`). `pilot.go` holds the book's Named Pilot Improvement Table as ladders (cumulative SP to reach a level), and derives a pilot's levels; `TestKirbyExample` replays the book's worked example. **Handicap is deliberately not tracked** (the book gives each step a handicap that balances opposing forces; this campaign doesn't use it), so don't add it back. A new pilot is a 4/5 pilot with 1 Edge token and 0 SP. At most four living named pilots per command (`maxNamedPilots`); a pilot killed in action (shown as "Killed in Action" everywhere; the column and code say `fallen`) keeps their row but frees a place, can't earn SP and leaves the active list and the overview. Tables/queries: `named_pilots`, `Store.Pilots/AddPilot/EarnSP/AllocateSP/MarkFallen`; endpoints `POST /api/pilots`, `/api/pilots/allocate`, `/api/pilots/fallen` (`pilots.go`), and the Named pilots panel on the Manage page (`pilots.js`): each pilot is a card with the wizard's yellow-number stat boxes, a **Manage SP** button and a **More** drop-down (a native `<details>`, closed by an outside click or Escape) whose first item is "Mark as killed in action" (`POST /api/pilots/fallen`); room for more items later. A pilot killed in action isn't removed: their card moves to a **Memorial** section below the active pilots (no buttons): the portrait goes grayscale with a red rotated **K.I.A.** stamp laid over it (`.kia-stamp`), the stats and ability chips are dimmed, and the "Killed in Action" badge stays vivid red, and they stay revivable or deletable under Advanced Management. Manage SP opens a level-up dialog (`#sp-dialog`) with the same sliders, number boxes and stat boxes as the wizard (`static/allocator.js`, the shared `SPAllocator`, which the wizard also uses): the sliders spend only the pilot's unallocated SP (the sliders and number boxes show each column's whole total with what the pilot already has as their minimum, and reach up from there by the unallocated SP; a row's number turns yellow while it has a pending change; the boxes preview the new levels), Apply saves, and an "Add earned SP" box (which asks for confirmation) *stages* SP for the pilot's total (SP is entered by hand because scenario rewards aren't automated yet): it raises what can be spent in the dialog, shows "+N SP earned. Not saved until you press Apply" with a Clear link, and nothing is saved until Apply, which posts the earned amount and the allocation together to `POST /api/pilots/allocate` (`earned` field, `Store.ApplySP`, one atomic statement); closing the dialog discards the staged SP. **Each campaign sets its starting instructions in `Intro.md` front matter**: `starting_named_pilots` (Refusal War: 2) and `starting_pilot_sp` (Refusal War: 150, the SP each starting pilot allocates; the book's p. 17 gives 150 too). **Starting a campaign is a wizard** (`#start-wizard`, `campaign.js`): a step naming the force, a step asking how many players (only when the campaign allows a range), one step per starting pilot (a name plus an allocator that splits the pilot's starting SP over the four columns, with four labeled boxes (Gunnery, Piloting, Edge tokens, Edge abilities, each a big yellow number with a big centred level with a tiny, thin "-> next level" (a small drawn arrow and the next level in bold muted gray, like the caption) at its lower right, "SP/needed SP" beneath it and a thin yellow progress bar for how far along that is; at the top of the ladder it says "max" with a full bar and no next level) beside the name showing the levels the allocation reaches live, computed from the same ladders the server uses, passed to the page as JSON in `data-ladders`; every SP must be allocated before moving on, and the allocator refuses to over-allocate; the sliders and the number boxes' arrows both step by 10 SP, and Next stays disabled, with a hint line saying what is missing, until the step is valid), then a step for the hangar link, with a step counter and progress bar at the bottom. It posts everything to `POST /api/campaign/start` in one go (fields `pilot<i>_name`, `pilot<i>_gunnery`, `_piloting`, `_edge_tokens`, `_edge_abilities`); `parseStartingPilots` validates it (exactly the campaign's pilot count, unique names, each allocating exactly `starting_pilot_sp`) and `Store.StartRunWithPilots` creates the run and the pilots in one transaction, refusing a second start (`ErrAlreadyStarted`). Posting again for a started campaign only changes its hangar link (the small `#run-dialog`). **Recruiting costs SP and the force has a size limit.** `Intro.md` sets `max_named_pilots` (the most living named pilots at once; `Campaign.PilotLimit()`, default 4, Refusal War 4) and `recruit_cost` (SP taken from the warchest to recruit a new named pilot after the start; Refusal War 300; the starting pilots are free). `POST /api/pilots` charges the warchest first (409 'Not enough in the warchest' when it can't) and refunds it if the pilot can't be added (a taken name or portrait, a full command). The Manage page's **Recruit New Pilot** button is grayed out when the command is full or the warchest can't pay, with a brief gray note under it (`RecruitNote`: 'Your command is full: 4 of 4 pilots.', 'Recruiting costs 300 SP (warchest: 120).', or just 'Recruiting costs 300 SP.' while it is available); the dialog shows 'Cost 300 SP. Warchest A → B SP.' and its button reads 'Recruit for 300 SP'. `TestRecruitingCostsSP`. The campaign's pilot count is a *starting* requirement only: pilots can die mid-campaign, so deploying never checks how many are alive, and pilots are added later with the **Recruit New Pilot** button under the active pilots on the Manage page (above the Memorial), which opens a one-step dialog (`#recruit-dialog`, `pilots.js`): a random portrait no living pilot has (click it for the picker), a name, a rank, and the campaign's `starting_pilot_sp` (150 in Refusal War) to allocate with the same sliders, number boxes and live stat boxes as the start wizard (`SPAllocator`); spending all of it is optional, and whatever is left stays unallocated for Manage SP (a campaign with no starting SP shows no sliders). It posts `POST /api/pilots` with the allocation in the `gunnery`/`piloting`/`edge_tokens`/`edge_abilities` fields (refused above the starting SP; `Store.AddPilotWithRank` takes the allocation and a total, which is the starting SP; names are unique per campaign ignoring case, a command holds `maxNamedPilots` living pilots, so the button is disabled with a reason when it is full and comes back when a pilot is Killed in Action). The wizard script has no JS test runner; `TestScriptsParse` only syntax-checks it, so after changing it drive it with jsdom against a running server (that is how it was verified). The book's 100-SP-per-track cap is deliberately not enforced because campaigns set their own rewards (Scenario 000 pays 150 to 900); starting SP; the MVP and combat-pay rules are not built yet (assigning pilots to hangar units is in the Deploy popup, see MekBay hangar integration).

**Starting Edge abilities and placeholder names.** In the start wizard a pilot whose allocation reaches an Edge abilities level must choose that many abilities before Next works (the same combo boxes and ability cards as the Manage picker, `#wiz-body .wiz-abilities`, `AbilityCard`); moving SP out of the Edge abilities column until the level drops removes the choices that no longer fit (last first). `parseStartingPilots` requires exactly that many distinct, known `pilot<i>_ability` values and `StartRunWithPilots` stores them as the pilot's learned abilities. The name boxes' placeholder is drawn at random from `static/pilotnames.js` (`PilotNames.random(group)`), following the portrait's gender group (Male/Female draw from their own names plus neutral ones; Generic and Special from all) and changing when the portrait does (in the wizard and the Recruit dialog). `TestStartChoosesEdgeAbilities`; driven with jsdom.

**Edge abilities.** The twelve Edge abilities of Hot Spots: Draconis Reach (printed p. 166, physical page 168 of the PDF; text kept as the book prints it, Alpha Strike rule first with the Total Warfare rule in parentheses) are the catalog in `abilities.go` (`edgeAbilities`: stable ID, name, category, text; Attack, Indirect Fire, Defense, Heat, Melee, Movement). The book says that when a named pilot reaches a new Edge abilities level they choose one, permanently (p. 36, step 4); this site only records the choice, it doesn't play the abilities. A pilot may hold as many abilities as their Edge abilities level, so **pending = level - learned** (`NamedPilot.PendingAbilities`, never negative). Whenever it is above zero the pilot's card on the Manage page shows a yellow "Choose a new Edge ability" / "Choose N new Edge abilities" button beside an "Edge abilities" row of chips for the ones already learned (hovering or keyboard-focusing a chip shows the same ability card as the picker in a floating panel anchored under it, `AbilityCard.attach` in the shared `static/abilitycard.js`, like the mech icon hover card on the overview; there is no native `title`). It opens a picker (`#skill-dialog`, `pilots.js`) with one combo box per pending ability, grouped by category and listing only abilities the pilot doesn't have; one chosen in another box is greyed out, and the chosen ability shows as a card under its box (`AbilityCard.fill` in `abilitycard.js`, shared with the Deploy popup; it also owns the catalog, `splitTrigger` and the floating panel, which is a popover so it can sit on top of another popover or a dialog; `pilots.js` and `mekbay.js` load it after `abilitycard.js`): its name, a pill in its category's colour, and the rule with the **trigger in bold** as the book prints it (everything up to the first colon outside parentheses, `splitTrigger` in `abilitycard.js`, since Protector's trigger contains a "(TW: 1 hex)" aside) and each "(TW: ...)" aside dimmed; an empty box shows a dashed placeholder. **Learn** asks for confirmation (the choice is permanent) and posts all the choices together to `POST /api/pilots/abilities` (repeated `ability` fields; `Store.LearnAbilities`, one transaction, which refuses a wrong number of choices, an unknown or already-learned ability, a pilot with nothing pending, and a pilot killed in action). Learned abilities are rows of `pilot_abilities` (pilot, ability ID, order learned), removed with the pilot or campaign. They are permanent like allocated SP: the only undo is **Reset Edge abilities** in Advanced Management (`Store.ResetEdgeAbilities`, `POST /api/pilots/abilities/reset`, after a confirm; it works on killed pilots too, doesn't touch SP, and leaves the pilot owed the choices again). Resetting a pilot's *SP allocation* (the records dialog's other reset, formerly labelled "Reset abilities", now "Reset SP allocation") **also forgets their learned Edge abilities**, since they depended on that SP: so does setting a total below the allocation with the reset agreed (`ResetPilotSP` and `SetPilotTotal` delete the `pilot_abilities` rows in the same transaction; a total at or above the allocation touches nothing), and the confirmations say so when the pilot has any (`TestSPResetForgetsEdgeAbilities`). ## Campaign files are checked

Each kind of file has its own front matter schema (`introMeta`, `setupMeta`, `outcomeMeta` in `content.go`), decoded strictly (`readMarkdown` with `KnownFields`), so a misspelt or misplaced key is an error rather than a setting silently ignored. Every problem in a campaign's files (front matter that doesn't parse or has unknown keys, outcome rules that don't compile, keywords not in Keywords.md, branches to scenarios that don't exist) is collected in `Campaign.Problems`, listed in a red box at the top of the campaign's page for its author, and `TestCampaignFilesAreValid` keeps the real campaigns free of them (`TestCampaignProblemsAreReported`). `Library.Campaign(slug)` loads only that campaign's folder, not every campaign.

## Code layout notes

- Every endpoint that changes a campaign starts with `runRequest` (same origin, a seed, a named account, a started campaign; returns the playthrough, campaign and run) or `pilotRequest` (the same without the run), and a change to the hangar with `hangarRequest` (also needs a hangar the site owns); a paid hangar change goes through `payForHangarChange` (charge the warchest, make the change in MekBay, refund on failure) (`hangaredit.go`).
- Every change to a force in MekBay is a read, modify, save through `MekBayClient.editForce` and the session's `getForce`/`saveForce`/`saveData` (`mekbay.go`).
- Unit names and mech-row views are `unitview.go`, the Deploy popup's endpoints `deployhttp.go`, the OpFor draft `opfor.go`; the test fakes (`fakeMekBay`, the test server helpers) are in `testfakes_test.go`. The browser scripts share `static/dom.js` (`Dom.el`, `Dom.commas`), which the layout loads before any page script (`TestPagesLoadTheSharedHelpersFirst`); the jsdom checks load it first too.
- The outcome engine is `outcomes.go` (rules), `outcomestore.go` (storage) and `outcomehttp.go` (endpoints); the store is `store.go` (schema, runs), `pilotstore.go` (named pilots) and `battlestore.go` (battle operations).
- Pages are rendered into a buffer before anything is sent, so a template error is a clean 500. The recruit rules are `recruitStatus` (`pilots.go`).
- Mech lists size every row to its content (`.mech-list { grid-auto-rows: max-content }`): in a fixed-height scrolling list, auto rows were held to the rows' min-height at high display scaling and the content (the role band, the highlight) spilled into the next row.

## Long-term direction

These files are meant to eventually drive a campaign website: scenario pages with fluff images, tracking of scenario forks/jumps (branching between scenarios), and per-playthrough state via KEYWORDS. Keywords are tracked by the campaign as a whole, not by individual pilots, copying how BattleTech: Aces (Scouring Sands) tracks them. Only a simple read-only site exists so far (see Website above); branch tracking (the campaign log) and the keyword ledger exist (see The outcome engine); keywords that gate scenarios are not built yet, so don't build them unprompted. When adding or reformatting data keep it both machine-parsable and human-readable/writable: consistent headings and names, plain Markdown/XML/JSON, no ad-hoc prose where a structured field would do (e.g. scenario IDs, branch targets, keywords granted or required). Prefer stable identifiers over free-text references.

## MekBay hangar integration

**Built so far: deploying a force for a scenario.** A scenario page with OpFor files shows a "Deploy your force" section once the playthrough has *started that campaign* (otherwise it points to the campaign page). Its button opens a popup (`mekbay.js`, `#deploy-dialog`) fed by `GET /api/mekbay/hangar`: every unit of the campaign's hangar, read anonymously from MekBay (`MekBayClient.ReadHangar`), with name (Clan name preferred), class, tonnage, role, pilot and skills, Damaged/Destroyed tags and **base BV**: this campaign (a custom Classic BattleTech ruleset in the style of BattleTech: Aces, partly homebrewed) never lets pilot skill change a unit's BV, which matches the book's rule that named pilots' skills don't affect BV and avoids rewarding bad pilots with room under the cap. `adjustedBV` (`units.go`, MekBay's BV 2.0 table) is kept only for the `bv` metadata of the OpFor force we write, which is what MekBay itself would total. The player ticks the units for the mission; a scenario's `bv_limit` front matter (optional, e.g. `bv_limit: 7500` in Scenario 001, a little under the Jade Falcons' 7,934 base BV, since the players' named pilots are better than 4/5 for free and the second OpFor arrives late; absent means no limit) caps the total, checked in the page and again by `deployProblem` (also refuses destroyed and unknown units). Deploying is the Deploy wizard's Start battle (see The Deploy wizard and Battles below): it builds a force per player and the OpFor (from the scenario's `.mul` files, one group per file, "OpFor 1", "OpFor 2"; pilots and skills from the `.mul`; unit IDs from `units_index.json`) and one operation pairing them. (An earlier single-player deploy, `POST /api/mekbay/deploy` with `SyncOperation`, which also rearranged the hangar into Deployed and Hangar groups, has been removed.) **Pilot assignment** is part of the popup (below). `units_index.json` is a slim copy of `data/units.json` (name, chassis, model, BV, tons, weight class, role, type, tech base, icon file name) embedded because the full catalog isn't in the Docker image; it also carries each mech's `engine` (the crippling rule) and `ammo` entries (the rearm breakdown); regenerate it with `go generate ./internal/site` after refreshing `data/units.json` (see Unit names, icons and mech rows). Tests use a fake `MekBay` (`WithMekBay`) and a fake WebSocket server; `TestMekBayLive` hits the real mekbay.com and only runs when `MEKBAY_LIVE_UID` and `MEKBAY_LIVE_INSTANCE` are set (it reads the hangar and creates an OpFor force and operation in that account, but leaves the hangar's groups alone). Not built yet: reading damage after a sortie (the start/end snapshots below) and splitting `enemy:` IDs out of a pasted multi-force link.

**Hover cards on the campaign overview.** Hovering a pilot in "Your force" shows the same pilot card as the Deploy popup (after half a second, interactive, with the Edge ability cards): the card's content now lives in the shared `static/pilotcard.js` (`PilotCard.build` / `PilotCard.attach`, used by `mekbay.js` and by `static/roster.js`, which attaches it to each `.roster-pilot[data-name]` row from the overview's `data-pilots` and `data-abilities`; the rows are focusable, so the keyboard gets it too, shown at once on focus). **The outcome engine (mission outcomes, rewards, keywords).** A scenario's `Outcome.md` front matter says what the players report when the mission is over and what follows (`outcomes.go`, `expr.go`; `Scenario.EvaluateOutcome`). Most scenarios follow the **BattleTech: Aces model**: (1) the objectives met grant SP into the mission's **pool**; (2) the mission gives a flat `pilot_sp` to each **active** pilot, **half to each benched** pilot (one who did not take part) and **none to a pilot killed**, who is killed in action; these shares are **drawn from the pool**; (3) what is left of the pool goes to the **warchest** (a pool too small to pay every share is split in proportion); (4) objectives met or missed grant **keywords** into the campaign ledger. Example: objectives total 600 SP, `pilot_sp: 80`, four pilots, two active: (80 + 80) + (40 + 40) = 240 come out of the pool and 360 go to the warchest; if one of the active pilots was killed it is 80 + 0 + 40 + 40 = 160 and 440. Front matter: `pilot_sp: 80` (a number or an expression over the mission inputs) and `objectives: [{id, label, sp, grants, unmet_grants, required}]` (a `required` objective is a primary one: the dialog ticks it and disables the box, and the server refuses a report without it), which expands to a yes/no mission input and a rule adding `sp` to the pool and granting keywords. A scenario that is not like that, such as the bootstrap mission **Scenario 000** (the outlier: kills pay SP straight to a pilot from a table, and a pilot with no kills or killed is removed with a free replacement, and there is no pool), says what it needs with `inputs` (`id`, `label`, `scope` pilot|mission, `type` number|bool, `min`, `max`) and `outcomes`, a list of rules `{when, label, sp, pool, warchest, kia, free_recruits, grants}`. Every pilot has two built-in inputs, **Active** (unticked: benched) and `killed`. A rule that gives `sp` or `kia` or reads a pilot input (`killed` is one) is a pilot rule, tried for each active pilot (`sp` goes straight to the pilot, not through the pool); any other is a mission rule, tried once (`pool` and `grants` are mission-only); `warchest` and `free_recruits` add up from any rule. Expressions are **expr-lang** (https://expr-lang.org, `github.com/expr-lang/expr`) type-checked when the scenario loads against its inputs (a number input is an int, a bool input a bool; a condition must be true or false), so a typo is caught at once (`Scenario.OutcomeError`, which disables the engine for that scenario; `TestOutcomeRulesCompile` checks every real scenario compiles). Keywords must be registered in the campaign's `Keywords.md` (a bullet starting with the ID in backticks: `keywordIDs`, `Campaign.Keywords`), or the scenario is refused at load (`checkGrants`). **Completing**: a scenario with an outcome has a **Complete mission** button on its page (`#outcome-dialog`, `static/outcome.js`), which does not repeat the Outcome.md text (the Outcome dropdown is on the page for a completed mission, and for a page with no completion dialog, such as a scenario without an outcome engine or an unstarted campaign): a card for every living named pilot (Active, Killed in action, and the scenario's own pilot inputs), the mission's objectives with their SP, and the result previewed as you enter it by asking the server (`POST /api/campaign/scenario-outcome`, which changes nothing); **Commit as completed** asks for confirmation and posts `POST /api/campaign/scenario-outcome/commit`, which applies every effect and records the report in one transaction (`Store.CompleteWithOutcome`: SP to the pilots, pilots killed in action, warchest, free recruits, keywords into `campaign_keywords`, and the completion row with the report in `scenario_completions.outcome`), so the rewards can only be given once; it cannot be undone there (409), and a plain Mark completed is refused for such a scenario. The scenario page then shows the recorded report (`#outcome-summary`) and the **Keywords** page lists the campaign's **ledger** (`Store.Ledger`; a keyword is held once; removed with the campaign). **Free recruits**: an outcome can grant recruits that cost no SP (a replacement for a pilot who died); recruiting uses the credit before charging the warchest (`campaign_runs.free_recruits`, `Store.ConsumeFreeRecruit`), and the credit is given back if the recruit fails. Scenario 000 is the first user: kills 1 to 4 pay 150, 400, 650 and 900 SP; no kills means the pilot 'Failed Trial of Position with 0 kills. Demoted to Merchant Caste.', and a pilot killed reads 'Killed in Action.' (two separate rules); either way the pilot is removed and earns one free recruit, which starts with the usual 150 SP. What free recruits are for is said once in the dialog's total line ('N free recruits: replacement pilots can be recruited for free.', also in the recorded report), not in each pilot's card. Scenario 001 (Pyre Light) follows the Aces model: `pilot_sp: 100`, objectives for the plant buildings, the firebase and the waypoint bonuses (A, E), and a mission number input of Jade Falcon mechs crippled or destroyed that adds 200 SP each to the pool (`TestScenario001Outcome`); the tests' default server serves a copy of the campaigns where 001 has no engine (`plainScenario001Root`) so the plain Mark completed path stays covered. Not built yet: scenarios that *require* keywords, and outcomes that choose a branch. see `expr_test.go`, `outcomes_test.go`, `aces_test.go`, `aces_e2e_test.go`.

**Campaign log, branching and availability.** Each started campaign keeps a log of its completed scenarios (`scenario_completions`: playthrough, campaign, scenario slug, time; removed with the campaign by `DeleteRun`; `progress.go`, `Store.Completions/SetScenarioCompleted`). A scenario lists which scenarios it may branch to in its `Outcome.md` front matter, `branches: [scenario_001, ...]` (IDs, lowercased); **omitted, it leads to its `default_next`, or else to the next scenario number** (`resolveBranches`, `Scenario.Branches`), and an explicit empty list ends that path, so scenarios can be arranged into pseudo-branching paths. **Available** scenarios (`Campaign.Available`) are the campaign's first (000), every completed one and every branch of a completed one; the campaign page and the scenario page's breadcrumb menu list only those, so locked scenarios stay hidden (an unstarted campaign shows just 000). Completed cards are **green** with 'Completed ✓', available ones keep the gray card; a **Show all Scenarios** checkbox at the bottom of the campaign page (only while something is locked; `static/scenariolist.js`, remembered in localStorage) reveals the locked ones, dimmed and dashed. Every page of a started campaign except the Manage page has a **Manage Force** chip in the header, left of the account button (`.manage-chip`, `Page.OnManagePage`). While a battle is in progress the Mission log says **In progress** with a yellow LED, and that state is a button (`#mission-log-open`) that opens the operation like View operation. The Deploy section's Manage force button is hidden while a battle is in progress. Once a scenario is completed, a **Next missions** list under its Outcome shows a vertical button link for each scenario it branches to (the heading reads "Next mission" when there is only one) (`Page.NextScenarios`; nothing shows before completion). A scenario page of a started campaign has a **Mission log** bar at the top showing the mission's state with a small glowing **LED** after it (soft red while not completed, green once completed, gray while locked; `.mission-led`), and **the action buttons live at the bottom of the page** (`#mission-actions`, after the Outcome fold: Complete mission for an outcome scenario that has no OpFor to deploy against (one that has moves it into the Deploy dialog's Operation in progress pane, see Battles), otherwise `static/missionlog.js`'s Mark completed / Mark not completed (`POST /api/campaign/scenario-complete`: same-origin, started campaigns only; only an available scenario can be completed, 409 otherwise; un-completing is always allowed and leaves later scenarios alone; a locked scenario's page still opens by link but says it is not available yet). Nothing is completed automatically yet: rewards and outcomes are still entered by hand. `TestScenarioBranches`, `TestCampaignLog`.

**Provided forces (scenario-unique available mechs).** A scenario's `Setup.md` front matter can list `provided_units` (MekBay unit IDs) to replace the player's hangar with a fixed pool of mechs for that scenario, for story reasons (`provided.go`, `Scenario.ProvidedUnits`, `Scenario.provides()`). Scenario 000, the Trial of Position, offers `BMBlackHawk_Prime` (Nova Prime), `BMRyoken_Prime` (Stormcrow Prime), `BMShadowCat_Prime` (Shadow Cat Prime), `BMPouncer_Prime` (Pouncer Prime) and `BMGrendel_Prime` (shown by its Clan name, Mongrel Prime): lighter, evenly matched machines on purpose, because the trial is back-to-back 1v1s and a cadet should expect one kill, rarely two and very rarely three (the Mad Dog and Timber Wolf Primes made it too easy). Such a force is **ephemeral**: `providedForce` builds a `HangarForce` of new, uncrewed units (IDs `provided-<lowercased unit ID>`) so the Deploy popup (`hangarJSON`, and `Page.DeployJSON`, which embeds it with no MekBay read), the old single-player deploy and `POST /api/deploy/plan` (all through `Server.scenarioHangar`) work on it unchanged: named pilots can be assigned, the scenario's BV limit and the player count apply, and each mech can be taken once. It is never read from or written to MekBay, never cached as the hangar and never changes it; the hangar JSON carries `provided: true`, which shows the popup's note (`#deploy-provided`). A scenario with no `provided_units` uses the hangar as before, and one with provided units has no **Manage force** button in its Deploy section (there is no hangar to manage for it). **Scenario rules**: front matter `unit_limit: N` (the most mechs the players may take in all, shared by every player, like the BV limit) and `pilots_required: true` (every mech taken needs a named pilot) apply to any scenario; Scenario 000 sets both (two mechs, a pilot on each) and no `bv_limit`. They are enforced by `Scenario.rulesProblem` in `POST /api/deploy/plan` and the old single-player deploy, and in the popup (`data-unit-limit`, `data-pilots-required`): the meter counts mechs against the limit instead of saying '(no limit)', the mechs not yet taken are disabled once the limit is reached (counting one mech kept for every other player, since each player needs at least one: with a limit of 2 and two players each takes one, and a player holding too many after the count changes is told to leave one and can't go on), a `#deploy-rules` line states the rules and what is still missing, and Next/Deploy wait until every mech taken has a pilot. `TestScenarioRules`, `TestScenario000EnforcesItsRules`. `TestProvidedForce`, `TestScenario000ProvidesItsOwnMechs` (which also checks every scenario's provided units are catalog mechs), `TestProvidedScenarioDeploy`.

**The Deploy wizard (several players).** A campaign's `min_players` and `max_players` (Refusal War: 1 to 2; at most 4, `playerRange`) say how many players a sortie can be deployed with. The force's mechs (its MekBay hangar) and named pilots are **one shared pool** that the players divide, so the Deploy popup (`static/mekbay.js`) is a wizard: with one player (or a campaign that allows only one) it is a single step as before; with a range, the first step has a **Players** picker (a segmented control from the minimum to the maximum, starting at the minimum), and choosing more than one makes it a wizard of **one step per player plus a review**, with a **progress bar and "Step n of m" at the bottom**, Back and Next, and each step titled "Player k of N". A player takes mechs by ticking them and assigns pilots to those mechs (a pilot slot only works on a mech the player has taken); **a later step is offered only what the others left**: a mech another player took is not listed, and a pilot another player assigned is not in the tray (going back to an earlier player hides what a later one took; to take it back, untake it there). Each player needs at least one mech to go on, the scenario's BV limit is **shared by all the players together** (the step shows this player's figure and the force total), and choosing fewer players gives the dropped players' mechs back. Player 1 starts with the mechs already in the hangar's Deployed group, with the named pilots already in them. The last step reviews every player's mechs, pilots and BV, and its **Start battle** button starts the battle (see Battles below). The dry-run `POST /api/deploy/plan` (not called by the page today; kept as a read-only check of a plan, and what the plan tests drive) (`plan.go`: `players`, then `p<i>_units` and `p<i>_assign_unit` / `p<i>_assign_pilot` for each player) checks a plan and describes it back without touching MekBay; `checkPlan` is the check, shared with Start battle: the player count against the campaign's range, `planProblem`/`deployProblem` over all the players' mechs together, `parseCrewPairs` for each player's pilots, no pilot or mech twice, an assignment only on a mech that player takes, the scenario's own rules. `TestPlayerRange`, `TestPlanProblem`, `TestDeployPlanEndpoint`; the wizard was driven with jsdom (`deploy_wizard_check.js`: the picker, a step per player, what is left over, the review, the progress bar, the request) and the dialog in headless Edge.

**Battles: Start battle, the operation and the Operation in progress view** (`battle.go`, `battlestart.go`, `sorties`-free: a battle is a row of `mekbay_operations`). **Start battle** (`POST /api/battle/start`, the plan's fields plus `reset_opfor`) re-checks the plan, then builds in MekBay, all owned by the seed's one account: the **OpFor** force (from the scenario's `.mul` files; an earlier start's OpFor, with its recorded damage, is kept unless reset), a **force for each player** (their mechs copied out of the hangar copy by `subsetForce`, keeping each unit's own ID, damage, ammunition and crew, with the pilots they were given applied; or built from drafts when the scenario provides its own mechs, which are not in MekBay), and **one operation** (`saveOperation`, confirmed with `getOperation` since MekBay doesn't acknowledge it) named `<Campaign> - Scenario NNN` with every player's force on the friendly side and the OpFor on the enemy side. One force per player, not one force of several groups, because MekBay saves a force as a whole document so two people editing different forces can't overwrite each other. The scenario is recorded as started in `mekbay_operations` (operation and OpFor IDs), and the answer is `{url, operation}`, where `url` is the **table's one link** (`mekbay-<id>.<host>/?operation=<id>`, label `table`, see The MekBay proxy). The work runs detached from the request (`context.WithoutCancel`) so a browser that goes away doesn't leave it half-done. Starting again (only through Abort first, since the page then offers View operation) updates the same operation and keeps the OpFor unless reset. **Why an operation and not a lobby:** a multiplayer lobby was built and verified live first and dropped. Lobbies exist only while someone is connected, an account can be in only one lobby (a start that stopped halfway left accounts stuck in it: "You are already in a lobby"), membership belongs to a live connection (a second connection for an account with one open doesn't resume it), and alignment is per viewer (each participant sees itself as friendly and everyone else as enemy until it says otherwise, and `setLobbyAlignment` changes only the caller's own view). An operation is a saved document that needs no connection kept open and can be reopened later. **Devices stay in step without a lobby:** MekBay pushes every save of a force to every session that has it loaded (`subscribeToForceUpdates`, then an `updatedForce` message with the whole force; verified live with two connections, and by hand with a repair made in Edge appearing in Firefox), so a table sharing the one link sees each other's edits as they are saved. **Operation in progress** is the Deploy dialog's last pane (`static/mekbay.js`: `enterOperation`, `renderOperation`, `refreshStatus`), shown straight after Start battle and, for a battle already going, when the dialog opens (`data-in-progress`): the table's link (full URL as selectable text, a Copy button, an anchor that is not draggable so a drag selects the text, and a click that leaves text selected doesn't open it), then how the battle stands: each player's force from MekBay (the OpFor's is neither read nor shown) with its mechs as the same rows as the Hangar's, each with its live status pills (armor or structure damage, crippled, destroyed, ammo expended), a mech crewed by a named pilot showing that pilot's card to the right as the pilot slots do (other crew keeps the plain Gunnery/Piloting chip), an "Updated <time>" stamp and a **Refresh** button that is the circle-arrow icon (spinning while it reads), re-read every 10 seconds while the dialog is open and the tab visible (`GET /api/battle/status`: reads the operation and each of its players' forces anonymously with `ReadBattle`, answers `{url, operation, forces: [{name, alignment, units}], updatedAt}` with the units described by `hangarViews`; a failed read keeps what is showing and says so, a 404 means the battle ended elsewhere and reloads). The pane holds the mission's actions (`#op-actions`): **Complete mission** (the `#outcome-open` button, moved off the page bottom, for a scenario with an outcome engine) and, under a collapsed **More options**, a red **Abort mission** (the same large outline button in red; after a danger confirmation `POST /api/battle/abort` forgets the operation, so the scenario goes back to not started with no rewards; nothing is deleted in MekBay). While a battle is in progress the scenario page's section reads **Operation in progress** and its button **View operation** (it opens the dialog on this pane) instead of **Deploy force**, and there is no separate Open in MekBay button. The link row also has a **QR icon button** before Copy that opens a dismissable dialog with the link's QR code (`qrSvg`; vendored MIT library `static/qrcode.js`, licence in `static/qrcode-LICENSE.txt`; Escape on it doesn't close the Deploy dialog under it). **The MekBay proxy (`mekbay-<link id>.<site host>`; `mekbayproxy.go`, `mekbaylinks.go`).** MekBay keeps a visitor's identity (a UUID) in the browser's IndexedDB and an account owns its forces, so a force owned by an account nobody holds (the site's OpFor, a player's derived account) would be read-only in a stock browser (a lobby participant's forces reach other browsers with `owned` false). The site therefore serves MekBay's own web app from host names of its own, each acting as the account its link names, with everything in this one Go program (no fork, no Node or Angular build; MekBay's server is closed source, `../mekbay` is only its front end). `NewHandler` sends every request whose host's first label is `mekbay` (the localhost sandbox) or starts with `mekbay-` (`parseMekBayHost`/`isMekBayHost`) to the proxy. **The identity is the host name.** A **link** is a 160-bit random id (32 characters of a-z and 2-7, `newMekBayLinkID`) in the first label: `https://mekbay-<id>.battletech.zech.io/?instance=<force>`, locally `http://mekbay-<id>.localhost:8080/`. Each link is its own browser origin, so two links open in two tabs of one browser are two accounts with separate cookies, IndexedDB and `BroadcastChannel` (MekBay shares those between tabs of one origin), closing a tab and reopening, bookmarking or iMessaging the same address gives the same account, and the site's own cookies never reach these hosts while MekBay's JavaScript is cross-origin to the site's APIs. Links live in the table `mekbay_links` (`id`, `playthrough_id`, `campaign`, `label`, `account`, `ttl_seconds`, `expires_at`; one per playthrough, campaign and label, and since a seed has one account the site uses the one label `table`, `tableLabel`, for the Manage page's editable hangar and for the battle's operation): the account is stored **plainly** beside the link (the seed is never stored, and the MekBay account can't be recomputed from what is, so the link has to carry it; the link id is the credential anyway, so encrypting the account would add almost nothing, and links now survive restarts with no key to manage; a table from when accounts were sealed under `MEKBAY_LINK_KEY` is dropped at startup and its links made again on demand, `TestMekBayLinksSurviveARestart`), `Store.EnsureMekBayLink` returns the same id every time for a label (so the link is stable and bookmarkable; a changed account is updated under the same id; an expired link is replaced by a new id), `Store.MekBayLink` looks one up and **slides the expiry forward while the link is used** (14 days, `mekbayLinkTTL`), `RevokeMekBayLink` ends one at once, and deleting a campaign (`DeleteRun`) deletes its links. Links are never single-use (chat apps fetch a link to build a preview). `Server.mekbayLink(r, playthroughID, campaign, label, account, query)` builds the URL from the request's host (`?instance=<force>` loads a force and `?operation=<id>` an operation). **Web app:** MekBay's prebuilt static files are fetched from mekbay.com on demand, cached (an hour; the page a minute; the last copy is served if MekBay is unreachable) and served unchanged except for two things: the one JavaScript string naming its WebSocket (`` `wss://mekbay.com/ws` ``, found in whichever chunk holds it, since file names are hashed) becomes this host's `/ws`, and `ngsw-worker.js` and `safety-worker.js` are stubs that unregister themselves and empty the caches (a rewritten file would fail the real worker's hash checks and it would otherwise control the page); `/ngsw.json` is a 404. The app is always MekBay's current build, so it stays in step with its server's `PROTOCOL_VERSION`. Pages (any path that isn't a file) are served only for a valid link (403 otherwise); MekBay's own public files are served to any host. **Every response carries `Referrer-Policy: no-referrer`** (plus `X-Robots-Tag: noindex` and `nosniff`), so following a link out of MekBay (Sarna, the MUL) never reveals the host name, which is the credential. **Relay (`/ws`):** accepts the browser's WebSocket (the default same-origin check stops another page from using a link's host through a visitor's browser), opens one to `wss://mekbay.com/ws` with `Origin: https://mekbay.com` and passes messages through, replacing the top-level `"uuid"` of every text message the browser sends with the link's account (`swapUUID`: nested values are never parsed; the browser still believes it is a random visitor). A link host that is not valid (unknown, malformed, expired or revoked) gets no pages and no relay (401), so the deployed site is never an open door to MekBay; **the one exception is a developer's machine** (`sandboxAllowed`): the bare `mekbay.localhost` host, reached from a loopback address with no forwarding header (the Host header alone proves nothing, a remote client picks its own), acts as one shared **sandbox** account (`sandboxAccount`, a fixed derived ID), so `mekbay.localhost:8080` works when opened directly. `Check` says whether the live MekBay still has the WebSocket string to replace; `main` runs it once at startup (`site.CheckMekBay`) and logs a warning if it fails, so a MekBay release that breaks the proxy shows in the server log (`TestCheckMekBayLive`). **Production setup (DigitalOcean App Platform; DNS for zech.io is already on DigitalOcean):** add the wildcard domain `*.battletech.zech.io` to the app (Networking, Domains; "We manage your domain"; the wildcard certificate needs TXT verification records added to the zone; the wildcard also keeps each link's host name out of Certificate Transparency logs); a wildcard covers one label, which is why the host is `mekbay-<id>.battletech.zech.io` and not `<id>.mekbay.battletech.zech.io`. The wildcard also sends every other subdomain of the site to the app (they just serve the main site). **Known downsides:** MekBay's own Share button builds links from `window.location.origin`, so a link shared from inside MekBay carries the host (the credential; revoke or let it expire, and tell players to share links from the site); host names are more visible than query strings (DNS lookups, TLS server names, browser history). Verified (2026-11) against the real mekbay.com: `TestMekBayProxyLive` (runs only with `MEKBAY_LIVE_PROXY=1`, throwaway random accounts) shows a browser on the owner's link, though it registers as a random UUID, reads its force with `ownedOnly` and `owned: true` and saves an edit that reaches MekBay, while a browser on another link is refused as not_owner; and in headless Edge, two links in two tabs of one browser each opened their own force with the edit controls, a third tab (alpha's link viewing bravo's force) was read-only, and a closed tab reopened at the same address was still the same account. `TestMekBayHostParsing`, `TestMekBayProxyServesAndRewrites`, `TestMekBayProxyRefusesBadLinks`, `TestMekBayProxyCachesAndSurvivesAnOutage`, `TestMekBayRelaySwapsTheIdentity`, `TestMekBayRelayTwoLinksTwoAccounts`, `TestMekBayRelaySandbox`, `TestMekBayCheck`, `TestSwapUUID`, `TestMekBayLinkIDs`, `TestMekBayLinkStore`, `TestMekBayLinkBuilder` run in CI against a fake MekBay with a real WebSocket. **Users of the links:** a battle's table link (see Battles); the Manage page no longer links the hangar copy. `TestDeletingTheCampaignRevokesItsLinks`. **Not built yet:** answering unknown subdomains with a 404.

Findings from probing MekBay (2026-11): its server is closed source and only reachable over `wss://mekbay.com/ws`, so everything here is unofficial and may break. An anonymous client (random `sessionId` and `uuid`, `register` with `version: 2`, then `getForce {instanceId}`) can read any force by ID; writes (`saveForce`) need the owner's UID, which is why the site writes only to forces owned by accounts it derives from the seed (the hangar copy, the OpFor, each player). Reading needs no account.

- **Unit condition pills (Hangar rows).** MekBay stores no "crippled" flag (only `destroyed`, the raw `locations`/`crits`, and a torso-check result in `state.ruleChecks`; crippled is computed in its client, `src/app/models/rules/mek-rules.ts`), so `condition.go` recomputes it the way MekBay does (forced withdrawal on, its default): two engine crits; two destroyed limbs, one a leg; two destroyed torsos; or one destroyed torso when the engine isn't Fusion/Compact or the stored torso check failed. A location is destroyed when its internal loss reaches its structure, taken from `structureByTons` (standard bipeds; an unknown tonnage never counts as crippled), and the catalog's `engine` is in `units_index.json` for that. `conditionOf` shows the worst state only: destroyed > crippled > internal structure damage > armor damage, each its own pill colour on the mech row (`mechrow.js`, `.mr-chip.cond-*`; the tooltip says why), plus a separate blue "Ammo expended" pill when any ammo bin has been used (rearming is a different need from repair). Hangar views carry `condition`, `conditionNote`, `ammoExpended`. `TestConditionsOfTheLiveHangar` replays the raw values of a real four-mech hangar.
- **Status pill tooltips.** The condition and ammo pills on a mech row don't use the browser's `title`: hovering or keyboard-focusing one shows the same floating card as the unit icons (`.unit-tip.pill-tip`, built by `attachTip` in `mechrow.js`, one element per page. It is a `popover="manual"` shown with `showPopover()` and **a child of the open dialog** when the element it belongs to is in one (else of `<body>`): the popover renders in the top layer, above the dialog and **not clipped by a dialog's cut-corner `clip-path`** (which clips everything inside a dialog, including a fixed-position child), while living inside the dialog keeps it **hoverable**, because everything outside a modal dialog is inert (a card on `<body>` showed fine but `elementFromPoint` over it returned the list behind it, so the pointer could never reach it); a browser without popovers just keeps it inside the dialog. A delayed show is dropped if the element has left the page (`isConnected`), and `MechRow.hideTip()` closes a card before the popup re-renders its pilots, which stops a card being placed at (0, 0) when a live hangar read replaces the chips during the hover delay): the condition in its colour with the reason as a sentence (location codes spelled out, `conditionText`), and for the ammo pill the breakdown and the rearm cost.
- **Purchase New Units (Hangar section).** A right-aligned "Purchase New Units" button under the unit rows (like Recruit New Pilot) opens `#purchase-dialog` (`static/purchase.js`): a search box over MekBay's unit list (`GET /api/units/search?q=&campaign=&all=1`, `search.go`; debounced, a reply for older text is ignored, Enter searches rather than buys), whose results are the same mech rows as the hangar (without the pilot chip) with the unit-page link, and **clicking a row adds it to "Your cart"** (no Stage button; `MechRow`'s `onPick`, also Enter or Space) **and clicking it again takes it out**: the cart holds one of each unit (`stage` refuses a duplicate), a result in the cart is tinted like a unit picked in the deploy popup and badged `In cart`, and the cart sits below the results (which keep a fixed height so rows don't jump), each cart row with a small × to remove it; the search box is a themed field with a magnifier and a clear button (its placeholder is the only instruction; the results area stays empty until something is typed), and the faction checkbox the site's square yellow-ticked `.themed-check`; MekBay offers no embeddable search or way to hand a chosen unit back (no postMessage or callback), but its data is public, so the site searches its own embedded catalog the way MekBay does (typed words matched, punctuation ignored, against chassis and model; mechs only; best matches first: every word starting a word of the name, then by name; at most 40 shown with the total). A campaign names a faction and an era in `Intro.md` (`availability_faction: Clan Wolf`, `availability_era: Clan Invasion` for Refusal War), and the search then lists only the units MekBay says that faction fields in that era (`availability.json`, built by `gen_units.go` from MekBay's `factions.json` and `eras.json`, vendored in `data/`, joined by Master Unit List ID), with a checkbox in the popup, ticked by default, to search everything (`all=1`); a campaign that names neither has no filter. Re-run `go generate ./internal/site` after refreshing `data/units.json`, `factions.json` or `eras.json`, or when a campaign names a new faction or era. the same "Cost N SP. Warchest A → B SP." line as repair, and a Buy button. BV is SP: each unit costs its base BV. Buy posts `POST /api/hangar/purchase` (`purchaseUnits` in `purchase.go`, repeated `unit` fields; needs a hangar the site owns; `purchaseCost` refuses anything that isn't a catalog mech), which charges the warchest first (`SpendWarchest`, refunded if MekBay fails) and adds each unit, undamaged with a 4/5 pilot, to the force's Hangar group in MekBay (`MekBayClient.PurchaseUnits`, `addUnitsToForce`). `TestPurchaseEndpoint`, `TestAddUnitsToForce`, `TestPurchaseCost`.
- **Manage force from a sortie.** Each scenario page's Deploy section has a **Manage force** button (`#manage-link`) to `/<campaign>/manage/?back=<scenario slug>`; the Manage page then shows 'Back to Sortie NNN: Title' to that scenario instead of 'Back to the campaign'. Only a real scenario of the campaign is honoured (it is looked up with `Campaign.Scenario`, never echoed as a URL), so `?back=` can't be used for an open redirect. `TestManageBackLinkReturnsToTheSortie`.
- **Selling units (Hangar rows).** Every mech row has a **Sell** button after Rearm and Repair (`hangarlist.js`, `sell.go`). A unit sells for half its base BV in SP; a unit that is not fully repaired and rearmed (`unitPristine`: no recorded damage, not destroyed, no spent ammunition) gets half of that again, rounding down, so about BV/4 (`sellValue`). A truly destroyed mech can't be repaired (and now can't be rearmed either: `POST /api/hangar/service` answers 409), so selling is its only action, always at the reduced price. The confirmation (danger style) lists the price breakdown as `Confirm` items (base BV at 100%, the 50% price for a fully repaired and rearmed unit, the 25% price and why when it is worn, what it sells for) and shows the warchest change; `POST /api/hangar/sell` (`sellUnit`, needs a hangar the site owns) works the price out itself from the unit's state (the page's `sellValue`/`sellFull` are only for display), removes the unit and its crew from the site's copy with `MekBayClient.SellUnit` (`removeUnitFromForce`) and **then** pays the warchest (`RefundWarchest`), so a failure in MekBay never pays for a unit the player still has. `TestSellValue`, `TestRemoveUnitFromForce`, `TestSellUnitEndpoint`.
- **Reconfiguring omnimechs (Hangar rows).** An omnimech (`omni` in `units_index.json`, `Unit.Omni`) has a **Reconfigure** button (`swap.go`, `#swap-dialog` in `manage.html`, `hangarlist.js`) whose variant dropdown starts on the current variant (Reconfigure disabled, since that would change nothing) and lists the other variants of the same chassis with their BV and price, coloured like a stock (green for more BV, red for less); choosing one shows the unit's full mech row, a flow arrow with the BV change and price, the new variant's full row (`swapOptions` carries what a row needs) and a brief cost breakdown (50% of tonnage, 50% of BV gained) (`swapOptions`, sent as `swapOptions` in the hangar views; other units have none and no button). **Like Purchase, the dialog offers only the variants the campaign's faction fields in its era**: each option carries `available` (`markSwapAvailability`, applied by `forceData` with the campaign, from the same `availability.json` list as the purchase search), and a ticked-by-default `#swap-available` box ('Only variants Clan Wolf fields in the Clan Invasion era', only when the campaign names a faction and era) hides the others; unticking it lists every variant, a chosen variant that is no longer listed falls back to the current one, and the box is ticked again each time the dialog opens. Like Purchase, the server doesn't refuse an unavailable variant: the box is the player's choice (`TestSwapOptionsFollowAvailability`, `service_check.js`). The SP Activity Cost Table prices a reconfiguration at half the tonnage, but BV is SP here, so that alone would let a cheap starting variant be swapped up almost free (beating the starting BV cap) and then sold at a profit. The price is **half the tonnage (rounded up) plus half the BV gained (rounded down)**, and swapping to a lower-BV variant costs only the half tonnage with no refund (`swapPrice`): cheaper than selling and buying the other variant (so being an omni matters), while swapping up and selling a clean unit always loses the half tonnage. The unit must be fully repaired and rearmed (`unitPristine`; 409 otherwise) because the old variant's crit slots and ammo don't map onto the new one; only omnimechs can swap (400), only to a variant offered for them. Crews are a per-scenario matter, so the swap carries no crew over: `swapUnitState` replaces the unit's design and gives it a fresh state. `POST /api/hangar/swap` (`swapUnit`, needs a hangar the site owns) charges the warchest first and refunds it if MekBay fails, like repairs. `TestSwapPriceAndOptions`, `TestSwapUnitState`, `TestSwapUnitEndpoint`. Re-run `go generate ./internal/site` after refreshing `data/units.json` (the index carries the omni flag).
- **Truly destroyed, repair and rearm (Hangar rows).** Per Hot Spots: Draconis Reach (the SP Activity Cost Table and "Destroyed vs. Truly Destroyed", printed p. 33, physical page 35), a mech whose center torso internal structure is eliminated is **truly destroyed** (`CondTruly`, shown as a dark red "Truly destroyed" pill, above plain destroyed): it can't be repaired or salvaged. Every other mech row has **Rearm** and **Repair** buttons at its right (`mechrow.js` `actions`, wired in `hangarlist.js`, costs from the server in `service.go`). Repair costs tonnage x 0.5 (armor only), x 2 (structure and/or crits), x 3 (crippled) or x 5 (destroyed), x 1.5 rounded up for Clan or Mixed tech, and a repair at one level also covers the levels before it in the list. The repair dialog (`#repair-dialog`) lists only the repairs that would fix something on that unit (`repairOptions`: armor if any armor is lost; structure if a surviving location has lost internal structure or has a critical hit, engine hits excluded; crippled for a crippled or destroyed unit; destroyed for a destroyed one), none greyed out, the highest selected, with the price following the choice; any one can be chosen on its own, so a crippled unit can have just its armor repaired. What each level clears (`serviceUnitState`/`repairState`): armor = lost armor everywhere; structure = also internal structure in locations that aren't destroyed and critical hits there (not the engine's, which cripple, and not a destroyed location's); crippled = everything (locations, crits, torso check); destroyed = also the destroyed flag. Rearm is 10 SP per ton, counting each ammo bin with any consumed as one ton (`HangarUnit.AmmoBins`) and is confirmed with `Confirm.ask`, which lists the breakdown first (`items`: one row per ammo type, e.g. "LRM 5 Ammo: 1 ton · 5 of 24 shots used", from `ammoBreakdown`: MekBay records only the shots used per bin, so the capacity per ton comes from the unit's `ammo` entries in `units_index.json`, shots divided by slots, and a bin the catalog doesn't list still counts as a ton with an unknown capacity), whose optional `detail` line (bold yellow, red with `detailShort`) carries the same "Cost N SP. Warchest A → B SP." text as the repair dialog. Both go through `POST /api/hangar/service` (`serviceUnit`): needs a hangar the site owns (it edits the force in MekBay with `MekBayClient.ServiceUnit`, `serviceUnitState` in `service.go`, `saveForce` like a deploy), the server works out the condition and the price itself (a repair names the level chosen and is refused with 409 if it isn't one of the unit's current options), charges the warchest atomically first (`Store.SpendWarchest`, 409 if it can't cover it) and refunds it if MekBay fails (`RefundWarchest`). Without an owned hangar (a run from before the site made copies) the buttons are disabled with a tooltip and the endpoints answer 409. `TestServiceUnitEndpoint`, `TestServiceUnitState`, `TestRepairCostsFollowTheSPActivityCostTable`.
- **Damage:** a unit's `state.locations[loc].armor` / `.internal` are points *lost* (absent when undamaged), `state.crits` has critical hits and ammo `consumed`, `state.crew` has pilot hits. Join units to `data/units.json` by the unit's `unit` field (equals `name` there) for costs and totals.
- **Alignment is not stored in a force.** "Hostile" is only the `enemy:` prefix in the URL (`?instance=<mine>,enemy:<opfor>`) or an Operation (`?operation=<id>`, a saved list of whole forces with alignments; anonymous reads work). The OpFor is a separate saved force with its own instance ID, so setup should eventually accept the multi-force link and store the friendly and `enemy:` instance IDs separately, not a single `instance`.
- **MekBay cannot load part of a force.** Chosen design for deployment: the campaign's hangar force holds every mech, and players drag the units going on a sortie into a group named "Deployed" (case-insensitive); every other group is reserve. The site treats that group as the sortie roster. "Start sortie" records the roster and a damage/ammo/crew snapshot in our own database, "end sortie" re-reads the force and diffs against it, and a change to a reserve unit is flagged rather than billed. Players can regroup later without rewriting history because the snapshot is ours. Repairs are billed from the diff; clearing the damage in MekBay is up to the player unless modify mode is on.
- **Sortie hotlinks** could be built as `https://mekbay.com/?instance=<campaign>,enemy:<sortie opfor>` once each sortie's OpFor force exists (unknown: whether a non-owner can mark damage on a force they don't own; the scenario operation above already gives players a one-click link).

## Scenario file conventions

Follow the layout in `Scenario_000/Setup.md` and `Scenario_000/Outcome.md` when adding scenarios:

- Both files start with YAML front matter holding the machine-readable fields; the Markdown body below it is the human-readable write-up. The folder name lowercased (`Scenario_000` -> `scenario_000`) is the scenario `id`, and all cross-references (`next`, branch targets) use IDs, never titles.
  - `Setup.md` front matter: `id`, `title`, `planet` (the planet the scenario takes place on, e.g. `Strana Mechty` for Scenario 000; every scenario has one), `map`, `forces` (maps `opfor1`, `opfor2`... to the `.mul` files beside it), `provided_units` (optional list of MekBay unit IDs the players pick from instead of their hangar, see Provided forces), `readout` (optional list of `Label: value` lines, kept in order, drawn as a translucent technical readout over the left of the first image, and below it on narrow pages; used for planet data), and `images` (list of paths in the folder's `images/`, e.g. `images/strana_mechty.png`; each is shown as a wide fluff-image banner under the scenario title, cropped to the top, so put the subject in the upper part of the picture; empty until used).
  - `Outcome.md` front matter: `id`, `default_next`, `branches` (optional list of scenario IDs this scenario may lead to; omitted, it leads to `default_next` or the next number), and the outcome engine's `pilot_sp`, `objectives`, `inputs` and `outcomes` (see The outcome engine). Scenario 000 has none: it bootstraps the campaign's starting parameters (starting SP and pilot) rather than granting keywords. `when` is a plain condition over `kills` and `pilot_dead` for now (`kills >= 1`, `pilot_dead or kills == 0`); keep it simple and settle the syntax when a second scenario needs more. `grants` and any required keywords are IDs from `campaigns/RefusalWar/Keywords.md`; add new keywords there before using them.
- Deployment: every unit eventually gets an initial hex position (or is marked off-map with custom rules). Play uses standard two-mapsheet neoprene battlemats with labeled hexes. Hexes are written as four digits, `XXYY` (column then row, e.g. `2113`), as in `Scenario_001`; any other position format is still undecided, so leave deployment positions as `TBD` and don't invent coordinates or a schema until the user supplies them.
- `Setup.md`: `# Scenario NNN: <Title>`, a blockquote of fluff text (if it isn't written yet, leave the placeholder rather than inventing lore). Fluff is a mission briefing: an in-world commander speaking directly to the player in second person, formal and terse, in the style of the MechWarrior 2 briefings (see `Scenario_000/Setup.md`). Aim for less is more: show, don't tell, with a slightly alien yet familiar tone (Hidetaka Miyazaki-style lore, Dune), keep it to a few lines, and don't restate the rules that the sections below cover, then `## Overview`, `## Map`, `## Forces` (each force group, `### Player Forces` and `### OpFor N`, has a `**Deployment:**` line; the OpFor groups are bullet lists written as `Variant (gunnery/piloting) Role: Pilot, hex XXYY`, e.g. `Nova Prime (3/4) Skirmisher: Star Commander Alrek, hex 2113` (the role is the unit's Master Unit List role, capitalized as there: Scout, Striker, Skirmisher, Brawler, Missile Boat, Sniper, Juggernaut, Ambusher; look it up in the `role` field of `data/units.json`; the hex is left off for reserves, and `: Pilot, hex XXYY` entirely when neither is set yet, as in Scenario 000), with the mech name hyperlinked to MekBay as `https://mekbay.com/?gs=cbt&shareUnit=BM<IS-name>_<Variant>&tab=General`; the unit ID is not always obvious: the chassis name has no spaces, the variant follows an underscore, and a chassis with no named variant takes no suffix. Some chassis use the Inner Sphere name (Mist Lynx is `BMKoshi_E`, Kit Fox is `BMUller_J`) while others don't (`BMMadCat_H` for Timber Wolf H, `BMLoki_Prime`, `BMGrizzly`). Ask the user for the working URL rather than guessing a new one; **hovering such a link shows a unit card**: `renderMarkdown` gives every link to a catalog unit's MekBay page (its `shareUnit` ID) the class `unit-link` and the unit's card as JSON in `data-unit` (`annotateUnitLinks`, `unitlinks.go`), and `static/unitlinks.js` shows it at once in the shared floating card (`MechRow.attachTip`); the link still opens MekBay, and a link to an ID the catalog doesn't know stays plain and is listed in `Campaign.Problems` (`unknownUnitLinks`). **The unit card is one component everywhere** (`static/unitcard.js`, `UnitCard.build(card, {status, pilot})`, data from `catalogCard` in `unitlinks.go`): a scenario's unit links, the campaign overview's unit icons (`forcesummary.js`) and **the Manage page's Hangar rows** (`hangarlist.js`: hovering or focusing a row shows the card under it, right-aligned with the row (`attachTip`'s `align: 'right'`) so the mechs on the left stay in view, the row keeps its yellow border while it is open (`.mech-row.tip-open`), and coming back off a status pill, which has its own card, brings the row's card back); a hangar unit's view carries `card` and `UnitCard.forUnit` adds its condition pills under the name, so pages load `mechrow.js`, then `unitcard.js`, then the script using it. It shows the icon, Clan name and model, and **the BV at the top right in bold yellow** ('BV: 2,663', or at the pilot's skills when the `(g/p)` written after a link isn't 4/5: 'BV (3/4): 3,515', `adjustedBV`), then two columns of eight rows each (the user wants them level): what the unit is (role, class and OmniMech, tonnage, tech, engine, armor type, structure type, base BV) and how it is built (armor and structure points, heat generated firing everything, dissipation, Walk/Run/Jump, Firepower, Max range and Effective range in hexes), values in bold, and under the right column **MekBay's weapon type bar**: counts of ballistic, energy and missile weapons, each an icon on its colour (`static/weapon-*.svg`, MekBay's GPL-3.0 icons, see `static/weapon-icons-NOTICE.txt`; zero dimmed). The figures are in `units_index.json` for mechs (`gen_units.go`: `armor`, `armorType`, `internal`, `structureType`, `heat`, `dissipation`, `walk`, `run`, `jump`, and `firepower`, `maxRange`, `range`, `ballistic`, `energy`, `missile`, worked out by `weaponStats` the way MekBay's stat bars do, `unit-search-index.service.ts` and `unit-range.util.ts` in `../mekbay`: Firepower is every weapon fired at once without physical attacks, Max range the longest weapon range, Effective range MekBay's damage-weighted range, how far most of the damage reaches). Only an `interactive` floating card (the pilot card) takes the pointer and has the invisible bridge back to its element; on any other the bridge lay over the bottom of the link and closed the card. `TestUnitLinksCarryTheirCards`, `TestScenarioPagesHaveUnitCards`, `TestFirepowerAndRange`, `TestWeaponCountsAndTheOverviewCard`, and `roster_check.js` in jsdom) `## Special Rules`, and, when the scenario uses waypoints, `## Waypoints` last. Waypoints are a core mechanic, like the back-of-book waypoints in BattleTech: Aces (Scouring Sands): you only read one when the game calls for it. Each is a `### Waypoint X` heading (any `### ` name works) with its rules text beneath it; text between `## Waypoints` and the first `### ` is dropped. Where they are placed, and when they are revealed, belongs in `## Map` and `## Special Rules`. The site pulls the section out of `Setup.md` and shows each waypoint redacted (its text blacked out line by line, with a Reveal button that wipes the bars away; without JavaScript they are simply readable), inside the collapsed Waypoints block.
- `Outcome.md`: `# Scenario NNN: <Title> - Outcome` with `## Victory & Rewards`. Rewards are in SP (the campaign's pilot-advancement points). The kills-to-SP table is specific to Scenario 000's graduation mission; don't assume later scenarios use it.
- Campaign rules visible so far: pilots are named and persistent; a pilot who dies or fails to score a kill in the graduation mission is permanently removed and replaced by a new named pilot with 0 SP for Sortie 001; Clan honor rules such as zellbrigen apply and violations have mechanical consequences.

## Force files (.mul)

Each scenario folder also holds `OpFor1.mul` and `OpFor2.mul`: MegaMek's XML force format (MekBay exports and imports it), one `<entity>` per mech with its `<pilot>` skills and `<Game id>`. Prefer a real MekBay export over hand-writing. When hand-writing, `chassis` and `model` must match MegaMek's database. A mech with two names uses `chassis="<Inner Sphere name> (<Clan name>)"`, e.g. `Koshi (Mist Lynx)` or `Mad Cat (Timber Wolf)`; a single-name mech such as the Grizzly has a plain chassis and an empty `model`. Deployment attributes, `externalId` and `quirks` can be omitted.

## Working notes

- Mech names and variants are canon BattleTech Clan designs (e.g. Mist Lynx, Timber Wolf, Shadow Cat, Loki); keep to real variant names and Clan terminology (touman, zellbrigen, Trial, etc.).
- For mech data, the authoritative sources are the Master Unit List (`https://masterunitlist.battletech.com/units/<chassis>-<variant>`, e.g. `shadow-cat-a`) and MekBay, not Sarna. The MUL site is behind a Cloudflare bot challenge and returns 403 to automated fetches.
- `data/units.json` is a vendored copy of MekBay's unit catalog, downloaded from `https://db.mekbay.com/units.json` on 2026-11-16 (with `factions.json` and `eras.json` from the same host) (~27 MB; MekBay builds it from MegaMek's `mm-data`). To refresh it, re-download that URL over the file (e.g. `curl --compressed -o data/units.json https://db.mekbay.com/units.json`). Search it with Grep/Python rather than reading it whole. Each entry's `chassis` and `model` are exactly what `.mul` files need, and its `name` field is the `shareUnit` ID for MekBay links (e.g. `BMMadCat_H`). MekBay's source is at `../mekbay`.
- Maps referenced are official BattleTech battlemats (e.g. "Circles of Equals").
