# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A repo of custom tabletop BattleTech campaigns, one per folder under `campaigns/`, mostly Markdown. A Go web server turns the campaigns into a website; there is no lint or test tooling. The only campaign so far is `RefusalWar/` ("Refusal War", inspired by the MechWarrior 2 video game, a conflict between Clan Wolf and Clan Jade Falcon); expect more, so keep campaign-specific rules inside the campaign's folder and put only genuinely shared things (like `data/units.json`) at the top level.

## Structure

Every campaign folder (shown for `campaigns/RefusalWar/`) has the same shape:

- `campaigns/RefusalWar/Intro.md` - campaign introduction (currently just front matter). Its YAML front matter holds campaign-level fields: `min_players` and `max_players` (how many players the campaign supports; Refusal War is 1 to 2), shown under the campaign's name on the home page's campaign list. Leave `max_players` out to show nothing. It also holds the campaign's starting instructions: `starting_named_pilots` (how many named pilots must be named before scenarios deploy; Refusal War is 2; see Named pilots under Playthrough identity), `starting_pilot_sp` (the SP each of them allocates; 150) `starting_bv` (the most BV the starting hangar may total; Refusal War is 6000) and `starting_min_mechs` (the fewest mechs it may hold; 4). `starting_warchest` (the SP a started campaign's warchest begins with; Refusal War is 4500; stored per run in `campaign_runs.warchest`, set by `StartRunWithPilots`, listed in the start rules and shown as the Funds box in the Manage page's Warchest section; a run started before the column existed reads 0). These are listed as bullets on an unstarted campaign's page (the site doesn't model Scale, it just says 6,000 BV). **The starting hangar is checked** by `checkStartingHangar` (`startcheck.go`): units are looked up in the catalog, BV is each unit's *base* BV (what a standard 4/5 pilot gives it; pilot skill never matters), only catalog type `Mek` counts as a mech (a tank adds BV but isn't a mech), and a unit missing from the catalog is a problem since its BV is unknown. The wizard asks for the check as soon as a pasted link has a valid shape (`GET /api/campaign/hangar-check?campaign=&hangar=`, which reads the force from MekBay, never writes, and needs a seed with a named company): it waits 350 ms after typing, shows a spinner and "Reading your hangar..." meanwhile, ignores a reply for a link that has since changed, then shows a summary (mechs, BV of the limit), the units counted and every problem, and keeps Start campaign disabled until the hangar passes. Because the player fixes the hangar in MekBay without changing the link, a refresh icon embedded on the right of the link box re-reads it at once (disabled until the link has a valid shape, and spinning while it reads), and returning to the tab while the hangar is failing re-checks it automatically; each read carries a sequence number so an older reply can never overwrite a newer one, **a refresh of an unchanged link keeps the finished result on screen** (a small "Updating" note with a spinner appears beside the summary, the new data replaces it only when it arrives, identical data repaints nothing at all, and a failed refresh keeps the old data with a "Couldn't refresh" note, so Start follows the committed data and the server re-checks on submit) while a *changed* link clears it, since the old result would describe a different hangar, and the reason a hangar fails is shown once (in the status area, and as the disabled button's tooltip) rather than repeated in the hint line. `POST /api/campaign/start` runs the same check on the server before creating anything (400 with the problems, 502 if MekBay can't be read); changing the hangar link of an already started campaign is not checked again.
- `campaigns/RefusalWar/Keywords.md` - registry of every keyword scenarios can grant or require, one bullet per keyword ID.
- `campaigns/RefusalWar/Scenario_NNN/` - one folder per scenario, zero-padded and numbered sequentially, containing `Setup.md` (fluff, map, forces, special rules) and `Outcome.md` (victory conditions and rewards). `Scenario_000` is the "Trial of Position", a one-off graduation mission whose kill count determines each pilot's starting SP. Later sorties are referred to as "Sortie 001", etc.

## Website

Go is the base for the website, chosen so it can grow into keyword/branch state tracking rather than staying a static site. Run it from the repo root with `go run .` (flags: `-addr :8080`, which defaults to `localhost:8080` under `go run` (detected by the `go-build` temp path of the binary) so Windows Firewall doesn't prompt for every rebuilt binary; `-content campaigns`, `-db playthroughs.db`, `-postgres <url>`). It reads the campaign folders on every request (edit a Markdown file and refresh), renders Markdown with `goldmark` and front matter with `yaml.v3`, and embeds its templates and CSS from `internal/site/` (`templates/*.html`, `static/style.css`). Dark mode only, with an industrial-yellow BattleTech look (no theme toggle). Every page's big title (`h1.bt-title`) use the BattleTech old-style font `internal/site/static/bt_oldstyle.ttf`, loaded with `@font-face` in `style.css`. The scenario fluff (the leading blockquote in `Setup.md`) is pulled out of the body and shown as an "incoming transmission" briefing block; a paragraph that opens with a quotation mark becomes a styled pull quote, and a paragraph right after it that opens with an em dash (`— Name, Title`) becomes its attribution line. The scenario's Waypoints section (see the scenario conventions) and Outcome section are collapsed `<details class="fold">` blocks, Waypoints above Outcome, with a collapsed Force files block (the `.mul` downloads) between them; their open/close animation is a small Web Animations script in `layout.html` (the CSS-only `::details-content` approach doesn't work in Firefox, so don't switch back to it); without the script it still toggles. Routes: `/` (campaigns), `/<campaign>/` (intro and scenarios), `/<campaign>/<scenario>/` (Setup then Outcome, plus download buttons for the `.mul` files listed in the `forces` front matter, served from `/<campaign>/<scenario>/forces/<file>`; only listed files are served), `/<campaign>/keywords/`. Campaigns are any folder under `campaigns/` containing `Scenario_NNN/` folders, so a new campaign or scenario that follows the conventions below needs no code changes. `go vet ./...` and `go test ./...` are the checks.

## Checks, CI and Docker

The checks are `gofmt -l .` (must print nothing), `go build ./...`, `go vet ./...`, `staticcheck ./...` (config in `staticcheck.conf`, which turns off ST1005 because a few error strings are visitor-facing sentences; run it with `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...`) and `go test ./...`. `.github/workflows/ci.yml` runs all of them, plus a `docker build`, on pushes to `main` and on pull requests. The `Dockerfile` is a multi-stage build (pure-Go, `CGO_ENABLED=0`) into a distroless nonroot image that bundles `campaigns/` and keeps the SQLite database in the `/data` volume (`-db /data/playthroughs.db`) unless `DATABASE_URL` is set; it listens on 8080. `data/units.json` is not in the image (see `.dockerignore`). Hosting note: DigitalOcean App Platform's disk is ephemeral and would lose a SQLite file on every deploy, so there it must run against Postgres via `DATABASE_URL`. The footer shows the build's short commit hash: the revision `go build` stamps when `.git` is present, else the `COMMIT_HASH` environment variable (on App Platform set it to `${_self.COMMIT_HASH}`, since neither the Go buildpack nor the Dockerfile build sees `.git`), else `dev` (as under `go run`); see `internal/site/commit.go`.

## Playthrough identity (seeds)

Visitors track their own campaign without logging in, using a **seed**: 8 to 32 lowercase letters and digits that the visitor chooses or generates (the Random button makes two English words plus three digits, e.g. `ironfalcon417`). The seed is the only credential, so anyone who knows it can read and change that playthrough; it is stored in an HttpOnly `seed` cookie (one year) and shown back to the visitor in a popup. The server hashes it (`playthroughID` in `seed.go`) into the opaque key used in the database (`internal/site/store.go`); the seed itself is never stored in the database. The store speaks SQLite (pure-Go `modernc.org/sqlite`, file set by `-db`, git-ignored; the default for local runs) or PostgreSQL (pure-Go `pgx`): the `-postgres` flag defaults to `$DATABASE_URL`, and when that is non-empty it is used instead of `-db`. Queries are written once with `?` placeholders and rebound for Postgres by `Store.q`; keep SQL to what both accept. Postgres is for hosts without a persistent disk (DigitalOcean App Platform with its dev database). `TestStorePostgres` runs only when `TEST_DATABASE_URL` is set (CI sets it with a Postgres service container); locally, e.g. `docker run -d -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=bt -p 55432:5432 postgres:17-alpine` then `TEST_DATABASE_URL=postgres://postgres:pw@localhost:55432/bt?sslmode=disable go test ./...`. In code and the database a tracked run is a "playthrough", to avoid clashing with the `campaigns/` content folders.

A seed is a **company**: a new seed continues to a second popup step asking for the **company name** (`Playthrough.CompanyName`, e.g. "Wolf's Dragoons", validated by `parseCompanyName` in `setup.go`; a seed counts as set up once it has one). A company then runs **campaigns**, each with its own state: a campaign is *started* from its own page (the Start button on `/<campaign>/` opens a **wizard**, see Named pilots below), whose last step asks for **that campaign's MekBay hangar link** (any MekBay link will do: `parseHangar` in `setup.go`, mirrored by `canonicalHangar` in `campaign.js`, keeps only the force's instance ID and reduces it to `https://mekbay.com/?instance=<uuid>`, so `&sel=` (the selected unit, which we have no use for, even a garbled one), `&operation=`, tracking parameters and fragments are dropped, and a list of forces `<mine>,enemy:<theirs>` gives the first friendly one; only https on mekbay.com/www.mekbay.com is accepted, and an operation link gets a message saying to paste the hangar link instead; the wizard rewrites the link box to the plain link as soon as a pasted link is recognised; `campaign_runs` no longer has a `hangar_sel` column in its `CREATE`, existing databases keep the unused column, which defaults to empty so inserts without it work) and records a `CampaignRun` (table `campaign_runs`, one row per seed and campaign slug; the row existing means started). Starting again for a started campaign just changes its hangar link. While a campaign's pages are open the header shows a "Your hangar" link to that campaign's hangar. Endpoints (same-origin only): `POST /api/seed`, `POST /api/company` (name plus the optional owner UID) and `POST /api/campaign/start`; the popup logic is `internal/site/static/seed.js` and the campaign page's is `campaign.js`. There is deliberately no human player count (it used to be asked for but nothing used it). The company step also takes an optional **MekBay user ID** (`owner`, a UUID), which is per seed, shared by all its campaigns: MekBay only lets the owner's UID overwrite a force (the `saveForce` WebSocket action returns `not_owner` otherwise), so a playthrough that holds one is in **modify mode** (`Playthrough.CanModify()`) and is allowed to write to its hangars, while one without is read-only. The UID is a secret, like a password for all of that player's MekBay forces: it is stored server-side only (`owner_uid`, plaintext for now), never rendered back to the page (the field is a blank password input; a blank value keeps the saved one, the `clear_owner` checkbox forgets it), and must never be logged. The site only writes to MekBay when deploying a force (see MekBay hangar integration) and never reads damage yet; MekBay's protocol (`wss://mekbay.com/ws`, closed-source server, client in `../mekbay`) is unofficial and undocumented. Keyword and scenario-progress tracking build on this but are not implemented yet.

**Named pilots** follow BattleTech: Hot Spots - Draconis Reach, "Named Pilots" (pp. 34-35; the book is at `C:\Users\david\iCloudDrive\Documents\Battletech\Books\`, too big for the Read tool, so extract pages with `pdftotext -f 34 -l 37` and note the PDF's physical page is 2 higher than the printed number). Only named pilots improve Gunnery/Piloting, use Edge and earn Edge abilities; which abilities a pilot has chosen is tracked (see Edge abilities below). A pilot tracks one number, **total SP earned** (`named_pilots.sp_total`), and the SP allocated so far in four columns (Gunnery, Piloting, Edge tokens, Edge abilities); **unallocated SP is the total minus the columns' sum** (`NamedPilot.Unallocated`), never stored separately. A new pilot's starting SP is all allocated; later SP is earned into the total (`Store.EarnSP`, `POST /api/pilots/earn`) and spent with `Store.AllocateSP` (`POST /api/pilots/allocate`, which adds to the columns and refuses more than is unallocated, checked in the same SQL statement). The older direct `POST /api/pilots/sp` (`AwardSP`) raises total and columns together and is no longer used by the UI. A database from before the total existed gets `sp_total` backfilled to the columns' sum (`Store.init`, `TestMigrateSPTotal`). `pilot.go` holds the book's Named Pilot Improvement Table as ladders (cumulative SP to reach a level), and derives a pilot's levels; `TestKirbyExample` replays the book's worked example. **Handicap is deliberately not tracked** (the book gives each step a handicap that balances opposing forces; this campaign doesn't use it), so don't add it back. A new pilot is a 4/5 pilot with 1 Edge token and 0 SP. At most four living named pilots per command (`maxNamedPilots`); a pilot killed in action (shown as "Killed in Action" everywhere; the column and code say `fallen`) keeps their row but frees a place, can't earn SP and leaves the active list and the overview. Tables/queries: `named_pilots`, `Store.Pilots/AddPilot/EarnSP/AllocateSP/MarkFallen`; endpoints `POST /api/pilots`, `/api/pilots/sp`, `/api/pilots/fallen` (`pilots.go`), and the Named pilots panel on the Manage page (`pilots.js`): each pilot is a card with the wizard's yellow-number stat boxes, a **Manage SP** button and a **More** drop-down (a native `<details>`, closed by an outside click or Escape) whose first item is "Mark as killed in action" (`POST /api/pilots/fallen`); room for more items later. A pilot killed in action isn't removed: their card moves to a **Memorial** section below the active pilots (no buttons): the portrait goes grayscale with a red rotated **K.I.A.** stamp laid over it (`.kia-stamp`), the stats and ability chips are dimmed, and the "Killed in Action" badge stays vivid red, and they stay revivable or deletable under Advanced Management. Manage SP opens a level-up dialog (`#sp-dialog`) with the same sliders, number boxes and stat boxes as the wizard (`static/allocator.js`, the shared `SPAllocator`, which the wizard also uses): the sliders spend only the pilot's unallocated SP (the sliders and number boxes show each column's whole total with what the pilot already has as their minimum, and reach up from there by the unallocated SP; a row's number turns yellow while it has a pending change; the boxes preview the new levels), Apply saves, and an "Add earned SP" box (which asks for confirmation) *stages* SP for the pilot's total (SP is entered by hand because scenario rewards aren't automated yet): it raises what can be spent in the dialog, shows "+N SP earned. Not saved until you press Apply" with a Clear link, and nothing is saved until Apply, which posts the earned amount and the allocation together to `POST /api/pilots/allocate` (`earned` field, `Store.ApplySP`, one atomic statement); closing the dialog discards the staged SP. **Each campaign sets its starting instructions in `Intro.md` front matter**: `starting_named_pilots` (Refusal War: 2) and `starting_pilot_sp` (Refusal War: 150, the SP each starting pilot allocates; the book's p. 17 gives 150 too). **Starting a campaign is a wizard** (`#start-wizard`, `campaign.js`): one step per starting pilot (a name plus an allocator that splits the pilot's starting SP over the four columns, with four labeled boxes (Gunnery, Piloting, Edge tokens, Edge abilities, each a big yellow number with a big centred level with a tiny, thin "-> next level" (a small drawn arrow and the next level in bold muted gray, like the caption) at its lower right, "SP/needed SP" beneath it and a thin yellow progress bar for how far along that is; at the top of the ladder it says "max" with a full bar and no next level) beside the name showing the levels the allocation reaches live, computed from the same ladders the server uses, passed to the page as JSON in `data-ladders`; every SP must be allocated before moving on, and the allocator refuses to over-allocate; the sliders and the number boxes' arrows both step by 10 SP, and Next stays disabled, with a hint line saying what is missing, until the step is valid), then a step for the hangar link, with a step counter and progress bar at the bottom. It posts everything to `POST /api/campaign/start` in one go (fields `pilot<i>_name`, `pilot<i>_gunnery`, `_piloting`, `_edge_tokens`, `_edge_abilities`); `parseStartingPilots` validates it (exactly the campaign's pilot count, unique names, each allocating exactly `starting_pilot_sp`) and `Store.StartRunWithPilots` creates the run and the pilots in one transaction, refusing a second start (`ErrAlreadyStarted`). Posting again for a started campaign only changes its hangar link (the small `#run-dialog`). The campaign's pilot count is a *starting* requirement only: pilots can die mid-campaign, so deploying never checks how many are alive, and pilots are added later with the **Recruit New Pilot** button under the active pilots on the Manage page (above the Memorial), which opens a one-step dialog (`#recruit-dialog`, `pilots.js`): a random portrait no living pilot has (click it for the picker), a name, a rank, and the campaign's `starting_pilot_sp` (150 in Refusal War) to allocate with the same sliders, number boxes and live stat boxes as the start wizard (`SPAllocator`); spending all of it is optional, and whatever is left stays unallocated for Manage SP (a campaign with no starting SP shows no sliders). It posts `POST /api/pilots` with the allocation in the `gunnery`/`piloting`/`edge_tokens`/`edge_abilities` fields (refused above the starting SP; `Store.AddPilotWithRank` takes the allocation and a total, which is the starting SP; names are unique per campaign ignoring case, a command holds `maxNamedPilots` living pilots, so the button is disabled with a reason when it is full and comes back when a pilot is Killed in Action). The wizard script has no JS test runner; `TestScriptsParse` only syntax-checks it, so after changing it drive it with jsdom against a running server (that is how it was verified). The book's 100-SP-per-track cap is deliberately not enforced because campaigns set their own rewards (Scenario 000 pays 150 to 900); starting SP; the MVP and combat-pay rules and assigning pilots to hangar units are not built yet.

**Edge abilities.** The twelve Edge abilities of Hot Spots: Draconis Reach (printed p. 166, physical page 168 of the PDF; text kept as the book prints it, Alpha Strike rule first with the Total Warfare rule in parentheses) are the catalog in `abilities.go` (`edgeAbilities`: stable ID, name, category, text; Attack, Indirect Fire, Defense, Heat, Melee, Movement). The book says that when a named pilot reaches a new Edge abilities level they choose one, permanently (p. 36, step 4); this site only records the choice, it doesn't play the abilities. A pilot may hold as many abilities as their Edge abilities level, so **pending = level - learned** (`NamedPilot.PendingAbilities`, never negative). Whenever it is above zero the pilot's card on the Manage page shows a yellow "Choose a new Edge ability" / "Choose N new Edge abilities" button beside an "Edge abilities" row of chips for the ones already learned (hovering or keyboard-focusing a chip shows the same ability card as the picker in a floating panel anchored under it, `showSkillTip`, like the mech icon hover card on the overview; there is no native `title`). It opens a picker (`#skill-dialog`, `pilots.js`) with one combo box per pending ability, grouped by category and listing only abilities the pilot doesn't have; one chosen in another box is greyed out, and the chosen ability shows as a card under its box (`fillAbilityCard` in `pilots.js`): its name, a pill in its category's colour, and the rule with the **trigger in bold** as the book prints it (everything up to the first colon outside parentheses, `splitTrigger`, since Protector's trigger contains a "(TW: 1 hex)" aside) and each "(TW: ...)" aside dimmed; an empty box shows a dashed placeholder. **Learn** asks for confirmation (the choice is permanent) and posts all the choices together to `POST /api/pilots/abilities` (repeated `ability` fields; `Store.LearnAbilities`, one transaction, which refuses a wrong number of choices, an unknown or already-learned ability, a pilot with nothing pending, and a pilot killed in action). Learned abilities are rows of `pilot_abilities` (pilot, ability ID, order learned), removed with the pilot or campaign. They are permanent like allocated SP: the only undo is **Reset Edge abilities** in Advanced Management (`Store.ResetEdgeAbilities`, `POST /api/pilots/abilities/reset`, after a confirm; it works on killed pilots too, doesn't touch SP, and leaves the pilot owed the choices again). Resetting a pilot's *SP allocation* (the records dialog's other reset, formerly labelled "Reset abilities", now "Reset SP allocation") **also forgets their learned Edge abilities**, since they depended on that SP: so does setting a total below the allocation with the reset agreed (`ResetPilotSP` and `SetPilotTotal` delete the `pilot_abilities` rows in the same transaction; a total at or above the allocation touches nothing), and the confirmations say so when the pilot has any (`TestSPResetForgetsEdgeAbilities`). A memorial card shows the chips read-only, and the records row lists the abilities. `TestEdgeAbilityCatalog`, `abilityStore` and `TestEdgeAbilitiesThroughThePages` cover the server; the picker and the reset were driven with jsdom.

**Pilot portraits.** Each named pilot has a portrait: one of 79 MechWarrior 5 pilot busts (transparent backgrounds) vendored in `internal/site/portraits/` at 192x192 (see `portraits/NOTICE.md`; refresh with `go run gen_portraits.go -src <folder>` from `internal/site`, which lowercases names and rescales), embedded with `go:embed` and served at `GET /portraits/{file}` (`portraits.go`; lowercase PNG names only). `portraits()` groups them Male/Female/Generic/Special from the file names (`male_rank2_3.png`); the list goes to the page as JSON (`data-portraits`). The start wizard gives every starting pilot a random portrait nobody else has, shown beside the name; clicking it opens `static/portraitpicker.js` (`PortraitPicker.open`, shared with the Named pilots panel), a scrollable grid that opens scrolled to the current choice and dims portraits another pilot has. Two living pilots of a campaign never share one (`ErrPortraitTaken`; a fallen pilot frees theirs), enforced by `AddPilot`, `StartRunWithPilots`/`parseStartingPilots` and `SetPilotPortrait` (`POST /api/pilots/portrait`); a pilot added from the panel gets a random free one. The column `named_pilots.portrait` was added with `Store.ensureColumn` (the pattern for adding a column to an existing table); a pilot with none stored (from before portraits) is shown a stable one derived from their ID by `portraitOf`. Fallen pilots show theirs in grayscale and can't change it.

**Overview and Manage pages.** A started campaign's page (`/<campaign>/`) shows only a compressed "Your force" overview: a roster of the living named pilots (portrait, name, SP earned, and the same yellow-number stat boxes as the start wizard for Gunnery, Piloting, Edge tokens and Edge abilities) and a one-line hangar summary in the same card style (up to 8 unit icons, each with a hover card of the unit's details, anchored to the icon, which also gets a yellow border (also on keyboard focus), then the unit count, damaged/destroyed counts and the total base BV; the per-unit list is the Manage page's Mechs section) (`static/force.js`, built by the shared `static/forcesummary.js` (`ForceSummary.build`, which also owns the unit hover card; load it first), fed by `GET /api/campaign/force`, which reads the hangar anonymously from MekBay and sums the base BV of every catalog-known unit; destroyed units still count). A "Manage force" button leads to `/<campaign>/manage/` (`manage.go`, `templates/manage.html`; its main sections, Warchest, Named pilots and Hangar, share the bigger `h2.section-title` heading), which holds everything else: a **Warchest** section at the top (a Funds box with the run's warchest in SP, starting at the campaign's `starting_warchest`; nothing spends it yet and the rest of the finances are TBD), then the full Named pilots panel (portraits, award SP, add, mark fallen), then a **Hangar** section under the Memorial that holds the hangar (there is no Open hangar button: the page carries the hangar URL as `data-hangar-url` for the row click, and Change hangar link is in the Danger zone above Delete, so it isn't clicked by accident; the `<p id="campaign-run">` under the unit rows, which holds the Purchase new unit button, is the wrapper `campaign.js` looks for) and lists every unit of the hangar as the same mech rows as the deploy popup, made taller here (`.mech-list` styles) and without the pilot G/P chip, since a hangar pilot's skills are about assigning pilots, not the mech; each unit name is followed by a small gray "opens in a new tab" icon (`.mr-ext`, no button border, yellow on hover) opening, in a new tab, the unit's generic page on mekbay.com (`https://mekbay.com/?gs=cbt&shareUnit=<MekBay unit ID>&tab=General`, `unitPageURL`, sent as `mekbayUrl` in the hangar views; clicking anywhere else on a Hangar row opens the player's hangar on MekBay with that unit selected (`rowUrl`, built by `hangarlist.js` from the Open hangar link plus `&sel=<force unit ID>`, which MekBay's `restoreSelectionFromUrl` reads; keyboard Enter works too); the icon is opt-in through `MechRow`'s `externalUrl`, so the deploy popup's checkbox rows have none, and only https://mekbay.com/ links are accepted) (`static/hangarlist.js` with `mechrow.js` and `forcesummary.js`: the section opens with two big labelled numbers, **UNITS** and **BASE BV** (`ForceSummary.stats`: small-caps label over a big yellow number, plus DAMAGED / DESTROYED boxes only when there are any), with no icons since the rows below carry the units, above the link buttons and the rows; it embeds the cached hangar like the overview, so it paints at once and refreshes from `GET /api/campaign/force`, with a "Showing your last known hangar" note if the live read fails) and the Danger zone; it redirects back to the campaign page when the campaign isn't started. An unstarted campaign's page still has the start rules and wizard.

**Factions and ranks.** Each campaign names its player force's **faction** in `Intro.md` front matter (`faction: clan`), and the faction decides the cosmetic flavour of its named pilots, starting with their **ranks**. `factions.go` is the registry (`factions` map: ID, name, rank ladder lowest first); Refusal War is `clan`: MechWarrior, Star Commander, Star Captain, Star Colonel, Galaxy Commander, saKhan, Khan (per https://www.sarna.net/wiki/Clan_Military_Structure, which also lists Point Commander, Nova Commander and others we skipped). To add a faction, e.g. an Inner Sphere Royal House force with Sergeant, Lieutenant and so on, add an entry there and name its ID in that campaign's Intro.md; a campaign can instead list its own `ranks:` in Intro.md, which replaces its faction's ladder without a code change. `Campaign.Faction/Ranks` carry this to the pages; an empty or unknown faction (and no `ranks`) turns ranks off. A pilot's rank is a name stored in `named_pilots.rank` (empty means the lowest, so everyone starts as the first rank, and a stored rank the campaign no longer has reads as the lowest too: `rankFor`); it is cosmetic and changes nothing in play. It shows under the portrait (8rem square on the Manage cards and in the wizard) on the Manage page, on one line: the longest Clan rank, Galaxy Commander, fits at the stylesheet's size and `fitRanks` in `pilots.js` scales down any rank still too wide for the box (a longer ladder in another campaign), the way mech row role labels do; clicking it opens a small dialog (`#rank-dialog`) with a dropdown of the campaign's ranks (`Store.SetPilotRank`, `POST /api/pilots/rank`, which refuses anything not in the campaign's ranks), and the overview shows it beside the SP. A pilot Killed in Action keeps their rank, shown as a label in the memorial. The stat boxes call the Edge abilities column "Abilities" (`boxLabels` in `pilot.go`, sent to the pages as `short` in the ladders JSON) so the label doesn't wrap; the slider rows keep the full name.

**Advanced Management.** An "Advanced Management..." button (a regular yellow one) inside the Danger zone of the Manage page, which is collapsed behind its "Danger zone" heading and caret (a `<details class="danger-details">` holding Advanced Management, Change hangar link and Delete campaign, animated open and closed by the same script in `layout.html` as the scenario pages' folds, which needs its content wrapped in `.fold-body`), opens a dialog listing every pilot the campaign has had, active or killed in action, to correct misclicks and desyncs. Each row can: **rename** the pilot (a pencil beside the name turns it into a text field with a confirm check embedded in it; Escape cancels; the same editor, shared in `pilots.js` as `attachNameEditor`, is on the pilot cards of the Manage page too, and a new name shows in both places at once; `Store.RenamePilot`, `POST /api/pilots/rename`, names stay unique per campaign ignoring case); **Revive** (`Store.RevivePilot`, `POST /api/pilots/revive`; refused when the command already has `maxNamedPilots` living pilots, and a portrait another living pilot took in the meantime is swapped for a free one); **Delete** (`Store.DeletePilot`, `POST /api/pilots/delete`; permanent, after a confirm); **Reset SP allocation** (the factory reset, formerly "Reset abilities") zeroes the four allocation columns and keeps the total, so every earned SP becomes unallocated, and forgets the pilot's learned Edge abilities (`Store.ResetPilotSP`, `POST /api/pilots/reset`, after a confirm); **Reset Edge abilities** (see Edge abilities); and a **Warchest funds** box at the top of the dialog that sets the force's funds directly (`Store.SetWarchest`, `POST /api/warchest`, whole number 0 to 100,000,000; the page behind reloads on close, like the other actions; `TestSetWarchest`); **Set total SP**, an override of the pilot's total (`Store.SetPilotTotal`, `POST /api/pilots/total`): a total below what is already allocated first asks the player to confirm that it resets the allocation, and the server refuses it with 409 unless the request carries `reset=1`, so the rule can't be bypassed by accident. Every action updates its row in place and **never closes the dialog**; the page behind is reloaded once when the dialog is closed, if anything changed. `TestReviveAndDeletePilots`, `TestRepairEndpoints` and `TestRenamePilots` cover the server; the dialog's script was driven with jsdom against a rendered page (no JS test runner in the repo).

**Confirmations.** The site never uses the browser's `window.confirm`. `static/confirm.js` provides `Confirm.ask({title, message, confirmLabel, cancelLabel, danger}) -> Promise<boolean>`, a styled modal dialog that stacks on top of any dialog already open (the Advanced Management and Manage SP dialogs call it for Killed in Action, Reset abilities, a total below the allocation, Delete pilot and Add earned SP). `danger` makes the confirm button red and focuses Cancel, so a stray Enter never confirms something destructive; Escape and a backdrop click cancel; text is inserted as text. Load it before the script that uses it (`manage.html` does). The delete-campaign popup is its own dialog (`campaigndelete.js`). **Button rows** (`.form-actions`) give every button the same fixed height, font and centring (end of `style.css`), so Apply/Close, Delete/Cancel and the like line up exactly whatever their style.

**Deleting a campaign.** A started campaign's Manage page ends with a red "Danger zone" holding a Delete button (`static/campaigndelete.js`) that opens a confirmation popup; confirming posts `POST /api/campaign/delete` (`deleteCampaign`, same-origin, started campaigns only), which calls `Store.DeleteRun`: one transaction removing that campaign's named pilots, saved MekBay operation IDs and the run. The company and its other campaigns are untouched, and nothing is deleted in MekBay itself (the hangar, OpFors and operations stay in the player's account). The campaign then shows as not started and can be started again. `TestDeleteCampaign` covers it.

Schema changes go through `Store.init` (`store.go`): `CREATE TABLE IF NOT EXISTS` for the current tables, run one statement at a time, after `migrateLegacy` upgrades an older database. The one migration so far (to companies and per-campaign hangars) drops the old single hangar link, player count and all operations but keeps seeds, creation times and owner UIDs, because the single hangar couldn't be attributed to a campaign. `TestMigrateLegacySQLite` and `TestMigrateLegacyPostgres` (the latter only with `TEST_DATABASE_URL`) build an old-format database and check it; add a similar test with any further migration.

## Long-term direction

These files are meant to eventually drive a campaign website: scenario pages with fluff images, tracking of scenario forks/jumps (branching between scenarios), and per-playthrough state via KEYWORDS. Keywords are tracked by the campaign as a whole, not by individual pilots, copying how BattleTech: Aces (Scouring Sands) tracks them. Only a simple read-only site exists so far (see Website above); keyword and branch tracking are not built yet, so don't build them unprompted. When adding or reformatting data keep it both machine-parsable and human-readable/writable: consistent headings and names, plain Markdown/XML/JSON, no ad-hoc prose where a structured field would do (e.g. scenario IDs, branch targets, keywords granted or required). Prefer stable identifiers over free-text references.

## MekBay hangar integration

**Built so far: deploying a force for a scenario.** A scenario page with OpFor files shows a "Deploy your force" section once the playthrough has *started that campaign* (otherwise it points to the campaign page). Its button opens a popup (`mekbay.js`, `#deploy-dialog`) fed by `GET /api/mekbay/hangar`: every unit of the campaign's hangar, read anonymously from MekBay (`MekBayClient.ReadHangar`), with name (Clan name preferred), class, tonnage, role, pilot and skills, Damaged/Destroyed tags and **base BV**: this campaign (a custom Classic BattleTech ruleset in the style of BattleTech: Aces, partly homebrewed) never lets pilot skill change a unit's BV, which matches the book's rule that named pilots' skills don't affect BV and avoids rewarding bad pilots with room under the cap. `adjustedBV` (`units.go`, MekBay's BV 2.0 table) is kept only for the `bv` metadata of the OpFor force we write, which is what MekBay itself would total. The player ticks the units for the mission; a scenario's `bv_limit` front matter (optional, e.g. `bv_limit: 10000` in Scenario 001; absent means no limit) caps the total, checked in the page and again by `deployProblem` (also refuses destroyed and unknown units). Deploying (`POST /api/mekbay/deploy`, modify mode only, since MekBay only accepts the owner's writes) goes through `MekBayClient.SyncOperation` (`mekbay.go`), which in order: rearranges the hangar force so the chosen units sit in a group named "Deployed" and every other unit in "Hangar" (`deployGroups` in `deploy.go`; other groups are dissolved, existing Deployed/Hangar groups keep their ID and color, everything else in the force, e.g. damage and C3 networks, is untouched), saves an OpFor force built from the scenario's `.mul` files (one group per file, named "OpFor 1", "OpFor 2"; pilots and skills from the `.mul`; unit IDs from `units_index.json`), and saves an operation named `<Campaign> - Scenario NNN` pairing the hangar (friendly) with the OpFor (enemy). The IDs are stored per seed, campaign and scenario in `mekbay_operations`; deploying again re-sorts the hangar but **keeps the existing OpFor and its damage** unless the popup's "Reset OpFor" box is ticked (`reset_opfor=1`). Without modify mode the popup still lists the hangar but can't deploy and says to add the user ID. Pilot assignment is not built (the popup shows the hangar's pilots as they are). `units_index.json` is a slim copy of `data/units.json` (name, chassis, model, BV, tons, weight class, role, type, tech base, icon file name) embedded because the full catalog isn't in the Docker image; it also carries each mech's `engine` (the crippling rule) and `ammo` entries (the rearm breakdown); regenerate it with `go generate ./internal/site` after refreshing `data/units.json` (see Unit names, icons and mech rows). Tests use a fake `MekBay` (`WithMekBay`) and a fake WebSocket server; `TestMekBayLive` hits the real mekbay.com and only runs when `MEKBAY_LIVE_UID` and `MEKBAY_LIVE_INSTANCE` are set (it reads the hangar and creates an OpFor force and operation in that account, but leaves the hangar's groups alone). Not built yet: reading damage after a sortie (the start/end snapshots below), pilot assignment, and splitting `enemy:` IDs out of a pasted multi-force link.

**Hangar cache (pull-through).** Reading a hangar from MekBay takes a moment, so every successful live read is also saved in the database (`hangar_cache`, one row per playthrough and campaign: the hangar link's instance, the `HangarForce` as JSON, and a Unix time; `Store.SaveHangarCache/CachedHangar`, `hangarcache.go`; works on SQLite and Postgres and is cleared by `DeleteRun`). The campaign overview and the scenario page embed the last copy (`Page.ForceJSON` / `Page.DeployJSON` in a `data-cached` attribute) so they paint the hangar straight away, and `force.js` / `mekbay.js` then read MekBay in the background and replace it (stale-while-revalidate): only a run that has never been read shows "Reading your hangar...", once. A failed live read keeps the cached copy on screen with a "Showing your last known hangar" note; the deploy popup keeps the player's ticks across the refresh. The live endpoints `GET /api/campaign/force` and `GET /api/mekbay/hangar` write through; starting a campaign primes the cache with the hangar its starting check read. A copy belongs to the hangar link it was read from, so changing the link makes the old one invisible (`CachedHangar` matches on the instance). The deploy itself and the start check's own reads are always live. `TestHangarCachePullThrough` and `hangarCacheStore` cover the server; the scripts were driven with jsdom (no JS test runner in the repo).

Findings from probing MekBay (2026-11): its server is closed source and only reachable over `wss://mekbay.com/ws`, so everything here is unofficial and may break. An anonymous client (random `sessionId` and `uuid`, `register` with `version: 2`, then `getForce {instanceId}`) can read any force by ID; writes (`saveForce`) need the owner's UID, which is why setup has the optional owner UID (modify mode). Read-only is the default and the design must work without writing.

- **Unit condition pills (Hangar rows).** MekBay stores no "crippled" flag (only `destroyed`, the raw `locations`/`crits`, and a torso-check result in `state.ruleChecks`; crippled is computed in its client, `src/app/models/rules/mek-rules.ts`), so `condition.go` recomputes it the way MekBay does (forced withdrawal on, its default): two engine crits; two destroyed limbs, one a leg; two destroyed torsos; or one destroyed torso when the engine isn't Fusion/Compact or the stored torso check failed. A location is destroyed when its internal loss reaches its structure, taken from `structureByTons` (standard bipeds; an unknown tonnage never counts as crippled), and the catalog's `engine` is in `units_index.json` for that. `conditionOf` shows the worst state only: destroyed > crippled > internal structure damage > armor damage, each its own pill colour on the mech row (`mechrow.js`, `.mr-chip.cond-*`; the tooltip says why), plus a separate blue "Ammo expended" pill when any ammo bin has been used (rearming is a different need from repair). Hangar views carry `condition`, `conditionNote`, `ammoExpended`. `TestConditionsOfTheLiveHangar` replays the raw values of a real four-mech hangar.
- **Status pill tooltips.** The condition and ammo pills on a mech row don't use the browser's `title`: hovering or keyboard-focusing one shows the same floating card as the unit icons (`.unit-tip.pill-tip`, built by `attachTip` in `mechrow.js`, one element per page, moved into an open dialog when the pill is in one so it isn't hidden beneath it): the condition in its colour with the reason as a sentence (location codes spelled out, `conditionText`), and for the ammo pill the breakdown and the rearm cost.
- **Purchase new unit (Hangar section).** A "Purchase new unit" button under the unit rows opens `#purchase-dialog` (`static/purchase.js`): a search box over MekBay's unit list (`GET /api/units/search?q=&campaign=&all=1`, `search.go`; debounced, a reply for older text is ignored, Enter searches rather than buys), whose results are the same mech rows as the hangar (without the pilot chip) with the unit-page link, and **clicking a row adds it to "Your cart"** (no Stage button; `MechRow`'s `onPick`, also Enter or Space) **and clicking it again takes it out**: the cart holds one of each unit (`stage` refuses a duplicate), a result in the cart is tinted like a unit picked in the deploy popup and badged `In cart`, and the cart sits below the results (which keep a fixed height so rows don't jump), each cart row with a small × to remove it; the search box is a themed field with a magnifier and a clear button, and the faction checkbox the site's square yellow-ticked `.themed-check`; MekBay offers no embeddable search or way to hand a chosen unit back (no postMessage or callback), but its data is public, so the site searches its own embedded catalog the way MekBay does (typed words matched, punctuation ignored, against chassis and model; mechs only; best matches first: every word starting a word of the name, then by name; at most 40 shown with the total). A campaign names a faction and an era in `Intro.md` (`availability_faction: Clan Wolf`, `availability_era: Clan Invasion` for Refusal War), and the search then lists only the units MekBay says that faction fields in that era (`availability.json`, built by `gen_units.go` from MekBay's `factions.json` and `eras.json`, vendored in `data/`, joined by Master Unit List ID), with a checkbox in the popup, ticked by default, to search everything (`all=1`); a campaign that names neither has no filter. Re-run `go generate ./internal/site` after refreshing `data/units.json`, `factions.json` or `eras.json`, or when a campaign names a new faction or era. the same "Cost N SP. Warchest A → B SP." line as repair, and a Buy button. BV is SP: each unit costs its base BV. Buy posts `POST /api/hangar/purchase` (`purchaseUnits` in `purchase.go`, repeated `unit` fields; modify mode only; `purchaseCost` refuses anything that isn't a catalog mech), which charges the warchest first (`SpendWarchest`, refunded if MekBay fails) and adds each unit, undamaged with a 4/5 pilot, to the force's Hangar group in MekBay (`MekBayClient.PurchaseUnits`, `addUnitsToForce`). `TestPurchaseEndpoint`, `TestAddUnitsToForce`, `TestPurchaseCost`.
- **Truly destroyed, repair and rearm (Hangar rows).** Per Hot Spots: Draconis Reach (the SP Activity Cost Table and "Destroyed vs. Truly Destroyed", printed p. 33, physical page 35), a mech whose center torso internal structure is eliminated is **truly destroyed** (`CondTruly`, shown as a dark red "Truly destroyed" pill, above plain destroyed): it can't be repaired or salvaged. Every other mech row has **Rearm** and **Repair** buttons at its right (`mechrow.js` `actions`, wired in `hangarlist.js`, costs from the server in `service.go`). Repair costs tonnage x 0.5 (armor only), x 2 (structure and/or crits), x 3 (crippled) or x 5 (destroyed), x 1.5 rounded up for Clan or Mixed tech, and a repair at one level also covers the levels before it in the list. The repair dialog (`#repair-dialog`) lists only the repairs that would fix something on that unit (`repairOptions`: armor if any armor is lost; structure if a surviving location has lost internal structure or has a critical hit, engine hits excluded; crippled for a crippled or destroyed unit; destroyed for a destroyed one), none greyed out, the highest selected, with the price following the choice; any one can be chosen on its own, so a crippled unit can have just its armor repaired. What each level clears (`serviceUnitState`/`repairState`): armor = lost armor everywhere; structure = also internal structure in locations that aren't destroyed and critical hits there (not the engine's, which cripple, and not a destroyed location's); crippled = everything (locations, crits, torso check); destroyed = also the destroyed flag. Rearm is 10 SP per ton, counting each ammo bin with any consumed as one ton (`HangarUnit.AmmoBins`) and is confirmed with `Confirm.ask`, which lists the breakdown first (`items`: one row per ammo type, e.g. "LRM 5 Ammo: 1 ton · 5 of 24 shots used", from `ammoBreakdown`: MekBay records only the shots used per bin, so the capacity per ton comes from the unit's `ammo` entries in `units_index.json`, shots divided by slots, and a bin the catalog doesn't list still counts as a ton with an unknown capacity), whose optional `detail` line (bold yellow, red with `detailShort`) carries the same "Cost N SP. Warchest A → B SP." text as the repair dialog. Both go through `POST /api/hangar/service` (`serviceUnit`): modify mode only (it edits the force in MekBay with `MekBayClient.ServiceUnit`, `serviceUnitState` in `service.go`, `saveForce` like a deploy), the server works out the condition and the price itself (a repair names the level chosen and is refused with 409 if it isn't one of the unit's current options), charges the warchest atomically first (`Store.SpendWarchest`, 409 if it can't cover it) and refunds it if MekBay fails (`RefundWarchest`). Without modify mode the buttons are disabled with a tooltip. `TestServiceUnitEndpoint`, `TestServiceUnitState`, `TestRepairCostsFollowTheSPActivityCostTable`.
- **Damage:** a unit's `state.locations[loc].armor` / `.internal` are points *lost* (absent when undamaged), `state.crits` has critical hits and ammo `consumed`, `state.crew` has pilot hits. Join units to `data/units.json` by the unit's `unit` field (equals `name` there) for costs and totals.
- **Alignment is not stored in a force.** "Hostile" is only the `enemy:` prefix in the URL (`?instance=<mine>,enemy:<opfor>`) or an Operation (`?operation=<id>`, a saved list of whole forces with alignments; anonymous reads work). The OpFor is a separate saved force with its own instance ID, so setup should eventually accept the multi-force link and store the friendly and `enemy:` instance IDs separately, not a single `instance`.
- **MekBay cannot load part of a force.** Chosen design for deployment: the campaign's hangar force holds every mech, and players drag the units going on a sortie into a group named "Deployed" (case-insensitive); every other group is reserve. The site treats that group as the sortie roster. "Start sortie" records the roster and a damage/ammo/crew snapshot in our own database, "end sortie" re-reads the force and diffs against it, and a change to a reserve unit is flagged rather than billed. Players can regroup later without rewriting history because the snapshot is ours. Repairs are billed from the diff; clearing the damage in MekBay is up to the player unless modify mode is on.
- **Sortie hotlinks** could be built as `https://mekbay.com/?instance=<campaign>,enemy:<sortie opfor>` once each sortie's OpFor force exists (unknown: whether a non-owner can mark damage on a force they don't own; the scenario operation above already gives players a one-click link).

## Scenario file conventions

Follow the layout in `Scenario_000/Setup.md` and `Scenario_000/Outcome.md` when adding scenarios:

- Both files start with YAML front matter holding the machine-readable fields; the Markdown body below it is the human-readable write-up. The folder name lowercased (`Scenario_000` -> `scenario_000`) is the scenario `id`, and all cross-references (`next`, branch targets) use IDs, never titles.
  - `Setup.md` front matter: `id`, `title`, `planet` (the planet the scenario takes place on, e.g. `Strana Mechty` for Scenario 000; every scenario has one), `map`, `forces` (maps `opfor1`, `opfor2`... to the `.mul` files beside it), `readout` (optional list of `Label: value` lines, kept in order, drawn as a translucent technical readout over the left of the first image, and below it on narrow pages; used for planet data), and `images` (list of paths in the folder's `images/`, e.g. `images/strana_mechty.png`; each is shown as a wide fluff-image banner under the scenario title, cropped to the top, so put the subject in the upper part of the picture; empty until used).
  - `Outcome.md` front matter: `id`, `default_next`, and, only when a scenario actually branches or changes state, `outcomes`, a list of `{when, grants, next}`. Scenario 000 has none: it bootstraps the campaign's starting parameters (starting SP and pilot) rather than granting keywords. `when` is a plain condition over `kills` and `pilot_dead` for now (`kills >= 1`, `pilot_dead or kills == 0`); keep it simple and settle the syntax when a second scenario needs more. `grants` and any required keywords are IDs from `campaigns/RefusalWar/Keywords.md`; add new keywords there before using them.
- Deployment: every unit eventually gets an initial hex position (or is marked off-map with custom rules). Play uses standard two-mapsheet neoprene battlemats with labeled hexes. Hexes are written as four digits, `XXYY` (column then row, e.g. `2113`), as in `Scenario_001`; any other position format is still undecided, so leave deployment positions as `TBD` and don't invent coordinates or a schema until the user supplies them.
- `Setup.md`: `# Scenario NNN: <Title>`, a blockquote of fluff text (if it isn't written yet, leave the placeholder rather than inventing lore). Fluff is a mission briefing: an in-world commander speaking directly to the player in second person, formal and terse, in the style of the MechWarrior 2 briefings (see `Scenario_000/Setup.md`). Aim for less is more: show, don't tell, with a slightly alien yet familiar tone (Hidetaka Miyazaki-style lore, Dune), keep it to a few lines, and don't restate the rules that the sections below cover, then `## Overview`, `## Map`, `## Forces` (each force group, `### Player Forces` and `### OpFor N`, has a `**Deployment:**` line; the OpFor groups are bullet lists written as `Variant (gunnery/piloting) Role: Pilot, hex XXYY`, e.g. `Nova Prime (3/4) Skirmisher: Star Commander Alrek, hex 2113` (the role is the unit's Master Unit List role, capitalized as there: Scout, Striker, Skirmisher, Brawler, Missile Boat, Sniper, Juggernaut, Ambusher; look it up in the `role` field of `data/units.json`; the hex is left off for reserves, and `: Pilot, hex XXYY` entirely when neither is set yet, as in Scenario 000), with the mech name hyperlinked to MekBay as `https://mekbay.com/?gs=cbt&shareUnit=BM<IS-name>_<Variant>&tab=Sheet`; the unit ID is not always obvious: the chassis name has no spaces, the variant follows an underscore, and a chassis with no named variant takes no suffix. Some chassis use the Inner Sphere name (Mist Lynx is `BMKoshi_E`, Kit Fox is `BMUller_J`) while others don't (`BMMadCat_H` for Timber Wolf H, `BMLoki_Prime`, `BMGrizzly`). Ask the user for the working URL rather than guessing a new one) `## Special Rules`, and, when the scenario uses waypoints, `## Waypoints` last. Waypoints are a core mechanic, like the back-of-book waypoints in BattleTech: Aces (Scouring Sands): you only read one when the game calls for it. Each is a `### Waypoint X` heading (any `### ` name works) with its rules text beneath it; text between `## Waypoints` and the first `### ` is dropped. Where they are placed, and when they are revealed, belongs in `## Map` and `## Special Rules`. The site pulls the section out of `Setup.md` and shows each waypoint redacted (its text blacked out line by line, with a Reveal button that wipes the bars away; without JavaScript they are simply readable), inside the collapsed Waypoints block.
- `Outcome.md`: `# Scenario NNN: <Title> - Outcome` with `## Victory & Rewards`. Rewards are in SP (the campaign's pilot-advancement points). The kills-to-SP table is specific to Scenario 000's graduation mission; don't assume later scenarios use it.
- Campaign rules visible so far: pilots are named and persistent; a pilot who dies or fails to score a kill in the graduation mission is permanently removed and replaced by a new named pilot with 0 SP for Sortie 001; Clan honor rules such as zellbrigen apply and violations have mechanical consequences.

## Force files (.mul)

Each scenario folder also holds `OpFor1.mul` and `OpFor2.mul`: MegaMek's XML force format (MekBay exports and imports it), one `<entity>` per mech with its `<pilot>` skills and `<Game id>`. Prefer a real MekBay export over hand-writing. When hand-writing, `chassis` and `model` must match MegaMek's database. A mech with two names uses `chassis="<Inner Sphere name> (<Clan name>)"`, e.g. `Koshi (Mist Lynx)` or `Mad Cat (Timber Wolf)`; a single-name mech such as the Grizzly has a plain chassis and an empty `model`. Deployment attributes, `externalId` and `quirks` can be omitted.

## Working notes

- Mech names and variants are canon BattleTech Clan designs (e.g. Mist Lynx, Timber Wolf, Shadow Cat, Loki); keep to real variant names and Clan terminology (touman, zellbrigen, Trial, etc.).
- For mech data, the authoritative sources are the Master Unit List (`https://masterunitlist.battletech.com/units/<chassis>-<variant>`, e.g. `shadow-cat-a`) and MekBay, not Sarna. The MUL site is behind a Cloudflare bot challenge and returns 403 to automated fetches.
- `data/units.json` is a vendored copy of MekBay's unit catalog, downloaded from `https://db.mekbay.com/units.json` on 2026-11-16 (with `factions.json` and `eras.json` from the same host) (~27 MB; MekBay builds it from MegaMek's `mm-data`). To refresh it, re-download that URL over the file (e.g. `curl --compressed -o data/units.json https://db.mekbay.com/units.json`). Search it with Grep/Python rather than reading it whole. Each entry's `chassis` and `model` are exactly what `.mul` files need, and its `name` field is the `shareUnit` ID for MekBay links (e.g. `BMMadCat_H`). MekBay's source is at `../mekbay`.
- Maps referenced are official BattleTech battlemats (e.g. "Circles of Equals").
