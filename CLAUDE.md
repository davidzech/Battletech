# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A repo of custom tabletop BattleTech campaigns, one per folder under `campaigns/`, mostly Markdown. A Go web server turns the campaigns into a website; there is no lint or test tooling. The only campaign so far is `RefusalWar/` ("Refusal War", inspired by the MechWarrior 2 video game, a conflict between Clan Wolf and Clan Jade Falcon); expect more, so keep campaign-specific rules inside the campaign's folder and put only genuinely shared things (like `data/units.json`) at the top level.

## Structure

Every campaign folder (shown for `campaigns/RefusalWar/`) has the same shape:

- `campaigns/RefusalWar/Intro.md` - campaign introduction (currently empty).
- `campaigns/RefusalWar/Keywords.md` - registry of every keyword scenarios can grant or require, one bullet per keyword ID.
- `campaigns/RefusalWar/Scenario_NNN/` - one folder per scenario, zero-padded and numbered sequentially, containing `Setup.md` (fluff, map, forces, special rules) and `Outcome.md` (victory conditions and rewards). `Scenario_000` is the "Trial of Position", a one-off graduation mission whose kill count determines each pilot's starting SP. Later sorties are referred to as "Sortie 001", etc.

## Website

Go is the base for the website, chosen so it can grow into keyword/branch state tracking rather than staying a static site. Run it from the repo root with `go run .` (flags: `-addr :8080`, `-content campaigns`, `-db playthroughs.db`, `-postgres <url>`). It reads the campaign folders on every request (edit a Markdown file and refresh), renders Markdown with `goldmark` and front matter with `yaml.v3`, and embeds its templates and CSS from `internal/site/` (`templates/*.html`, `static/style.css`). Dark mode only, with an industrial-yellow BattleTech look (no theme toggle). The big page titles on the home, campaign and scenario pages (`h1.bt-title`) use the BattleTech old-style font `internal/site/static/bt_oldstyle.ttf`, loaded with `@font-face` in `style.css`. The scenario fluff (the leading blockquote in `Setup.md`) is pulled out of the body and shown as an "incoming transmission" briefing block; a paragraph that opens with a quotation mark becomes a styled pull quote, and a paragraph right after it that opens with an em dash (`— Name, Title`) becomes its attribution line. The scenario's Waypoints section (see the scenario conventions) and Outcome section are collapsed `<details class="fold">` blocks, Waypoints above Outcome; their open/close animation is a small Web Animations script in `layout.html` (the CSS-only `::details-content` approach doesn't work in Firefox, so don't switch back to it); without the script it still toggles. Routes: `/` (campaigns), `/<campaign>/` (intro and scenarios), `/<campaign>/<scenario>/` (Setup then Outcome, plus download buttons for the `.mul` files listed in the `forces` front matter, served from `/<campaign>/<scenario>/forces/<file>`; only listed files are served), `/<campaign>/keywords/`. Campaigns are any folder under `campaigns/` containing `Scenario_NNN/` folders, so a new campaign or scenario that follows the conventions below needs no code changes. `go vet ./...` and `go test ./...` are the checks.

## Checks, CI and Docker

The checks are `gofmt -l .` (must print nothing), `go build ./...`, `go vet ./...`, `staticcheck ./...` (config in `staticcheck.conf`, which turns off ST1005 because a few error strings are visitor-facing sentences; run it with `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...`) and `go test ./...`. `.github/workflows/ci.yml` runs all of them, plus a `docker build`, on pushes to `main` and on pull requests. The `Dockerfile` is a multi-stage build (pure-Go, `CGO_ENABLED=0`) into a distroless nonroot image that bundles `campaigns/` and keeps the SQLite database in the `/data` volume (`-db /data/playthroughs.db`) unless `DATABASE_URL` is set; it listens on 8080. `data/units.json` is not in the image (see `.dockerignore`). Hosting note: DigitalOcean App Platform's disk is ephemeral and would lose a SQLite file on every deploy, so there it must run against Postgres via `DATABASE_URL`. The footer shows the build's short commit hash: the revision `go build` stamps when `.git` is present, else the `COMMIT_HASH` environment variable (on App Platform set it to `${_self.COMMIT_HASH}`, since neither the Go buildpack nor the Dockerfile build sees `.git`), else `dev` (as under `go run`); see `internal/site/commit.go`.

## Playthrough identity (seeds)

Visitors track their own campaign without logging in, using a **seed**: 8 to 32 lowercase letters and digits that the visitor chooses or generates (the Random button makes two English words plus three digits, e.g. `ironfalcon417`). The seed is the only credential, so anyone who knows it can read and change that playthrough; it is stored in an HttpOnly `seed` cookie (one year) and shown back to the visitor in a popup. The server hashes it (`playthroughID` in `seed.go`) into the opaque key used in the database (`internal/site/store.go`); the seed itself is never stored in the database. The store speaks SQLite (pure-Go `modernc.org/sqlite`, file set by `-db`, git-ignored; the default for local runs) or PostgreSQL (pure-Go `pgx`): the `-postgres` flag defaults to `$DATABASE_URL`, and when that is non-empty it is used instead of `-db`. Queries are written once with `?` placeholders and rebound for Postgres by `Store.q`; keep SQL to what both accept. Postgres is for hosts without a persistent disk (DigitalOcean App Platform with its dev database). `TestStorePostgres` runs only when `TEST_DATABASE_URL` is set (CI sets it with a Postgres service container); locally, e.g. `docker run -d -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=bt -p 55432:5432 postgres:17-alpine` then `TEST_DATABASE_URL=postgres://postgres:pw@localhost:55432/bt?sslmode=disable go test ./...`. In code and the database a tracked run is a "playthrough", to avoid clashing with the `campaigns/` content folders.

A new seed continues to a second popup step asking for the playthrough's **MekBay hangar link** (`https://mekbay.com/?instance=<uuid>&sel=<uuid>`, parsed and validated in `setup.go`; `sel` is optional) and the number of **human players** (1 to 4). Once a playthrough has both, the header shows a "Your hangar" link to the hangar. Seed and setup endpoints are `POST /api/seed` and `POST /api/campaign` (same-origin only); the popup logic is `internal/site/static/seed.js`. Keyword and scenario-progress tracking build on this but are not implemented yet.

## Long-term direction

These files are meant to eventually drive a campaign website: scenario pages with fluff images, tracking of scenario forks/jumps (branching between scenarios), and per-playthrough state via KEYWORDS. Keywords are tracked by the campaign as a whole, not by individual pilots, copying how BattleTech: Aces (Scouring Sands) tracks them. Only a simple read-only site exists so far (see Website above); keyword and branch tracking are not built yet, so don't build them unprompted. When adding or reformatting data keep it both machine-parsable and human-readable/writable: consistent headings and names, plain Markdown/XML/JSON, no ad-hoc prose where a structured field would do (e.g. scenario IDs, branch targets, keywords granted or required). Prefer stable identifiers over free-text references.

## Scenario file conventions

Follow the layout in `Scenario_000/Setup.md` and `Scenario_000/Outcome.md` when adding scenarios:

- Both files start with YAML front matter holding the machine-readable fields; the Markdown body below it is the human-readable write-up. The folder name lowercased (`Scenario_000` -> `scenario_000`) is the scenario `id`, and all cross-references (`next`, branch targets) use IDs, never titles.
  - `Setup.md` front matter: `id`, `title`, `planet` (the planet the scenario takes place on, e.g. `Strana Mechty` for Scenario 000; every scenario has one), `map`, `forces` (maps `opfor1`, `opfor2`... to the `.mul` files beside it), `readout` (optional list of `Label: value` lines, kept in order, drawn as a translucent technical readout over the left of the first image, and below it on narrow pages; used for planet data), and `images` (list of paths in the folder's `images/`, e.g. `images/strana_mechty.png`; each is shown as a wide fluff-image banner under the scenario title, cropped to the top, so put the subject in the upper part of the picture; empty until used).
  - `Outcome.md` front matter: `id`, `default_next`, and, only when a scenario actually branches or changes state, `outcomes`, a list of `{when, grants, next}`. Scenario 000 has none: it bootstraps the campaign's starting parameters (starting SP and pilot) rather than granting keywords. `when` is a plain condition over `kills` and `pilot_dead` for now (`kills >= 1`, `pilot_dead or kills == 0`); keep it simple and settle the syntax when a second scenario needs more. `grants` and any required keywords are IDs from `campaigns/RefusalWar/Keywords.md`; add new keywords there before using them.
- Deployment: every unit eventually gets an initial hex position (or is marked off-map with custom rules). Play uses standard two-mapsheet neoprene battlemats with labeled hexes. Hexes are written as four digits, `XXYY` (column then row, e.g. `2113`), as in `Scenario_001`; any other position format is still undecided, so leave deployment positions as `TBD` and don't invent coordinates or a schema until the user supplies them.
- `Setup.md`: `# Scenario NNN: <Title>`, a blockquote of fluff text (if it isn't written yet, leave the placeholder rather than inventing lore). Fluff is a mission briefing: an in-world commander speaking directly to the player in second person, formal and terse, in the style of the MechWarrior 2 briefings (see `Scenario_000/Setup.md`). Aim for less is more: show, don't tell, with a slightly alien yet familiar tone (Hidetaka Miyazaki-style lore, Dune), keep it to a few lines, and don't restate the rules that the sections below cover, then `## Overview`, `## Map`, `## Forces` (each force group, `### Player Forces` and `### OpFor N`, has a `**Deployment:**` line; the OpFor groups are bullet lists written as `Variant (gunnery/piloting)`, e.g. `Timber Wolf H (3/4)`, with the mech name hyperlinked to MekBay as `https://mekbay.com/?gs=cbt&shareUnit=BM<IS-name>_<Variant>&tab=Sheet`; the unit ID is not always obvious: the chassis name has no spaces, the variant follows an underscore, and a chassis with no named variant takes no suffix. Some chassis use the Inner Sphere name (Mist Lynx is `BMKoshi_E`, Kit Fox is `BMUller_J`) while others don't (`BMMadCat_H` for Timber Wolf H, `BMLoki_Prime`, `BMGrizzly`). Ask the user for the working URL rather than guessing a new one) `## Special Rules`, and, when the scenario uses waypoints, `## Waypoints` last. Waypoints are a core mechanic, like the back-of-book waypoints in BattleTech: Aces (Scouring Sands): you only read one when the game calls for it. Each is a `### Waypoint X` heading (any `### ` name works) with its rules text beneath it; text between `## Waypoints` and the first `### ` is dropped. Where they are placed, and when they are revealed, belongs in `## Map` and `## Special Rules`. The site pulls the section out of `Setup.md` and shows each waypoint redacted (its text blacked out line by line, with a Reveal button that wipes the bars away; without JavaScript they are simply readable), inside the collapsed Waypoints block.
- `Outcome.md`: `# Scenario NNN: <Title> - Outcome` with `## Victory & Rewards`. Rewards are in SP (the campaign's pilot-advancement points). The kills-to-SP table is specific to Scenario 000's graduation mission; don't assume later scenarios use it.
- Campaign rules visible so far: pilots are named and persistent; a pilot who dies or fails to score a kill in the graduation mission is permanently removed and replaced by a new named pilot with 0 SP for Sortie 001; Clan honor rules such as zellbrigen apply and violations have mechanical consequences.

## Force files (.mul)

Each scenario folder also holds `OpFor1.mul` and `OpFor2.mul`: MegaMek's XML force format (MekBay exports and imports it), one `<entity>` per mech with its `<pilot>` skills and `<Game id>`. Prefer a real MekBay export over hand-writing. When hand-writing, `chassis` and `model` must match MegaMek's database. A mech with two names uses `chassis="<Inner Sphere name> (<Clan name>)"`, e.g. `Koshi (Mist Lynx)` or `Mad Cat (Timber Wolf)`; a single-name mech such as the Grizzly has a plain chassis and an empty `model`. Deployment attributes, `externalId` and `quirks` can be omitted.

## Working notes

- Mech names and variants are canon BattleTech Clan designs (e.g. Mist Lynx, Timber Wolf, Shadow Cat, Loki); keep to real variant names and Clan terminology (touman, zellbrigen, Trial, etc.).
- For mech data, the authoritative sources are the Master Unit List (`https://masterunitlist.battletech.com/units/<chassis>-<variant>`, e.g. `shadow-cat-a`) and MekBay, not Sarna. The MUL site is behind a Cloudflare bot challenge and returns 403 to automated fetches.
- `data/units.json` is a vendored copy of MekBay's unit catalog, downloaded from `https://db.mekbay.com/units.json` on 2026-10-12 (~27 MB; MekBay builds it from MegaMek's `mm-data`). To refresh it, re-download that URL over the file (e.g. `curl --compressed -o data/units.json https://db.mekbay.com/units.json`). Search it with Grep/Python rather than reading it whole. Each entry's `chassis` and `model` are exactly what `.mul` files need, and its `name` field is the `shareUnit` ID for MekBay links (e.g. `BMMadCat_H`). MekBay's source is at `../mekbay`.
- Maps referenced are official BattleTech battlemats (e.g. "Circles of Equals").
