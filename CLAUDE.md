# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A repo of custom tabletop BattleTech campaigns, one per folder under `campaigns/`, mostly Markdown. A Go web server turns the campaigns into a website; there is no lint or test tooling. The only campaign so far is `RefusalWar/` ("Refusal War", inspired by the MechWarrior 2 video game, a conflict between Clan Wolf and Clan Jade Falcon); expect more, so keep campaign-specific rules inside the campaign's folder and put only genuinely shared things (like `data/units.json`) at the top level.

## Structure

Every campaign folder (shown for `campaigns/RefusalWar/`) has the same shape:

- `campaigns/RefusalWar/Intro.md` - campaign introduction (currently just front matter). Its YAML front matter holds campaign-level fields: `min_players` and `max_players` (how many players the campaign supports; Refusal War is 1 to 2), shown under the campaign's name on the home page's campaign list. Leave `max_players` out to show nothing. It also holds the campaign's starting instructions: `starting_named_pilots` (how many named pilots must be named before scenarios deploy; Refusal War is 2; see Named pilots under Playthrough identity), `starting_pilot_sp` (the SP each of them allocates; 150) `starting_bv` (the most BV the starting hangar may total; Refusal War is 10000) and `starting_min_mechs` (the fewest mechs it may hold; Refusal War is 5). `starting_warchest` (the SP a started campaign's warchest begins with; Refusal War is 5000; stored per run in `campaign_runs.warchest`, set by `StartRunWithPilots`, listed in the start rules and shown as the Funds box in the Manage page's Warchest section; a run started before the column existed reads 0). These are listed as bullets on an unstarted campaign's page (the site doesn't model Scale, it just says 10,000 BV). **The starting hangar is checked** by `checkStartingHangar` (`startcheck.go`): units are looked up in the catalog, BV is each unit's *base* BV (what a standard 4/5 pilot gives it; pilot skill never matters), only catalog type `Mek` counts as a mech (a tank adds BV but isn't a mech), and a unit missing from the catalog is a problem since its BV is unknown. The wizard asks for the check as soon as a pasted link has a valid shape (`GET /api/campaign/hangar-check?campaign=&hangar=`, which reads the force from MekBay, never writes, and needs a seed with a named account): it waits 350 ms after typing, shows a spinner and "Reading your hangar..." meanwhile, ignores a reply for a link that has since changed, then shows a summary (mechs, BV of the limit), the units counted and every problem, and keeps Start campaign disabled until the hangar passes. Because the player fixes the hangar in MekBay without changing the link, a refresh icon embedded on the right of the link box re-reads it at once (disabled until the link has a valid shape, and spinning while it reads), and returning to the tab while the hangar is failing re-checks it automatically; each read carries a sequence number so an older reply can never overwrite a newer one, **a refresh of an unchanged link keeps the finished result on screen** (a small "Updating" note with a spinner appears beside the summary, the new data replaces it only when it arrives, identical data repaints nothing at all, and a failed refresh keeps the old data with a "Couldn't refresh" note, so Start follows the committed data and the server re-checks on submit) while a *changed* link clears it, since the old result would describe a different hangar, and the reason a hangar fails is shown once (in the status area, and as the disabled button's tooltip) rather than repeated in the hint line. `POST /api/campaign/start` runs the same check on the server before creating anything (400 with the problems, 502 if MekBay can't be read); changing the hangar link of an already started campaign is not checked again.
- `campaigns/RefusalWar/Keywords.md` - registry of every keyword scenarios can grant or require, one bullet per keyword ID.
- `campaigns/RefusalWar/Scenario_NNN/` - one folder per scenario, zero-padded and numbered sequentially, containing `Setup.md` (fluff, map, forces, special rules) and `Outcome.md` (victory conditions and rewards). `Scenario_000` is the "Trial of Position", a one-off graduation mission whose kill count determines each pilot's starting SP. Later sorties are referred to as "Sortie 001", etc.

## Website

Go is the base for the website, chosen so it can grow into keyword/branch state tracking rather than staying a static site. Run it from the repo root with `go run .` (flags: `-addr :8080`, which defaults to `localhost:8080` under `go run` (detected by the `go-build` temp path of the binary) so Windows Firewall doesn't prompt for every rebuilt binary; `-content campaigns`, `-db playthroughs.db`, `-postgres <url>`). It reads the campaign folders on every request (edit a Markdown file and refresh), renders Markdown with `goldmark` and front matter with `yaml.v3`, and embeds its templates and CSS from `internal/site/` (`templates/*.html`, `static/style.css`). Dark mode only, with an industrial-yellow BattleTech look (no theme toggle). Every page's big title (`h1.bt-title`) use the BattleTech old-style font `internal/site/static/bt_oldstyle.ttf`, loaded with `@font-face` in `style.css`. The scenario fluff (the leading blockquote in `Setup.md`) is pulled out of the body and shown as an "incoming transmission" briefing block; a paragraph that opens with a quotation mark becomes a styled pull quote, and a paragraph right after it that opens with an em dash (`— Name, Title`) becomes its attribution line. The scenario's Waypoints section (see the scenario conventions) and Outcome section are collapsed `<details class="fold">` blocks, Waypoints above Outcome, (a collapsed Force files block with the `.mul` downloads used to sit between them; it is commented out of `scenario.html` for now with a Go template comment, and the `/<campaign>/<scenario>/forces/<file>` route still works, so restoring it is just removing the comment); their open/close animation is a small Web Animations script in `layout.html` (the CSS-only `::details-content` approach doesn't work in Firefox, so don't switch back to it); without the script it still toggles. Routes: `/` (campaigns), `/<campaign>/` (intro and scenarios), `/<campaign>/<scenario>/` (Setup then Outcome, plus download buttons for the `.mul` files listed in the `forces` front matter, served from `/<campaign>/<scenario>/forces/<file>`; only listed files are served), `/<campaign>/keywords/`. Campaigns are any folder under `campaigns/` containing `Scenario_NNN/` folders, so a new campaign or scenario that follows the conventions below needs no code changes. `go vet ./...` and `go test ./...` are the checks.

## Checks, CI and Docker

The checks are `gofmt -l .` (must print nothing), `go build ./...`, `go vet ./...`, `staticcheck ./...` (config in `staticcheck.conf`, which turns off ST1005 because a few error strings are visitor-facing sentences; run it with `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...`) and `go test ./...`. `.github/workflows/ci.yml` runs all of them, plus a `docker build`, on pushes to `main` and on pull requests. The `Dockerfile` is a multi-stage build (pure-Go, `CGO_ENABLED=0`) into a distroless nonroot image that bundles `campaigns/` and keeps the SQLite database in the `/data` volume (`-db /data/playthroughs.db`) unless `DATABASE_URL` is set; it listens on 8080. `data/units.json` is not in the image (see `.dockerignore`). Hosting note: DigitalOcean App Platform's disk is ephemeral and would lose a SQLite file on every deploy, so there it must run against Postgres via `DATABASE_URL`. The footer shows the build's short commit hash: the revision `go build` stamps when `.git` is present, else the `COMMIT_HASH` environment variable (on App Platform set it to `${_self.COMMIT_HASH}`, since neither the Go buildpack nor the Dockerfile build sees `.git`), else `dev` (as under `go run`); see `internal/site/commit.go`.

## Playthrough identity (seeds)

Visitors track their own campaign without logging in, using a **seed**: 8 to 32 lowercase letters and digits that the visitor chooses or generates (the Random button makes two English words plus three digits, e.g. `ironfalcon417`). The seed is the only credential, so anyone who knows it can read and change that playthrough; it is stored in an HttpOnly `seed` cookie (one year) and shown back to the visitor in a popup. The server hashes it (`playthroughID` in `seed.go`) into the opaque key used in the database (`internal/site/store.go`); the seed itself is never stored in the database. The store speaks SQLite (pure-Go `modernc.org/sqlite`, file set by `-db`, git-ignored; the default for local runs) or PostgreSQL (pure-Go `pgx`): the `-postgres` flag defaults to `$DATABASE_URL`, and when that is non-empty it is used instead of `-db`. Queries are written once with `?` placeholders and rebound for Postgres by `Store.q`; keep SQL to what both accept. Postgres is for hosts without a persistent disk (DigitalOcean App Platform with its dev database). `TestStorePostgres` runs only when `TEST_DATABASE_URL` is set (CI sets it with a Postgres service container); locally, e.g. `docker run -d -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=bt -p 55432:5432 postgres:17-alpine` then `TEST_DATABASE_URL=postgres://postgres:pw@localhost:55432/bt?sslmode=disable go test ./...`. In code and the database a tracked run is a "playthrough", to avoid clashing with the `campaigns/` content folders.

A seed is an **account**: a new seed continues to a second popup step asking for the **account name** (`Playthrough.AccountName`, whatever the player likes to call it; the column is still `playthroughs.company_name` from when it was a company; the name shown in the header chip), and each campaign's force has its own **force name** (see below), because campaigns can be thematically different forces, not necessarily a "company". The account name is validated by `parseCompanyName` in `setup.go`; a seed counts as set up once it has one). An account then runs **campaigns**, each with its own state: a campaign is *started* from its own page (the Start button on `/<campaign>/` opens a **wizard**, see Named pilots below), whose last step asks for **that campaign's MekBay hangar link** (any MekBay link will do: `parseHangar` in `setup.go`, mirrored by `canonicalHangar` in `campaign.js`, keeps only the force's instance ID and reduces it to `https://mekbay.com/?instance=<uuid>`, so `&sel=` (the selected unit, which we have no use for, even a garbled one), `&operation=`, tracking parameters and fragments are dropped, and a list of forces `<mine>,enemy:<theirs>` gives the first friendly one; only https on mekbay.com/www.mekbay.com is accepted, and an operation link gets a message saying to paste the hangar link instead; the wizard rewrites the link box to the plain link as soon as a pasted link is recognised; `campaign_runs` no longer has a `hangar_sel` column in its `CREATE`, existing databases keep the unused column, which defaults to empty so inserts without it work) and records a `CampaignRun` (table `campaign_runs`, one row per seed and campaign slug; the row existing means started). Starting again for a started campaign just changes its hangar link. While a campaign's pages are open the header shows a "Your hangar" link to that campaign's hangar. Endpoints (same-origin only): `POST /api/seed`, `POST /api/account` (name plus the players' optional MekBay user IDs) and `POST /api/campaign/start`; the popup logic is `internal/site/static/seed.js` and the campaign page's is `campaign.js`. There is deliberately no human player count (it used to be asked for but nothing used it). **MekBay accounts: real ones for the players, synthesized ones for the site** (`accounts.go`). MekBay identifiers are implicit (any UUID a client presents is an account that owns what it saves, and only the owner may change a force). Each physical player has their own **MekBay user ID, Player 1 to 4**, saved in the Account details dialog (`uid_p1`..`uid_p4`, `clear_uid_p1`..; table `player_accounts`; `Store.SetPlayerAccount/PlayerUIDs`; validated as UUIDs, two players can't share one, all validated before any is saved, a blank field keeps the saved ID, a ticked Forget box forgets it). They are secrets: server-side only, never rendered back (pages get only `Playthrough.PlayerIDs`/`PlayerIDsJSON` booleans) and never logged. They exist so that each player's force in the multiplayer lobby operation a Deploy will build is **owned by that player's own account**. The site's own bookkeeping is owned by **synthesized accounts**: `MekBayUID(seed, slot)` is a salted SHA-256 of the seed laid out as a v4 UUID, a stable 1:1 projection of seed to site-managed ID, one for the **hangar** (`SlotHangar`, derivation salt `p1` for historical reasons so existing copies keep working) and one for the **OpFor** (`SlotOpFor`); recomputed from the seed whenever needed, never stored or logged. **Starting a campaign needs the players' IDs**: the start wizard's first step (only when the campaign allows a range of players) asks how many players, the same [1][2][3][4] picker as the Deploy wizard up to the campaign's maximum, offering only counts whose Players 1 to N have an ID saved (`parseStartingPlayers`, `playerIDsProblem`; `POST /api/campaign/start` needs `players`, 400 otherwise). The count is saved on the run (`campaign_runs.players`, `CampaignRun.Players`) and is only the Deploy wizard's **default** (`data-default-players`; a deploy can still override it, and a default whose IDs were since forgotten steps down to what the IDs cover). The Manage page's **Overview** section (it was Warchest) shows the Funds box and a **Default players** picker (`static/overview.js`, `POST /api/campaign/players`, `Store.SetRunPlayers`, same rules). **Lobby planner** (`lobby.go`, no MekBay calls yet): `buildLobbyPlan` turns a validated deployment plan into who owns what (each player's force: their own account; the OpFor's forces: the synthesized OpFor account; the hangar: the synthesized hangar account), refusing missing or colliding IDs (a player may never own the OpFor); `POST /api/deploy/plan` builds it as a dry run (it needs Players 1 to N's IDs, 400 otherwise) and returns `lobby` (name, `player`/`site`, unit count; never an account). `TestMekBayUID`, `TestPlayerAccounts`, `TestPlayersMekBayIDsInTheCompanySettings`, `TestBuildLobbyPlan`, `TestStartNeedsPlayersAndTheirIDs`, `TestOverviewDefaultPlayers`. **The hangar is cloned**: `campaign_runs.hangar_url`/`hangar_instance` are then the site's copy and the new `source_url` column is the player's link (`CampaignRun.Owned()` is true when it is set); the copy is hidden from normal play (no 'Your hangar' header link), but for advanced users the Manage page's Danger zone shows its instance ID with an open-in-MekBay link and the synthesized account ID that owns it (`Page.SiteAccountUID`; it is derived from the seed the visitor already holds, so it reveals nothing new, and it appears nowhere else; MekBay shows the force read-only); the Re-import hangar dialog shows `SourceURL`, and saving it clones that link again into a fresh, clean copy, losing repairs, purchases and crews). Repairs, rearms, purchases and (later) deploys all act on the site's copy with the derived account; a run from before this change has no `source_url`, so those endpoints answer 409 and the buttons are disabled until the hangar is imported again. The old `owner_uid` column is unused. `TestMekBayUID`, `TestCloneForceIsPristine`, `TestStartClonesTheHangar`. Keyword and scenario-progress tracking build on this but are not implemented yet.

**Force names.** Each campaign run has its own **force name** (`campaign_runs.force_name`, `CampaignRun.ForceName`; `ForceLabel()` falls back to "Your force" for a run from before forces were named), chosen in the start wizard's first step (a random BattleTech-sounding placeholder from `static/pilotnames.js` `PilotNames.randomForce`; `POST /api/campaign/start` needs `force_name`, validated by `parseForceName`, 1 to 40 characters in the same style as an account name: `parseName`) and renamed later in place on the Manage page: the force name is the **Overview section's heading**, with a pencil that turns it into a text box (`static/overview.js`: Enter or Save keeps it, Escape or Cancel doesn't; `POST /api/campaign/force-name`, `Store.SetForceName`). The campaign page's started heading, the Manage page's hangar and delete texts use it; the header chip shows the account name. `TestForceNames`, `TestStartNeedsAForceNameAndItCanBeRenamed`.

**Named pilots** follow BattleTech: Hot Spots - Draconis Reach, "Named Pilots" (pp. 34-35; the book is at `C:\Users\david\iCloudDrive\Documents\Battletech\Books\`, too big for the Read tool, so extract pages with `pdftotext -f 34 -l 37` and note the PDF's physical page is 2 higher than the printed number). Only named pilots improve Gunnery/Piloting, use Edge and earn Edge abilities; which abilities a pilot has chosen is tracked (see Edge abilities below). A pilot tracks one number, **total SP earned** (`named_pilots.sp_total`), and the SP allocated so far in four columns (Gunnery, Piloting, Edge tokens, Edge abilities); **unallocated SP is the total minus the columns' sum** (`NamedPilot.Unallocated`), never stored separately. A new pilot's starting SP is all allocated; later SP is earned into the total (`Store.EarnSP`, `POST /api/pilots/earn`) and spent with `Store.AllocateSP` (`POST /api/pilots/allocate`, which adds to the columns and refuses more than is unallocated, checked in the same SQL statement). The older direct `POST /api/pilots/sp` (`AwardSP`) raises total and columns together and is no longer used by the UI. A database from before the total existed gets `sp_total` backfilled to the columns' sum (`Store.init`, `TestMigrateSPTotal`). `pilot.go` holds the book's Named Pilot Improvement Table as ladders (cumulative SP to reach a level), and derives a pilot's levels; `TestKirbyExample` replays the book's worked example. **Handicap is deliberately not tracked** (the book gives each step a handicap that balances opposing forces; this campaign doesn't use it), so don't add it back. A new pilot is a 4/5 pilot with 1 Edge token and 0 SP. At most four living named pilots per command (`maxNamedPilots`); a pilot killed in action (shown as "Killed in Action" everywhere; the column and code say `fallen`) keeps their row but frees a place, can't earn SP and leaves the active list and the overview. Tables/queries: `named_pilots`, `Store.Pilots/AddPilot/EarnSP/AllocateSP/MarkFallen`; endpoints `POST /api/pilots`, `/api/pilots/sp`, `/api/pilots/fallen` (`pilots.go`), and the Named pilots panel on the Manage page (`pilots.js`): each pilot is a card with the wizard's yellow-number stat boxes, a **Manage SP** button and a **More** drop-down (a native `<details>`, closed by an outside click or Escape) whose first item is "Mark as killed in action" (`POST /api/pilots/fallen`); room for more items later. A pilot killed in action isn't removed: their card moves to a **Memorial** section below the active pilots (no buttons): the portrait goes grayscale with a red rotated **K.I.A.** stamp laid over it (`.kia-stamp`), the stats and ability chips are dimmed, and the "Killed in Action" badge stays vivid red, and they stay revivable or deletable under Advanced Management. Manage SP opens a level-up dialog (`#sp-dialog`) with the same sliders, number boxes and stat boxes as the wizard (`static/allocator.js`, the shared `SPAllocator`, which the wizard also uses): the sliders spend only the pilot's unallocated SP (the sliders and number boxes show each column's whole total with what the pilot already has as their minimum, and reach up from there by the unallocated SP; a row's number turns yellow while it has a pending change; the boxes preview the new levels), Apply saves, and an "Add earned SP" box (which asks for confirmation) *stages* SP for the pilot's total (SP is entered by hand because scenario rewards aren't automated yet): it raises what can be spent in the dialog, shows "+N SP earned. Not saved until you press Apply" with a Clear link, and nothing is saved until Apply, which posts the earned amount and the allocation together to `POST /api/pilots/allocate` (`earned` field, `Store.ApplySP`, one atomic statement); closing the dialog discards the staged SP. **Each campaign sets its starting instructions in `Intro.md` front matter**: `starting_named_pilots` (Refusal War: 2) and `starting_pilot_sp` (Refusal War: 150, the SP each starting pilot allocates; the book's p. 17 gives 150 too). **Starting a campaign is a wizard** (`#start-wizard`, `campaign.js`): a step naming the force, a step asking how many players (only when the campaign allows a range), one step per starting pilot (a name plus an allocator that splits the pilot's starting SP over the four columns, with four labeled boxes (Gunnery, Piloting, Edge tokens, Edge abilities, each a big yellow number with a big centred level with a tiny, thin "-> next level" (a small drawn arrow and the next level in bold muted gray, like the caption) at its lower right, "SP/needed SP" beneath it and a thin yellow progress bar for how far along that is; at the top of the ladder it says "max" with a full bar and no next level) beside the name showing the levels the allocation reaches live, computed from the same ladders the server uses, passed to the page as JSON in `data-ladders`; every SP must be allocated before moving on, and the allocator refuses to over-allocate; the sliders and the number boxes' arrows both step by 10 SP, and Next stays disabled, with a hint line saying what is missing, until the step is valid), then a step for the hangar link, with a step counter and progress bar at the bottom. It posts everything to `POST /api/campaign/start` in one go (fields `pilot<i>_name`, `pilot<i>_gunnery`, `_piloting`, `_edge_tokens`, `_edge_abilities`); `parseStartingPilots` validates it (exactly the campaign's pilot count, unique names, each allocating exactly `starting_pilot_sp`) and `Store.StartRunWithPilots` creates the run and the pilots in one transaction, refusing a second start (`ErrAlreadyStarted`). Posting again for a started campaign only changes its hangar link (the small `#run-dialog`). The campaign's pilot count is a *starting* requirement only: pilots can die mid-campaign, so deploying never checks how many are alive, and pilots are added later with the **Recruit New Pilot** button under the active pilots on the Manage page (above the Memorial), which opens a one-step dialog (`#recruit-dialog`, `pilots.js`): a random portrait no living pilot has (click it for the picker), a name, a rank, and the campaign's `starting_pilot_sp` (150 in Refusal War) to allocate with the same sliders, number boxes and live stat boxes as the start wizard (`SPAllocator`); spending all of it is optional, and whatever is left stays unallocated for Manage SP (a campaign with no starting SP shows no sliders). It posts `POST /api/pilots` with the allocation in the `gunnery`/`piloting`/`edge_tokens`/`edge_abilities` fields (refused above the starting SP; `Store.AddPilotWithRank` takes the allocation and a total, which is the starting SP; names are unique per campaign ignoring case, a command holds `maxNamedPilots` living pilots, so the button is disabled with a reason when it is full and comes back when a pilot is Killed in Action). The wizard script has no JS test runner; `TestScriptsParse` only syntax-checks it, so after changing it drive it with jsdom against a running server (that is how it was verified). The book's 100-SP-per-track cap is deliberately not enforced because campaigns set their own rewards (Scenario 000 pays 150 to 900); starting SP; the MVP and combat-pay rules are not built yet (assigning pilots to hangar units is in the Deploy popup, see MekBay hangar integration).

**Starting Edge abilities and placeholder names.** In the start wizard a pilot whose allocation reaches an Edge abilities level must choose that many abilities before Next works (the same combo boxes and ability cards as the Manage picker, `#wiz-body .wiz-abilities`, `AbilityCard`); moving SP out of the Edge abilities column until the level drops removes the choices that no longer fit (last first). `parseStartingPilots` requires exactly that many distinct, known `pilot<i>_ability` values and `StartRunWithPilots` stores them as the pilot's learned abilities. The name boxes' placeholder is drawn at random from `static/pilotnames.js` (`PilotNames.random(group)`), following the portrait's gender group (Male/Female draw from their own names plus neutral ones; Generic and Special from all) and changing when the portrait does (in the wizard and the Recruit dialog). `TestStartChoosesEdgeAbilities`; driven with jsdom.

**Edge abilities.** The twelve Edge abilities of Hot Spots: Draconis Reach (printed p. 166, physical page 168 of the PDF; text kept as the book prints it, Alpha Strike rule first with the Total Warfare rule in parentheses) are the catalog in `abilities.go` (`edgeAbilities`: stable ID, name, category, text; Attack, Indirect Fire, Defense, Heat, Melee, Movement). The book says that when a named pilot reaches a new Edge abilities level they choose one, permanently (p. 36, step 4); this site only records the choice, it doesn't play the abilities. A pilot may hold as many abilities as their Edge abilities level, so **pending = level - learned** (`NamedPilot.PendingAbilities`, never negative). Whenever it is above zero the pilot's card on the Manage page shows a yellow "Choose a new Edge ability" / "Choose N new Edge abilities" button beside an "Edge abilities" row of chips for the ones already learned (hovering or keyboard-focusing a chip shows the same ability card as the picker in a floating panel anchored under it, `AbilityCard.attach` in the shared `static/abilitycard.js`, like the mech icon hover card on the overview; there is no native `title`). It opens a picker (`#skill-dialog`, `pilots.js`) with one combo box per pending ability, grouped by category and listing only abilities the pilot doesn't have; one chosen in another box is greyed out, and the chosen ability shows as a card under its box (`AbilityCard.fill` in `abilitycard.js`, shared with the Deploy popup; it also owns the catalog, `splitTrigger` and the floating panel, which is a popover so it can sit on top of another popover or a dialog; `pilots.js` and `mekbay.js` load it after `abilitycard.js`): its name, a pill in its category's colour, and the rule with the **trigger in bold** as the book prints it (everything up to the first colon outside parentheses, `splitTrigger` in `abilitycard.js`, since Protector's trigger contains a "(TW: 1 hex)" aside) and each "(TW: ...)" aside dimmed; an empty box shows a dashed placeholder. **Learn** asks for confirmation (the choice is permanent) and posts all the choices together to `POST /api/pilots/abilities` (repeated `ability` fields; `Store.LearnAbilities`, one transaction, which refuses a wrong number of choices, an unknown or already-learned ability, a pilot with nothing pending, and a pilot killed in action). Learned abilities are rows of `pilot_abilities` (pilot, ability ID, order learned), removed with the pilot or campaign. They are permanent like allocated SP: the only undo is **Reset Edge abilities** in Advanced Management (`Store.ResetEdgeAbilities`, `POST /api/pilots/abilities/reset`, after a confirm; it works on killed pilots too, doesn't touch SP, and leaves the pilot owed the choices again). Resetting a pilot's *SP allocation* (the records dialog's other reset, formerly labelled "Reset abilities", now "Reset SP allocation") **also forgets their learned Edge abilities**, since they depended on that SP: so does setting a total below the allocation with the reset agreed (`ResetPilotSP` and `SetPilotTotal` delete the `pilot_abilities` rows in the same transaction; a total at or above the allocation touches nothing), and the confirmations say so when the pilot has any (`TestSPResetForgetsEdgeAbilities`). A memorial card shows the chips read-only, and the records row lists the abilities. `TestEdgeAbilityCatalog`, `abilityStore` and `TestEdgeAbilitiesThroughThePages` cover the server; the picker and the reset were driven with jsdom.

**Pilot portraits.** Each named pilot has a portrait: one of 79 MechWarrior 5 pilot busts (transparent backgrounds) vendored in `internal/site/portraits/` at 192x192 (see `portraits/NOTICE.md`; refresh with `go run gen_portraits.go -src <folder>` from `internal/site`, which lowercases names and rescales), embedded with `go:embed` and served at `GET /portraits/{file}` (`portraits.go`; lowercase PNG names only). `portraits()` groups them Male/Female/Generic/Special from the file names (`male_rank2_3.png`); the list goes to the page as JSON (`data-portraits`). The start wizard gives every starting pilot a random portrait nobody else has, shown beside the name; clicking it opens `static/portraitpicker.js` (`PortraitPicker.open`, shared with the Named pilots panel), a scrollable grid that opens scrolled to the current choice and dims portraits another pilot has. Two living pilots of a campaign never share one (`ErrPortraitTaken`; a fallen pilot frees theirs), enforced by `AddPilot`, `StartRunWithPilots`/`parseStartingPilots` and `SetPilotPortrait` (`POST /api/pilots/portrait`); a pilot added from the panel gets a random free one. The column `named_pilots.portrait` was added with `Store.ensureColumn` (the pattern for adding a column to an existing table); a pilot with none stored (from before portraits) is shown a stable one derived from their ID by `portraitOf`. Fallen pilots show theirs in grayscale and can't change it.

**Overview and Manage pages.** A started campaign's page (`/<campaign>/`) shows only a compressed "Your force" overview: a roster of the living named pilots (portrait, name, SP earned, and the same yellow-number stat boxes as the start wizard for Gunnery, Piloting, Edge tokens and Edge abilities) and a one-line hangar summary in the same card style (up to 8 unit icons, each with a hover card of the unit's details, anchored to the icon, which also gets a yellow border (also on keyboard focus), then the unit count, damaged/destroyed counts and the total base BV; the per-unit list is the Manage page's Mechs section) (`static/force.js`, built by the shared `static/forcesummary.js` (`ForceSummary.build`, which also owns the unit hover card; load it first), fed by `GET /api/campaign/force`, which reads the hangar anonymously from MekBay and sums the base BV of every catalog-known unit; destroyed units still count). **Factions and ranks.** Each campaign names its player force's **faction** in `Intro.md` front matter (`faction: clan`), and the faction decides the cosmetic flavour of its named pilots, starting with their **ranks**. `factions.go` is the registry (`factions` map: ID, name, rank ladder lowest first); Refusal War is `clan`: MechWarrior, Star Commander, Star Captain, Star Colonel, Galaxy Commander, saKhan, Khan (per https://www.sarna.net/wiki/Clan_Military_Structure, which also lists Point Commander, Nova Commander and others we skipped). **Confirmations.** The site never uses the browser's `window.confirm`. `static/confirm.js` provides `Confirm.ask({title, message, confirmLabel, cancelLabel, danger}) -> Promise<boolean>`, a styled modal dialog that stacks on top of any dialog already open (the Advanced Management and Manage SP dialogs call it for Killed in Action, Reset abilities, a total below the allocation, Delete pilot and Add earned SP). `danger` makes the confirm button red and focuses Cancel, so a stray Enter never confirms something destructive; Escape and a backdrop click cancel; text is inserted as text. **Deleting a campaign.** A started campaign's Manage page ends with a red "Danger zone" holding a Delete button (`static/campaigndelete.js`) that opens a confirmation popup; confirming posts `POST /api/campaign/delete` (`deleteCampaign`, same-origin, started campaigns only), which calls `Store.DeleteRun`: one transaction removing that campaign's named pilots, saved MekBay operation IDs and the run. The account and its other campaigns are untouched, and nothing is deleted in MekBay itself (the hangar, OpFors and operations stay in the player's account). The campaign then shows as not started and can be started again. `TestDeleteCampaign` covers it.

Schema changes go through `Store.init` (`store.go`): `CREATE TABLE IF NOT EXISTS` for the current tables, run one statement at a time, after `migrateLegacy` upgrades an older database. The one migration so far (to companies and per-campaign hangars) drops the old single hangar link, player count and all operations but keeps seeds, creation times and owner UIDs, because the single hangar couldn't be attributed to a campaign. `TestMigrateLegacySQLite` and `TestMigrateLegacyPostgres` (the latter only with `TEST_DATABASE_URL`) build an old-format database and check it; add a similar test with any further migration.

## Long-term direction

These files are meant to eventually drive a campaign website: scenario pages with fluff images, tracking of scenario forks/jumps (branching between scenarios), and per-playthrough state via KEYWORDS. Keywords are tracked by the campaign as a whole, not by individual pilots, copying how BattleTech: Aces (Scouring Sands) tracks them. Only a simple read-only site exists so far (see Website above); keyword and branch tracking are not built yet, so don't build them unprompted. When adding or reformatting data keep it both machine-parsable and human-readable/writable: consistent headings and names, plain Markdown/XML/JSON, no ad-hoc prose where a structured field would do (e.g. scenario IDs, branch targets, keywords granted or required). Prefer stable identifiers over free-text references.

## MekBay hangar integration

**Built so far: deploying a force for a scenario.** A scenario page with OpFor files shows a "Deploy your force" section once the playthrough has *started that campaign* (otherwise it points to the campaign page). Its button opens a popup (`mekbay.js`, `#deploy-dialog`) fed by `GET /api/mekbay/hangar`: every unit of the campaign's hangar, read anonymously from MekBay (`MekBayClient.ReadHangar`), with name (Clan name preferred), class, tonnage, role, pilot and skills, Damaged/Destroyed tags and **base BV**: this campaign (a custom Classic BattleTech ruleset in the style of BattleTech: Aces, partly homebrewed) never lets pilot skill change a unit's BV, which matches the book's rule that named pilots' skills don't affect BV and avoids rewarding bad pilots with room under the cap. `adjustedBV` (`units.go`, MekBay's BV 2.0 table) is kept only for the `bv` metadata of the OpFor force we write, which is what MekBay itself would total. The player ticks the units for the mission; a scenario's `bv_limit` front matter (optional, e.g. `bv_limit: 10000` in Scenario 001; absent means no limit) caps the total, checked in the page and again by `deployProblem` (also refuses destroyed and unknown units). Deploying (`POST /api/mekbay/deploy`, needs a hangar the site owns, since MekBay only accepts the owner's writes) goes through `MekBayClient.SyncOperation` (`mekbay.go`), which in order: rearranges the hangar force so the chosen units sit in a group named "Deployed" and every other unit in "Hangar" (`deployGroups` in `deploy.go`; other groups are dissolved, existing Deployed/Hangar groups keep their ID and color, everything else in the force, e.g. damage and C3 networks, is untouched), saves an OpFor force built from the scenario's `.mul` files (one group per file, named "OpFor 1", "OpFor 2"; pilots and skills from the `.mul`; unit IDs from `units_index.json`), and saves an operation named `<Campaign> - Scenario NNN` pairing the hangar (friendly) with the OpFor (enemy). The IDs are stored per seed, campaign and scenario in `mekbay_operations`; deploying again re-sorts the hangar but **keeps the existing OpFor and its damage** unless the popup's "Reset OpFor" box is ticked (`reset_opfor=1`). Without modify mode the popup still lists the hangar but can't deploy and says to add the user ID. **Pilot assignment** is part of the popup (below). `units_index.json` is a slim copy of `data/units.json` (name, chassis, model, BV, tons, weight class, role, type, tech base, icon file name) embedded because the full catalog isn't in the Docker image; it also carries each mech's `engine` (the crippling rule) and `ammo` entries (the rearm breakdown); regenerate it with `go generate ./internal/site` after refreshing `data/units.json` (see Unit names, icons and mech rows). Tests use a fake `MekBay` (`WithMekBay`) and a fake WebSocket server; `TestMekBayLive` hits the real mekbay.com and only runs when `MEKBAY_LIVE_UID` and `MEKBAY_LIVE_INSTANCE` are set (it reads the hangar and creates an OpFor force and operation in that account, but leaves the hangar's groups alone). Not built yet: reading damage after a sortie (the start/end snapshots below) and splitting `enemy:` IDs out of a pasted multi-force link.

**Hover cards on the campaign overview.** Hovering a pilot in "Your force" shows the same pilot card as the Deploy popup (after half a second, interactive, with the Edge ability cards): the card's content now lives in the shared `static/pilotcard.js` (`PilotCard.build` / `PilotCard.attach`, used by `mekbay.js` and by `static/roster.js`, which attaches it to each `.roster-pilot[data-name]` row from the overview's `data-pilots` and `data-abilities`; the rows are focusable, so the keyboard gets it too, shown at once on focus). **Campaign log, branching and availability.** Each started campaign keeps a log of its completed scenarios (`scenario_completions`: playthrough, campaign, scenario slug, time; removed with the campaign by `DeleteRun`; `progress.go`, `Store.Completions/SetScenarioCompleted`). A scenario lists which scenarios it may branch to in its `Outcome.md` front matter, `branches: [scenario_001, ...]` (IDs, lowercased); **omitted, it leads to its `default_next`, or else to the next scenario number** (`resolveBranches`, `Scenario.Branches`), and an explicit empty list ends that path, so scenarios can be arranged into pseudo-branching paths. **Available** scenarios (`Campaign.Available`) are the campaign's first (000), every completed one and every branch of a completed one; the campaign page and the scenario page's breadcrumb menu list only those, so locked scenarios stay hidden (an unstarted campaign shows just 000). **Provided forces (scenario-unique available mechs).** A scenario's `Setup.md` front matter can list `provided_units` (MekBay unit IDs) to replace the player's hangar with a fixed pool of mechs for that scenario, for story reasons (`provided.go`, `Scenario.ProvidedUnits`, `Scenario.provides()`). Scenario 000, the Trial of Position, offers `BMBlackHawk_Prime` (Nova Prime), `BMRyoken_Prime` (Stormcrow Prime), `BMShadowCat_Prime` (Shadow Cat Prime), `BMPouncer_Prime` (Pouncer Prime) and `BMGrendel_Prime` (shown by its Clan name, Mongrel Prime): lighter, evenly matched machines on purpose, because the trial is back-to-back 1v1s and a cadet should expect one kill, rarely two and very rarely three (the Mad Dog and Timber Wolf Primes made it too easy). Such a force is **ephemeral**: `providedForce` builds a `HangarForce` of new, uncrewed units (IDs `provided-<lowercased unit ID>`) so the Deploy popup (`hangarJSON`, and `Page.DeployJSON`, which embeds it with no MekBay read), the old single-player deploy and `POST /api/deploy/plan` (all through `Server.scenarioHangar`) work on it unchanged: named pilots can be assigned, the scenario's BV limit and the player count apply, and each mech can be taken once. It is never read from or written to MekBay, never cached as the hangar and never changes it; the hangar JSON carries `provided: true`, which shows the popup's note (`#deploy-provided`). A scenario with no `provided_units` uses the hangar as before, and one with provided units has no **Manage force** button in its Deploy section (there is no hangar to manage for it). **Scenario rules**: front matter `unit_limit: N` (the most mechs the players may take in all, shared by every player, like the BV limit) and `pilots_required: true` (every mech taken needs a named pilot) apply to any scenario; Scenario 000 sets both (two mechs, a pilot on each) and no `bv_limit`. They are enforced by `Scenario.rulesProblem` in `POST /api/deploy/plan` and the old single-player deploy, and in the popup (`data-unit-limit`, `data-pilots-required`): the meter counts mechs against the limit instead of saying '(no limit)', the mechs not yet taken are disabled once the limit is reached, a `#deploy-rules` line states the rules and what is still missing, and Next/Deploy wait until every mech taken has a pilot. `TestScenarioRules`, `TestScenario000EnforcesItsRules`. `TestProvidedForce`, `TestScenario000ProvidesItsOwnMechs` (which also checks every scenario's provided units are catalog mechs), `TestProvidedScenarioDeploy`.

**The Deploy wizard (several players).** A campaign's `min_players` and `max_players` (Refusal War: 1 to 2; at most 4, `playerRange`) say how many players a sortie can be deployed with. The force's mechs (its MekBay hangar) and named pilots are **one shared pool** that the players divide, so the Deploy popup (`static/mekbay.js`) is a wizard: with one player (or a campaign that allows only one) it is a single step as before; with a range, the first step has a **Players** picker (a segmented control from the minimum to the maximum, starting at the minimum), and choosing more than one makes it a wizard of **one step per player plus a review**, with a **progress bar and "Step n of m" at the bottom**, Back and Next, and each step titled "Player k of N". A player takes mechs by ticking them and assigns pilots to those mechs (a pilot slot only works on a mech the player has taken); **a later step is offered only what the others left**: a mech another player took is not listed, and a pilot another player assigned is not in the tray (going back to an earlier player hides what a later one took; to take it back, untake it there). Each player needs at least one mech to go on, the scenario's BV limit is **shared by all the players together** (the step shows this player's figure and the force total), and choosing fewer players gives the dropped players' mechs back. Player 1 starts with the mechs already in the hangar's Deployed group, with the named pilots already in them. The last step reviews every player's mechs, pilots and BV Its **Deploy** posts the plan to `POST /api/deploy/plan` (`plan.go`: `players`, then `p<i>_units` and `p<i>_assign_unit` / `p<i>_assign_pilot` for each player), which re-checks everything on the server (the player count against the campaign's range, `planProblem`/`deployProblem` over all the players' mechs together, `parseCrewPairs` for each player's pilots, no pilot or mech twice, an assignment only on a mech that player takes) and describes the plan back. **It does not touch MekBay yet**: the wizard then says the plan is valid and nothing has been sent; building each player's force in their own MekBay account and the OpFor in the OpFor's, and the operation, is the next step. The earlier single-player `POST /api/mekbay/deploy` and `SyncOperation` are still in the code but the wizard no longer calls them. `TestPlayerRange`, `TestPlanProblem`, `TestDeployPlanEndpoint`; the wizard was driven with jsdom (`deploy_wizard_check.js`: the picker, a step per player, what is left over, the review, the progress bar, the request) and the dialog in headless Edge.

**Assigning named pilots to mechs (Deploy popup).** MekBay already stores a crew (a name and Gunnery and Piloting skills) on every unit, so an assignment is just that: the named pilot's name and their *current* levels written into the unit's crew in the hangar force (`crew.go`: `CrewAssignment`, `applyCrew`, `parseCrew`). The popup (`static/mekbay.js`) shows a **Pilots** tray above the mech list with the campaign's living named pilots (`Page.PilotsJSON`, the `data-pilots` attribute; portrait, name, rank and a compact strip of four mini stat boxes, GUN, PIL, EDGE and ABIL, a tiny label over a bold yellow number, which fits on a second row of both the tray chip and the slot), and every selectable mech row has a **pilot slot** beside it: **drag a pilot onto a slot** to assign them (HTML5 drag and drop; a pilot already in a mech can be dragged from its slot to another, which moves them, onto an occupied slot, which replaces its pilot and sends them back to the tray, or onto the tray, which takes them out), **or click a pilot and then a slot** (also by keyboard, and what works on touch screens), or use the × on a slot. A pilot drives one mech, so assigning them again moves them. **Hovering a pilot** (in the tray or in a slot) shows the styled hover card (`MechRow.attachTip` with `build`) laid out like the Manage page's pilot card: portrait, name, rank and SP earned, the four real stat boxes (`.stat-box`: level, next level, SP progress and bar, max at the top) and the Edge abilities they have chosen as chips (or "None learned yet"); it is **interactive** (`attachTip`'s `interactive` option): leaving the pilot closes it only after a 250 ms grace period, so the pointer can travel onto the card, and it stays open while the pointer is on it; **hovering one of the Edge ability chips inside it shows that ability's card** (`AbilityCard.attach`, the same card as the Manage page, a second popover shown after the first so it sits on top; the ability catalog comes from the dialog's `data-abilities`, and `PilotsJSON` sends each learned ability as `{id, name}`); it hides when a drag starts or the page scrolls, and the chip carries all four numbers in its `aria-label`. Every mech row in the popup is as tall as a row with a pilot in its slot (`.deploy-slot` has a minimum height, empty or filled, and the mech row stretches to it), so the list is uniform, and their content (icon, model, name, chips and the role label, whose band is wider with a bigger base size via the `--role-size` and `--role-scale` CSS variables) is scaled up to fill that height; the popup itself is wide (`dialog.deploy`, 68rem) (`.deploy-unit.has-slot` overrides in `style.css`). The pilot hover card waits **half a second** before it appears (`attachTip`'s `delay` option, 500 ms; leaving or starting a drag first cancels it, keyboard focus shows it at once); the status pills' tooltips have no delay. A named pilot already crewing a mech in MekBay (matched by name, ignoring case) shows in its slot when the popup opens; an unnamed or unknown crew doesn't. A destroyed or unknown mech has no slot, and a campaign with no living named pilots has no tray or slots (rows keep their crew chip). **Nothing is saved until Deploy**: it posts `assign_unit` / `assign_pilot` pairs (every mech that has a named pilot, so skills are refreshed after SP is spent, plus any that had one and lost it, sent with an empty pilot), and `parseCrew` checks them (units in the hangar, living named pilots only, no pilot or unit twice, skills taken from the pilot's levels and never from the request); `SyncOperation` applies them to the same hangar save as the Deployed and Hangar groups, and `applyCrew` also takes an assigned pilot off any unit they were crewing that wasn't named, so a pilot is never in two mechs. A unit with its pilot removed goes back to an unnamed 4/5 crew. The unit checkboxes and the Reset OpFor box use the themed checkbox (`input.themed-box` / `.themed-check`, a square dark box that fills yellow with a dark tick). A themed checkbox draws no ring after a mouse click (the dialog's generic `input:focus` outline used to leave a clipped one behind in the scrolling list); keyboard focus draws a white ring *inside* the box (`:focus-visible`, negative outline offset), so no overflow can clip it. `TestApplyCrew`, `TestParseCrew`, `TestDeployCarriesPilotAssignments`; the popup was driven with jsdom (drag events with a fake `dataTransfer`).

**Hangar cache (pull-through).** Reading a hangar from MekBay takes a moment, so every successful live read is also saved in the database (`hangar_cache`, one row per playthrough and campaign: the hangar link's instance, the `HangarForce` as JSON, and a Unix time; `Store.SaveHangarCache/CachedHangar`, `hangarcache.go`; works on SQLite and Postgres and is cleared by `DeleteRun`). The campaign overview and the scenario page embed the last copy (`Page.ForceJSON` / `Page.DeployJSON` in a `data-cached` attribute) so they paint the hangar straight away, and `force.js` / `mekbay.js` then read MekBay in the background and replace it (stale-while-revalidate): only a run that has never been read shows "Reading your hangar...", once. A failed live read keeps the cached copy on screen with a "Showing your last known hangar" note; the deploy popup keeps the player's ticks across the refresh. The live endpoints `GET /api/campaign/force` and `GET /api/mekbay/hangar` write through; starting a campaign primes the cache with the hangar its starting check read. A copy belongs to the hangar link it was read from, so changing the link makes the old one invisible (`CachedHangar` matches on the instance). The deploy itself and the start check's own reads are always live. `TestHangarCachePullThrough` and `hangarCacheStore` cover the server; the scripts were driven with jsdom (no JS test runner in the repo).

Findings from probing MekBay (2026-11): its server is closed source and only reachable over `wss://mekbay.com/ws`, so everything here is unofficial and may break. An anonymous client (random `sessionId` and `uuid`, `register` with `version: 2`, then `getForce {instanceId}`) can read any force by ID; writes (`saveForce`) need the owner's UID, which is why setup has the optional owner UID (modify mode). Read-only is the default and the design must work without writing.

- **Unit condition pills (Hangar rows).** MekBay stores no "crippled" flag (only `destroyed`, the raw `locations`/`crits`, and a torso-check result in `state.ruleChecks`; crippled is computed in its client, `src/app/models/rules/mek-rules.ts`), so `condition.go` recomputes it the way MekBay does (forced withdrawal on, its default): two engine crits; two destroyed limbs, one a leg; two destroyed torsos; or one destroyed torso when the engine isn't Fusion/Compact or the stored torso check failed. A location is destroyed when its internal loss reaches its structure, taken from `structureByTons` (standard bipeds; an unknown tonnage never counts as crippled), and the catalog's `engine` is in `units_index.json` for that. `conditionOf` shows the worst state only: destroyed > crippled > internal structure damage > armor damage, each its own pill colour on the mech row (`mechrow.js`, `.mr-chip.cond-*`; the tooltip says why), plus a separate blue "Ammo expended" pill when any ammo bin has been used (rearming is a different need from repair). Hangar views carry `condition`, `conditionNote`, `ammoExpended`. `TestConditionsOfTheLiveHangar` replays the raw values of a real four-mech hangar.
- **Status pill tooltips.** The condition and ammo pills on a mech row don't use the browser's `title`: hovering or keyboard-focusing one shows the same floating card as the unit icons (`.unit-tip.pill-tip`, built by `attachTip` in `mechrow.js`, one element per page. It is a `popover="manual"` shown with `showPopover()` and **a child of the open dialog** when the element it belongs to is in one (else of `<body>`): the popover renders in the top layer, above the dialog and **not clipped by a dialog's cut-corner `clip-path`** (which clips everything inside a dialog, including a fixed-position child), while living inside the dialog keeps it **hoverable**, because everything outside a modal dialog is inert (a card on `<body>` showed fine but `elementFromPoint` over it returned the list behind it, so the pointer could never reach it); a browser without popovers just keeps it inside the dialog. A delayed show is dropped if the element has left the page (`isConnected`), and `MechRow.hideTip()` closes a card before the popup re-renders its pilots, which stops a card being placed at (0, 0) when a live hangar read replaces the chips during the hover delay): the condition in its colour with the reason as a sentence (location codes spelled out, `conditionText`), and for the ammo pill the breakdown and the rearm cost.
- **Purchase new unit (Hangar section).** A "Purchase new unit" button under the unit rows opens `#purchase-dialog` (`static/purchase.js`): a search box over MekBay's unit list (`GET /api/units/search?q=&campaign=&all=1`, `search.go`; debounced, a reply for older text is ignored, Enter searches rather than buys), whose results are the same mech rows as the hangar (without the pilot chip) with the unit-page link, and **clicking a row adds it to "Your cart"** (no Stage button; `MechRow`'s `onPick`, also Enter or Space) **and clicking it again takes it out**: the cart holds one of each unit (`stage` refuses a duplicate), a result in the cart is tinted like a unit picked in the deploy popup and badged `In cart`, and the cart sits below the results (which keep a fixed height so rows don't jump), each cart row with a small × to remove it; the search box is a themed field with a magnifier and a clear button (its placeholder is the only instruction; the results area stays empty until something is typed), and the faction checkbox the site's square yellow-ticked `.themed-check`; MekBay offers no embeddable search or way to hand a chosen unit back (no postMessage or callback), but its data is public, so the site searches its own embedded catalog the way MekBay does (typed words matched, punctuation ignored, against chassis and model; mechs only; best matches first: every word starting a word of the name, then by name; at most 40 shown with the total). A campaign names a faction and an era in `Intro.md` (`availability_faction: Clan Wolf`, `availability_era: Clan Invasion` for Refusal War), and the search then lists only the units MekBay says that faction fields in that era (`availability.json`, built by `gen_units.go` from MekBay's `factions.json` and `eras.json`, vendored in `data/`, joined by Master Unit List ID), with a checkbox in the popup, ticked by default, to search everything (`all=1`); a campaign that names neither has no filter. Re-run `go generate ./internal/site` after refreshing `data/units.json`, `factions.json` or `eras.json`, or when a campaign names a new faction or era. the same "Cost N SP. Warchest A → B SP." line as repair, and a Buy button. BV is SP: each unit costs its base BV. Buy posts `POST /api/hangar/purchase` (`purchaseUnits` in `purchase.go`, repeated `unit` fields; needs a hangar the site owns; `purchaseCost` refuses anything that isn't a catalog mech), which charges the warchest first (`SpendWarchest`, refunded if MekBay fails) and adds each unit, undamaged with a 4/5 pilot, to the force's Hangar group in MekBay (`MekBayClient.PurchaseUnits`, `addUnitsToForce`). `TestPurchaseEndpoint`, `TestAddUnitsToForce`, `TestPurchaseCost`.
- **Manage force from a sortie.** Each scenario page's Deploy section has a **Manage force** button (`#manage-link`) to `/<campaign>/manage/?back=<scenario slug>`; the Manage page then shows 'Back to Sortie NNN: Title' to that scenario instead of 'Back to the campaign'. Only a real scenario of the campaign is honoured (it is looked up with `Campaign.Scenario`, never echoed as a URL), so `?back=` can't be used for an open redirect. `TestManageBackLinkReturnsToTheSortie`.
- **Selling units (Hangar rows).** Every mech row has a **Sell** button after Rearm and Repair (`hangarlist.js`, `sell.go`). A unit sells for half its base BV in SP; a unit that is not fully repaired and rearmed (`unitPristine`: no recorded damage, not destroyed, no spent ammunition) gets half of that again, rounding down, so about BV/4 (`sellValue`). A truly destroyed mech can't be repaired (and now can't be rearmed either: `POST /api/hangar/service` answers 409), so selling is its only action, always at the reduced price. The confirmation (danger style) lists the price breakdown as `Confirm` items (base BV at 100%, the 50% price for a fully repaired and rearmed unit, the 25% price and why when it is worn, what it sells for) and shows the warchest change; `POST /api/hangar/sell` (`sellUnit`, needs a hangar the site owns) works the price out itself from the unit's state (the page's `sellValue`/`sellFull` are only for display), removes the unit and its crew from the site's copy with `MekBayClient.SellUnit` (`removeUnitFromForce`) and **then** pays the warchest (`RefundWarchest`), so a failure in MekBay never pays for a unit the player still has. `TestSellValue`, `TestRemoveUnitFromForce`, `TestSellUnitEndpoint`.
- **Reconfiguring omnimechs (Hangar rows).** An omnimech (`omni` in `units_index.json`, `Unit.Omni`) has a **Reconfigure** button (`swap.go`, `#swap-dialog` in `manage.html`, `hangarlist.js`) whose variant dropdown starts on the current variant (Reconfigure disabled, since that would change nothing) and lists the other variants of the same chassis with their BV and price, coloured like a stock (green for more BV, red for less); choosing one shows the unit's full mech row, a flow arrow with the BV change and price, the new variant's full row (`swapOptions` carries what a row needs) and a brief cost breakdown (50% of tonnage, 50% of BV gained) (`swapOptions`, sent as `swapOptions` in the hangar views; other units have none and no button). The SP Activity Cost Table prices a reconfiguration at half the tonnage, but BV is SP here, so that alone would let a cheap starting variant be swapped up almost free (beating the starting BV cap) and then sold at a profit. The price is **half the tonnage (rounded up) plus half the BV gained (rounded down)**, and swapping to a lower-BV variant costs only the half tonnage with no refund (`swapPrice`): cheaper than selling and buying the other variant (so being an omni matters), while swapping up and selling a clean unit always loses the half tonnage. The unit must be fully repaired and rearmed (`unitPristine`; 409 otherwise) because the old variant's crit slots and ammo don't map onto the new one; only omnimechs can swap (400), only to a variant offered for them. Crews are a per-scenario matter, so the swap carries no crew over: `swapUnitState` replaces the unit's design and gives it a fresh state. `POST /api/hangar/swap` (`swapUnit`, needs a hangar the site owns) charges the warchest first and refunds it if MekBay fails, like repairs. `TestSwapPriceAndOptions`, `TestSwapUnitState`, `TestSwapUnitEndpoint`. Re-run `go generate ./internal/site` after refreshing `data/units.json` (the index carries the omni flag).
- **Truly destroyed, repair and rearm (Hangar rows).** Per Hot Spots: Draconis Reach (the SP Activity Cost Table and "Destroyed vs. Truly Destroyed", printed p. 33, physical page 35), a mech whose center torso internal structure is eliminated is **truly destroyed** (`CondTruly`, shown as a dark red "Truly destroyed" pill, above plain destroyed): it can't be repaired or salvaged. Every other mech row has **Rearm** and **Repair** buttons at its right (`mechrow.js` `actions`, wired in `hangarlist.js`, costs from the server in `service.go`). Repair costs tonnage x 0.5 (armor only), x 2 (structure and/or crits), x 3 (crippled) or x 5 (destroyed), x 1.5 rounded up for Clan or Mixed tech, and a repair at one level also covers the levels before it in the list. The repair dialog (`#repair-dialog`) lists only the repairs that would fix something on that unit (`repairOptions`: armor if any armor is lost; structure if a surviving location has lost internal structure or has a critical hit, engine hits excluded; crippled for a crippled or destroyed unit; destroyed for a destroyed one), none greyed out, the highest selected, with the price following the choice; any one can be chosen on its own, so a crippled unit can have just its armor repaired. What each level clears (`serviceUnitState`/`repairState`): armor = lost armor everywhere; structure = also internal structure in locations that aren't destroyed and critical hits there (not the engine's, which cripple, and not a destroyed location's); crippled = everything (locations, crits, torso check); destroyed = also the destroyed flag. Rearm is 10 SP per ton, counting each ammo bin with any consumed as one ton (`HangarUnit.AmmoBins`) and is confirmed with `Confirm.ask`, which lists the breakdown first (`items`: one row per ammo type, e.g. "LRM 5 Ammo: 1 ton · 5 of 24 shots used", from `ammoBreakdown`: MekBay records only the shots used per bin, so the capacity per ton comes from the unit's `ammo` entries in `units_index.json`, shots divided by slots, and a bin the catalog doesn't list still counts as a ton with an unknown capacity), whose optional `detail` line (bold yellow, red with `detailShort`) carries the same "Cost N SP. Warchest A → B SP." text as the repair dialog. Both go through `POST /api/hangar/service` (`serviceUnit`): needs a hangar the site owns (it edits the force in MekBay with `MekBayClient.ServiceUnit`, `serviceUnitState` in `service.go`, `saveForce` like a deploy), the server works out the condition and the price itself (a repair names the level chosen and is refused with 409 if it isn't one of the unit's current options), charges the warchest atomically first (`Store.SpendWarchest`, 409 if it can't cover it) and refunds it if MekBay fails (`RefundWarchest`). Without an owned hangar (a run from before the site made copies) the buttons are disabled with a tooltip and the endpoints answer 409. `TestServiceUnitEndpoint`, `TestServiceUnitState`, `TestRepairCostsFollowTheSPActivityCostTable`.
- **Damage:** a unit's `state.locations[loc].armor` / `.internal` are points *lost* (absent when undamaged), `state.crits` has critical hits and ammo `consumed`, `state.crew` has pilot hits. Join units to `data/units.json` by the unit's `unit` field (equals `name` there) for costs and totals.
- **Alignment is not stored in a force.** "Hostile" is only the `enemy:` prefix in the URL (`?instance=<mine>,enemy:<opfor>`) or an Operation (`?operation=<id>`, a saved list of whole forces with alignments; anonymous reads work). The OpFor is a separate saved force with its own instance ID, so setup should eventually accept the multi-force link and store the friendly and `enemy:` instance IDs separately, not a single `instance`.
- **MekBay cannot load part of a force.** Chosen design for deployment: the campaign's hangar force holds every mech, and players drag the units going on a sortie into a group named "Deployed" (case-insensitive); every other group is reserve. The site treats that group as the sortie roster. "Start sortie" records the roster and a damage/ammo/crew snapshot in our own database, "end sortie" re-reads the force and diffs against it, and a change to a reserve unit is flagged rather than billed. Players can regroup later without rewriting history because the snapshot is ours. Repairs are billed from the diff; clearing the damage in MekBay is up to the player unless modify mode is on.
- **Sortie hotlinks** could be built as `https://mekbay.com/?instance=<campaign>,enemy:<sortie opfor>` once each sortie's OpFor force exists (unknown: whether a non-owner can mark damage on a force they don't own; the scenario operation above already gives players a one-click link).

## Scenario file conventions

Follow the layout in `Scenario_000/Setup.md` and `Scenario_000/Outcome.md` when adding scenarios:

- Both files start with YAML front matter holding the machine-readable fields; the Markdown body below it is the human-readable write-up. The folder name lowercased (`Scenario_000` -> `scenario_000`) is the scenario `id`, and all cross-references (`next`, branch targets) use IDs, never titles.
  - `Setup.md` front matter: `id`, `title`, `planet` (the planet the scenario takes place on, e.g. `Strana Mechty` for Scenario 000; every scenario has one), `map`, `forces` (maps `opfor1`, `opfor2`... to the `.mul` files beside it), `provided_units` (optional list of MekBay unit IDs the players pick from instead of their hangar, see Provided forces), `readout` (optional list of `Label: value` lines, kept in order, drawn as a translucent technical readout over the left of the first image, and below it on narrow pages; used for planet data), and `images` (list of paths in the folder's `images/`, e.g. `images/strana_mechty.png`; each is shown as a wide fluff-image banner under the scenario title, cropped to the top, so put the subject in the upper part of the picture; empty until used).
  - `Outcome.md` front matter: `id`, `default_next`, `branches` (optional list of scenario IDs this scenario may lead to; omitted, it leads to `default_next` or the next number), and, only when a scenario actually branches or changes state, `outcomes`, a list of `{when, grants, next}`. Scenario 000 has none: it bootstraps the campaign's starting parameters (starting SP and pilot) rather than granting keywords. `when` is a plain condition over `kills` and `pilot_dead` for now (`kills >= 1`, `pilot_dead or kills == 0`); keep it simple and settle the syntax when a second scenario needs more. `grants` and any required keywords are IDs from `campaigns/RefusalWar/Keywords.md`; add new keywords there before using them.
- Deployment: every unit eventually gets an initial hex position (or is marked off-map with custom rules). Play uses standard two-mapsheet neoprene battlemats with labeled hexes. Hexes are written as four digits, `XXYY` (column then row, e.g. `2113`), as in `Scenario_001`; any other position format is still undecided, so leave deployment positions as `TBD` and don't invent coordinates or a schema until the user supplies them.
- `Setup.md`: `# Scenario NNN: <Title>`, a blockquote of fluff text (if it isn't written yet, leave the placeholder rather than inventing lore). Fluff is a mission briefing: an in-world commander speaking directly to the player in second person, formal and terse, in the style of the MechWarrior 2 briefings (see `Scenario_000/Setup.md`). Aim for less is more: show, don't tell, with a slightly alien yet familiar tone (Hidetaka Miyazaki-style lore, Dune), keep it to a few lines, and don't restate the rules that the sections below cover, then `## Overview`, `## Map`, `## Forces` (each force group, `### Player Forces` and `### OpFor N`, has a `**Deployment:**` line; the OpFor groups are bullet lists written as `Variant (gunnery/piloting) Role: Pilot, hex XXYY`, e.g. `Nova Prime (3/4) Skirmisher: Star Commander Alrek, hex 2113` (the role is the unit's Master Unit List role, capitalized as there: Scout, Striker, Skirmisher, Brawler, Missile Boat, Sniper, Juggernaut, Ambusher; look it up in the `role` field of `data/units.json`; the hex is left off for reserves, and `: Pilot, hex XXYY` entirely when neither is set yet, as in Scenario 000), with the mech name hyperlinked to MekBay as `https://mekbay.com/?gs=cbt&shareUnit=BM<IS-name>_<Variant>&tab=Sheet`; the unit ID is not always obvious: the chassis name has no spaces, the variant follows an underscore, and a chassis with no named variant takes no suffix. Some chassis use the Inner Sphere name (Mist Lynx is `BMKoshi_E`, Kit Fox is `BMUller_J`) while others don't (`BMMadCat_H` for Timber Wolf H, `BMLoki_Prime`, `BMGrizzly`). Ask the user for the working URL rather than guessing a new one) `## Special Rules`, and, when the scenario uses waypoints, `## Waypoints` last. Waypoints are a core mechanic, like the back-of-book waypoints in BattleTech: Aces (Scouring Sands): you only read one when the game calls for it. Each is a `### Waypoint X` heading (any `### ` name works) with its rules text beneath it; text between `## Waypoints` and the first `### ` is dropped. Where they are placed, and when they are revealed, belongs in `## Map` and `## Special Rules`. The site pulls the section out of `Setup.md` and shows each waypoint redacted (its text blacked out line by line, with a Reveal button that wipes the bars away; without JavaScript they are simply readable), inside the collapsed Waypoints block.
- `Outcome.md`: `# Scenario NNN: <Title> - Outcome` with `## Victory & Rewards`. Rewards are in SP (the campaign's pilot-advancement points). The kills-to-SP table is specific to Scenario 000's graduation mission; don't assume later scenarios use it.
- Campaign rules visible so far: pilots are named and persistent; a pilot who dies or fails to score a kill in the graduation mission is permanently removed and replaced by a new named pilot with 0 SP for Sortie 001; Clan honor rules such as zellbrigen apply and violations have mechanical consequences.

## Force files (.mul)

Each scenario folder also holds `OpFor1.mul` and `OpFor2.mul`: MegaMek's XML force format (MekBay exports and imports it), one `<entity>` per mech with its `<pilot>` skills and `<Game id>`. Prefer a real MekBay export over hand-writing. When hand-writing, `chassis` and `model` must match MegaMek's database. A mech with two names uses `chassis="<Inner Sphere name> (<Clan name>)"`, e.g. `Koshi (Mist Lynx)` or `Mad Cat (Timber Wolf)`; a single-name mech such as the Grizzly has a plain chassis and an empty `model`. Deployment attributes, `externalId` and `quirks` can be omitted.

## Working notes

- Mech names and variants are canon BattleTech Clan designs (e.g. Mist Lynx, Timber Wolf, Shadow Cat, Loki); keep to real variant names and Clan terminology (touman, zellbrigen, Trial, etc.).
- For mech data, the authoritative sources are the Master Unit List (`https://masterunitlist.battletech.com/units/<chassis>-<variant>`, e.g. `shadow-cat-a`) and MekBay, not Sarna. The MUL site is behind a Cloudflare bot challenge and returns 403 to automated fetches.
- `data/units.json` is a vendored copy of MekBay's unit catalog, downloaded from `https://db.mekbay.com/units.json` on 2026-11-16 (with `factions.json` and `eras.json` from the same host) (~27 MB; MekBay builds it from MegaMek's `mm-data`). To refresh it, re-download that URL over the file (e.g. `curl --compressed -o data/units.json https://db.mekbay.com/units.json`). Search it with Grep/Python rather than reading it whole. Each entry's `chassis` and `model` are exactly what `.mul` files need, and its `name` field is the `shareUnit` ID for MekBay links (e.g. `BMMadCat_H`). MekBay's source is at `../mekbay`.
- Maps referenced are official BattleTech battlemats (e.g. "Circles of Equals").
